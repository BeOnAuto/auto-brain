# @beonauto/computation

The implementation of computation functions. A computation function is a program in TypeScript with schemas for its input and output; a run calls the program's function with its input and answers with the value it returns, the same for the same input on every host of the same image, within bounds on its work, its memory, its stack, the values it answers and its time. [Decision 0005](../../docs/decisions/0005-computation-functions.md) says why it exists and how it is bounded.

User documentation is [Computation function format](../../docs/reference/computation-format.md), published at [on.auto/docs](https://on.auto/docs/): the document, the types, the check at save, the sandbox, the number rules, the endings and the bounds. Update it alongside behaviour changes.

## The document

`parseComputationDocument(source)` reads a document with the shared reader of [`@beonauto/definitions/document`](../../packages/definitions/README.md#reading-function-documents) and gives a `ComputationFunctionDefinitionDocument`: an optional `description`, the `language`, `typescript`, the compiled `input.schema` and `output.schema` when the document has them, the `program`, the module, and the line it starts on. A language other than `typescript` is refused with the engine's `oneLanguage`, `The brain's one language is TypeScript; write the program as a TypeScript function`, at its line. The front matter's keys are `description`, `language`, `input.schema` and `output.schema`; every other key, `model`, `config`, `tools`, `output.format` and `input.default` among them, is an issue at its line, and the message for empty front matter names `the language`. A schema is compiled with the reader's compiler and validates values nested at most 512 levels.

Parsing keeps the module as it is written. The module is checked when the document is saved, by the capability's `check` (`src/document/document-check.ts`), which asks the pool's check worker of [`@beonauto/definitions`](../../packages/definitions/README.md#the-check-at-save), a step of the save beside `prepare`, against `Input` and `Output`, the schemas as types, with the TypeScript compiler and the sandbox's own library, each problem refused with its line in the document and the compiler's words, in the words of a document that does not parse; a check that does not answer within 2 seconds leaves the document unsaved, `unavailable`. A run never checks again.

## A run

`makeComputationFunctionAdapter({ pool, deadlineMs })` makes the capability for `makeDefinitionOperations`; the server gives it a `ProgramPool` of the engine, with `COMPUTATION_WORKERS` workers. `deadlineMs` is 10,000 unless a test gives less, and is the capability's `longestAnyRunMs`. The capability reaches nothing outside and changes nothing there, calls no tools, and is stopped when its call is cancelled. A run:

1. refuses an input nested deeper than 512 levels, and one its input schema refuses, as `invalid_input` with the schema's pointers;
2. asks the pool to call the module's default export with the input, in a fresh sandbox of the engine (see [the engine](../../packages/workflow-engine/README.md#the-sandbox)) of `memoryBytes`, 256 MiB, with a stack of 1 MiB, under a budget of 20,000 checkpoints, with the moment the run started as the time of `Date`, the deadline counted from the start of the run and an output of at most `mostOutputBytes`, 1 MiB less 256 bytes for the record;
3. names the checked worker, `checkedWorker` of `@beonauto/definitions/json-schema`, for every run, with the output schema as the request's context or `null` when the definition has none, so every run of computation and recall functions is served by one worker module and the pool never lets go of a warm worker to start another module's (200 jobs at once on 4 permits took 346 ms on one module, against 6,801 ms alternating between two, at the medians of three; see [the engine](../../packages/workflow-engine/README.md#the-workers-of-the-pool-measured)); with a schema, the worker that runs the program also checks the output against the schema, under the run's deadline, and the thread that serves requests never waits on the check: a 1 MiB output against a recursive schema had taken 1,038 ms there;
4. turns the outcome into the run's ending (`src/run/run-outcome.ts`):

| Outcome of the pool                                                                      | Ending                                                                                                                        |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| answered, the output schema, if any, accepting it                                        | succeeded, with the output and the record `{ language, work, duration_ms, input_bytes, output_bytes }`, `work` in checkpoints |
| mismatched: its worker found the output does not match the output schema                 | `conflict`, kind `unworkable`, with the first three issues in the words of `issuesDetail`, each part cut at 1,024 bytes       |
| raised, a stack overflow the program did not catch among them                            | `conflict`, `unworkable`: `The program raised an error on line N: <its name and message>`, cut at 1,024 bytes                 |
| exhausted by work, by the memory of its sandbox or by the stack of its worker            | `conflict`, `unworkable`, naming the bound, and for memory the checkpoints spent                                              |
| an output that is not JSON, nests deeper than 512 levels, or is over its bytes           | `conflict`, `unworkable`, with the path of the member refused                                                                 |
| exhausted by the deadline, or stopped by the deadline, its worker's heap, no free worker | `unavailable`, with words that name the bound or the number of workers                                                        |
| stopped because the call was cancelled or the server is stopping                         | `unavailable`; the operations record the cancelled run as `failed`                                                            |
| crashed, or refused by a worker although the definition was accepted                     | a defect: the call fails with an incident and the run is `failed`                                                             |

A `conflict` of the kind `unworkable` is recorded with its kind, so the run, the listing and the history show it, and a workflow sees a `runtime` error of status 409 with that kind, which a retry policy matching 503 leaves alone. The words of a run that succeeded say `Its result: ...` from the output, or that it is too long to repeat.

## Bounds

`computationBounds` holds them: a budget of 20,000 checkpoints, a deadline of 10,000 ms, a sandbox of 256 MiB, a stack of 1 MiB, a worker heap of 256 MiB, 4 workers by default and a value depth of 512; the engine's pool adds the worker's own stack of 64 MiB. Each bound has a test that reaches it and ends as [the reference](../../docs/reference/computation-format.md#bounds) says (`src/run/run-endings.test.ts`, and the server's `src/computation` for the deadline over HTTP, a busy pool and a crash). Tests that start workers have 30 seconds, and assert wall-clock time only as a lower bound.

The hosted runtime does not offer computation functions until its adapter bounds the time and the memory of a run, measured in a real isolate; the sandbox's own memory maximum and deadline are the bounds it would keep, and its isolates have no threads, so a run that stalls in one native operation is stopped there by its deadline alone. The server here runs every run in a worker thread, terminated at the run's deadline and let go of after any run the pool had to stop.

## Measurements

`pnpm --filter @beonauto/computation measure` measures, outside the tests (`measure.ts`, with its parts in `measure/`), the checkpoints of the example by its rows and its time at the most rows its input takes, how long each of 22 constructs repeated in a loop takes to spend a run's 20,000 checkpoints, the first job of a worker and warm runs, plain and with an output schema, the JSON round trip of such a run's request, a burst of 200 runs alternating with and without an output schema, a job after its worker was idle a minute, a worker stopped at its deadline, the deepest recursion within the stack of a run, and two programs that keep allocating until their sandbox refuses. Measured on 2026-10-09 on Node 26.10.0 on an Apple M4 Max, 16 cores and 128 GiB, at a load average of about 2 to 4:

| What                                                         | Measured                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| the example's checkpoints                                    | 0 for 1,000, 2,000, 3,911 and 4,000 rows: its loops are the engine's own, `Map.groupBy`, `toSorted`, `map` and `reduce`, each calling back fewer than 10,000 times                                                                                                                   |
| the example at the most rows its input takes                 | 3,911 rows, 262,092 bytes: 4.7 ms at the median of 21 warm runs, each in a fresh sandbox                                                                                                                                                                                             |
| a run's 20,000 checkpoints, by construct, repeated in a loop | 0.85 s for a loop that does nothing, 1.6 s for a loop of calls, 2.1 s testing a regular expression, 4.6 s sorting with a comparator, 5.9 to 10.9 s reducing, concatenating strings, mapping, grouping and making a set                                                               |
| constructs whose native work spends no checkpoint            | joining, concatenating and spreading arrays, merging objects, sorting without a comparator, replacing, encoding and decoding JSON, searching, upper-casing, splitting and repeating strings and listing entries spent fewer than 20,000 checkpoints in 60 s; the deadline stops them |
| a run of a program that answers at once                      | 1.21 ms at the median of 30 warm runs, its fresh sandbox and prelude most of it                                                                                                                                                                                                      |
| the same with an output schema                               | 1.30 ms                                                                                                                                                                                                                                                                              |
| the first job of a worker, cold, of 9 fresh pools            | 196.2 ms, and 202.2 ms with an output schema; 217.0 ms once after a minute idle                                                                                                                                                                                                      |
| 200 jobs at once on 4 permits, half with an output schema    | 346 ms at the median of 3 when every job names the checked worker, against 6,801 ms when the half without a schema names the pool's plain worker                                                                                                                                     |
| a worker that never answers, under a deadline of 500 ms      | stopped after 500.6 ms                                                                                                                                                                                                                                                               |
| a function that calls itself once                            | 5,459 calls within the stack of 1 MiB of a run                                                                                                                                                                                                                                       |
| a program that keeps strings of a megabyte, twice            | stopped by memory after 0 checkpoints, 365 ms, both times                                                                                                                                                                                                                            |
| a program that keeps small objects, twice                    | stopped by memory after 395 checkpoints, 456 and 454 ms                                                                                                                                                                                                                              |

A checkpoint counts the engine's own steps, so a loop whose body is one native operation over a large value spends few of them, and the duration is the bound that stops it: thirteen of the 22 constructs ran for 60 s without spending a run's budget, where the deadline of a run is 10 s. Each run takes a fresh sandbox, so a run costs about a millisecond more than its program, and the first job of a worker pays its start and the compiling of the WebAssembly module, which the worker keeps for every job after. Every run of computation and recall functions names the checked worker, so the pool never lets go of a warm worker to start one of another module (see [The workers of the pool](../../packages/workflow-engine/README.md#the-workers-of-the-pool)); a job of each module in turn on a full pool costs twenty times as much.

## Testing

`@beonauto/computation/testing` exports `campaignPace`, the example document, and `campaignRows(count)`, an input of that many rows over four campaigns; the tests that need an outcome a real worker gives only rarely take `scriptedPool` from `@beonauto/workflow-engine/testing`. The tests of this package run real workers; the cents of the example are checked against a computation in big integers over 1,000 rows, and `src/run/warm-isolation.test.ts` runs, in one warm worker, a program that raises, one that exhausts its work, one whose output is over its bytes, one that runs out of memory, one that overflows the stack and three that write to `Object.prototype`, to `globalThis` and `Array.prototype`, and to `Math`, then finds none of it in the next program and the example answering with the same checkpoints as on a fresh worker.

## Source

`src/index.ts` is the entry point and `src/testing/index.ts` the entry point of the test support. `src/document` holds the document: its type, the front matter's keys and parsing. `src/run` holds a run: its bounds, the input's checks, the call of the pool and the endings. `src/capability` holds the capability, whose guide is the public reference page, served to agents as `computation-function`. `src/testing` holds the example and what the tests share.
