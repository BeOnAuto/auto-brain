# Run in a container

The runtime is in early development and is not ready for production use. Review [authentication and security](security.md) before exposing a deployment.

Every release publishes the image to Docker Hub as `onauto/runtime`. A container needs two things: an [API key](security.md#api-keys), because it listens on every interface, and a place for the ledger: a volume on `/data`, where it keeps the ledger in a SQLite file, or a [PostgreSQL database](#the-ledger-in-postgresql).

```bash
docker run --rm --log-driver none onauto/runtime:latest node packages/identity/src/key-command.ts --org acme
echo 'API_KEYS=[<the API_KEYS entry it printed>]' > auto-runtime.env
docker volume create auto-runtime-data
docker run --rm --publish 5555:5555 --env-file auto-runtime.env --volume auto-runtime-data:/data onauto/runtime:latest
curl --header 'authorization: Bearer <the key it printed>' http://localhost:5555/v1/orgs/acme/playbooks
```

Without a named volume, Docker gives each container a fresh anonymous volume, so its playbooks last only as long as that container.

The image reads a configuration file only when `CONFIG_FILE` names one. Mount the file read-only and name it:

```bash
docker run --rm --publish 5555:5555 --env-file auto-runtime.env --volume auto-runtime-data:/data \
  --volume "$PWD/auto-runtime.yaml:/etc/auto-runtime/auto-runtime.yaml:ro" --env CONFIG_FILE=/etc/auto-runtime/auto-runtime.yaml \
  onauto/runtime:latest
```

The secrets the file refers to, such as `GATEWAY_API_KEY`, go in `auto-runtime.env` with the other variables.

The [computation function adapter](../../reference/computation-format.md) runs each run of a computation function in a worker thread the server keeps between runs, so a run pays for starting a worker only when none is ready, with this setting:

| Variable              | Default | Purpose                                                                                                                                                      |
| --------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `COMPUTATION_WORKERS` | `4`     | The most worker threads the server keeps, and so the most runs it takes at once, from 1 to 64; a run that finds none free within 10 seconds is `unavailable` |

The server never keeps more worker threads alive, idle or busy, than this setting. It ends a worker after a run that ran past its time, used too much memory, was cancelled or broke, after its thousandth run, and after a minute without one, and starts another when a run needs it. A worker is stopped when its heap grows past 256 MiB, and it has a stack of 64 MiB, so plan for about 320 MiB for each worker on top of the server's own memory, about 1.25 GiB for the default four. A value outside the range stops the server at start, naming the setting.

The [recall function adapter](../../reference/recall-format.md) shares those workers: a run of a recall function answers in one, and the server that runs the workflows keeps the views of recall functions, folding each page of a playbook's history in one, using at most half of them at once and at least one. It keeps each view in a table beside the workflows' tables, in the ledger's database, so a view needs no other storage. These settings bound it:

| Variable                   | Default | Purpose                                                                                                                                          |
| -------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `RECALL_MAX_FUNCTIONS`     | `32`    | How many active recall functions a playbook may keep, from 1 to 1000; lowering it below what a playbook keeps refuses its saves and nothing else |
| `RECALL_MAX_REBUILDS`      | `4`     | How many views of one playbook are built at once, from 1 to 64; the others wait in the order they were saved                                     |
| `RECALL_PLAYBOOKS_AT_ONCE` | `4`     | How many playbooks the server folds at once, from 1 to 64                                                                                        |

A value outside its range stops the server at start, naming the setting.

The [prediction function adapter](../../reference/prediction-format.md) keeps the dataset of each saved prediction function in two tables beside the views, folded by the same server from the same pages of history, at most two datasets of a playbook built at once. The `data` tests of its filters run on the pool's one filter thread beside those workers, which the trigger and listener filters of workflows share: a dataset's tests are prepared once a page and each event is tested in that session, so a page of 1,000 events a data test reads cost about 63 ms more than one without, 107 ms against 44 ms measured on SQLite, its tests taking their turns on that thread one at a time with the workflows' filters. A dataset uploaded over HTTP is kept in the ledger's content. This setting bounds it:

| Variable                   | Default | Purpose                                                                                                                                              |
| -------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PREDICTION_MAX_FUNCTIONS` | `32`    | How many active prediction functions a playbook may keep, from 1 to 1000; lowering it below what a playbook keeps refuses its saves and nothing else |

The [interaction function adapter](../../reference/interaction-format.md) keeps the open requests in a table of the ledger's database, written in the same transaction as each run's facts, and the server that runs the workflows performs their expiries and delivery attempts with its timers, so a request needs no other storage or schedule. A function sends its request through a tool of a server in `mcp_servers`, which it names itself, and this setting goes with it:

| Variable                    | Default | Purpose                                                                                                                               |
| --------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `INTERACTION_OPEN_REQUESTS` | `10000` | How many requests a playbook may have open at once, from 1 to 1,000,000; a run past it is `unavailable` with the kind `requests_full` |

The server keeps a pool of model processes for prediction functions, which check the candidates a trainer uploads, score them in a build, make a shadow's predictions and answer questions: each a child process of its own, started only when a job asks for one and kept warm for the model it loaded, with an empty environment and no handle to the ledger, so a model that misbehaves ends its own process and never the server. The model processes load models with `onnxruntime-node`, whose native libraries the image keeps for its own architecture alone. In the image each runs under `prlimit` from the base image's `util-linux`, which bounds its data, the native allocations of a model's runtime as well as Node's heap, and sets its core file size to 0, so the kernel writes no core file when it crashes. A host whose core pattern pipes dumps to a helper still hands the dump to that helper, and the job's ordinary deadline remains the guard while the helper reads it (2.2 s measured on CI). These settings bound the pool:

| Variable                    | Default                 | Purpose                                                                                                                                                                                                                                                                                                   |
| --------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PREDICTION_PROCESSES`      | `4`                     | How many model processes run at once, from 2 to 64                                                                                                                                                                                                                                                        |
| `PREDICTION_PROCESS_MEMORY` | `1280`                  | The data each model process may reserve, in MiB, from 768 to 16,384; a process that reaches it is ended, and its job ends out of memory                                                                                                                                                                   |
| `PREDICTION_BUILDS_AT_ONCE` | `2`                     | How many builds the server may score at once, each holding one of the processes while its candidates are checked and walked, from 1 to 63 and below `PREDICTION_PROCESSES`, so that a prediction always finds a process; a build waiting for its trainer or for an approval holds none and is not counted |
| `PREDICTION_BUILDS_PER_DAY` | `4`                     | How many builds a prediction function may ask in a day, from 1 to 100; a build past it is `unavailable` with the kind `builds_full`                                                                                                                                                                       |
| `PREDICTION_CACHE_DIR`      | `/var/tmp/auto-runtime` | The absolute path of the folder the model processes read their files from, which the server makes readable by its own user alone; a folder that belongs to another user, or that other users may write to, stops the server at start                                                                      |

`PREDICTION_PROCESS_MEMORY` sets `RLIMIT_DATA`, which counts a process's writable private address space, and V8 reserves much of that eagerly, for its code range and its heap, about 700 MiB of it on amd64 before any work is done; so the setting bounds the data a process reserves, and its resident memory stays far below it. The least under which the model process's own entry starts, measured on 2026-10-12 in the image's Node 26.10, the image built natively on each architecture, is 704 MiB on amd64 and 448 MiB on arm64. The floor, 768 MiB, is the next multiple of 128 MiB above the larger of the two, which leaves 64 MiB of margin. The default, 1,280 MiB, is the floor plus 512 MiB of room for a loaded 64 MiB model session and its tensors, a multiple of 256 MiB. Every build of the image, on amd64 and on arm64, proves the floor: it runs `prlimit --core=0 --data=805306368 node --input-type=module --eval "await import('/app/capabilities/prediction/src/model-jobs/model-process.ts')"` as the image's user, which loads the model process's own module, `onnxruntime-node` with it, as a model process does, and fails if that does not load under 768 MiB of data.

The container's own memory limit is what bounds resident memory. Size it from the model processes' observed resident memory, on top of the server's own memory and the worker threads above, with the setting as the hard ceiling of each process; the processes times their setting, 5 GiB for the defaults, is the most they may reserve, not memory they hold. A value outside its range, as many builds at once as processes, or a cache folder another user owns or may write to stops the server at start, naming the setting. The server's start-up line states them: how many active functions a playbook may keep, how many builds a function may ask in a day, how many processes at most, how many of them the builds being scored may hold, the data each, whether `prlimit` bounds the processes, and the folder their files are kept in; where `prlimit` is not on the server's `PATH`, as on macOS, nothing bounds them.

A model process reads its model and a build's scoring rows from files the server keeps under `PREDICTION_CACHE_DIR`, the models in `models` and the rows in `rows`, each folder at most 1 GiB, the files used least recently removed first. Each file has a folder of its own named by its digest, `models/<sha256>/model.onnx` and `rows/<sha256>/rows.csv`, so the folder a model's runtime reads external data from holds that model alone. A file is written into a folder of its own name as its bytes arrive, its SHA-256 computed as it is written, and that folder is renamed to the digest once the file is whole, so a process never reads half a file. Every folder is made readable by the server's user alone: as the server starts it makes the folder `PREDICTION_CACHE_DIR` names, with mode 0700, when it is not there, refuses to start when it cannot be made or when another user owns it or may write to it, so no other user can make it first and own what the server trusts, and then reads every file it finds again and removes any whose bytes are not its digest. A model or a build's rows missing or removed are written again from the playbook's content when next needed, and a shadow's rows are written from the dataset at each close, so the folder needs no volume and loses nothing when the container is replaced. Two servers on one machine take a folder each, since each bounds by what it counts itself.

Measured on 2026-10-13 on a development machine of 16 cores with Node 26.10.0, at a load average of about 4 and with no `prlimit`, in two runs: a model process started cold, its model loaded and checked, takes about 143 ms; a question on a process that has not yet loaded the model about 140 ms, and on the process that holds it about 1 ms; each of eight candidates is walked over the scoring rows of 1,000 series, 200,000 rows, in 384 to 393 ms, far within its 10 minutes; a model of 64 MiB, on the 4 threads a process of four takes there, parses and walks the widest rows the bounds admit, 1,000 series of 200 periods with 40 features, 74 MiB, in about 1.3 s, its process resident at 644 and 649 MiB at the peak, from 160 and 166 MiB before it; and a question over an upload of those rows is answered in about 0.93 s, its window read by a model process, the server's heap no larger after it, where before the server parsed the whole upload on its event loop for each question, 1.4 s and about 315 MiB of heap. The [capability's README](../../../capabilities/prediction/README.md#measurements) has the figures and how they were taken. Every pull request's build of the image in CI, on each architecture, measures the size of the image and of the model runtime within it, and walks that 64 MiB model over the widest rows under `prlimit --data` at the default 1,280 MiB, on the threads the server gives a process of that runner, asserting that every series is walked and writing the resident memory to the run's summary. For the least data under which it does, the workflow `Model process memory` (`.github/workflows/model-memory.yml`), run by hand and never by a pull request, builds the image on each architecture, walks the model over the widest rows under 1,280 MiB, then searches by halves for the least data under which the walk still runs, to within 8 MiB; its run's summary gives, for each architecture, the resident memory before the session, after its walk and at the peak, and that least data. No figure of it is kept here: the search asserts nothing, and is run when the model runtime or the image changes.

The image is multi-arch (amd64 and arm64), runs as a non-root user that can read but not change its own code, keeps the ledger on the `/data` volume, where that user may write, as it may only in `/tmp`, `/var/tmp`, `/run/lock` and its home `/home/node` besides, and shuts down cleanly on `SIGTERM`, even in its first milliseconds, because `tini` runs as PID 1 and forwards the signal to the server. Its SQLite driver is compiled from source while the image is built. A second `SIGTERM` or `SIGINT` ends the server at once with exit code 1.

## The ledger in PostgreSQL

Set `DATABASE_URL` to a PostgreSQL database, and the server keeps the ledger there instead of in a file; the container then needs no volume. The URL holds the database's password, so it goes in `auto-runtime.env` with the other secrets, never in the configuration file, which refuses a `database_url` key:

```bash
echo 'DATABASE_URL=postgresql://auto_runtime:<password>@db.example.com:5432/auto_runtime' >> auto-runtime.env
docker run --rm --publish 5555:5555 --env-file auto-runtime.env onauto/runtime:latest
```

The server creates or migrates the ledger's tables in the database's `public` schema at every start, so its user needs `CREATE` on that schema at every start, not only the first; a user that may only read and write the tables fails to start with `permission denied for schema public`. It logs at start that the ledger is kept in PostgreSQL, naming the database and its host and never the URL. A database it cannot reach stops it at start, naming the host and port. The image needs nothing more for it: the PostgreSQL driver, `pg`, is pure JavaScript. Several servers may share the database: one runs the workflows and the others stand by to take them over; see [Workflow operations](workflows.md). Servers of different versions do not share a database at the same time: stop the servers of the old version before starting those of the new one. A version that keeps a new table in the ledger, such as the outcomes of runs that a playbook's analytics read, fills it from the ledger's history at its first start, before it answers, under the database's migration lock; another server starting meanwhile waits for that lock up to 60 seconds, longer than the longest fill the ledger README records, and stops only if it is still held then; start it again once the first is ready. The [ledger README](../../../packages/ledger/README.md#keyed-projections) records how long the fill takes. The [ledger README](../../../packages/ledger/README.md#postgresql) has the details and what was verified.

For TLS to a managed database, end the URL with `?sslmode=verify-full`: the connection is encrypted, and the database's certificate and host name are checked against the certificate authorities Node trusts. A private authority, such as your provider's root certificate mounted in the container, is added with `NODE_EXTRA_CA_CERTS`. `pg` 8 treats `sslmode=require`, `prefer` and `verify-ca` as `verify-full` too, but prints a multi-line security warning to stderr the first time it connects, so write `verify-full`. `sslmode=no-verify` encrypts without checking the certificate, which lets a machine in between read the connection; use it for nothing but a test.

### Without a password, on Amazon RDS

A database of Amazon RDS or Aurora PostgreSQL can authenticate its user with IAM instead of a password, so that no database password exists anywhere: the server signs a token for each connection it opens, from the identity the container runs as.

1. Turn IAM database authentication on for the instance or the cluster.
2. Grant the database user the `rds_iam` role, beside the privileges the ledger needs, `CREATE` on the `public` schema among them: `GRANT rds_iam TO auto_runtime;`. A user with that role signs in with a token.
3. Give the identity the container runs as, such as the role of its task or of its instance, `rds-db:connect` on that user: `arn:aws:rds-db:<region>:<account>:dbuser:<the instance's or cluster's resource id>/auto_runtime`.
4. Set `DATABASE_URL` without a password, and `DATABASE_CREDENTIALS=aws-iam`. Neither is a secret, so both may go in the container's environment.
5. Keep TLS on. The certificate authorities of Amazon RDS are not among those Node trusts, so mount their bundle, `global-bundle.pem`, in the container and name it with `NODE_EXTRA_CA_CERTS`.

```bash
echo 'DATABASE_URL=postgresql://auto_runtime@ledger.c9akciq32.eu-west-1.rds.amazonaws.com:5432/auto_runtime' >> auto-runtime.env
echo 'DATABASE_CREDENTIALS=aws-iam' >> auto-runtime.env
echo 'NODE_EXTRA_CA_CERTS=/etc/auto-runtime/rds-global-bundle.pem' >> auto-runtime.env
docker run --rm --publish 5555:5555 --env-file auto-runtime.env \
  --volume "$PWD/global-bundle.pem:/etc/auto-runtime/rds-global-bundle.pem:ro" onauto/runtime:latest
```

Each time a pool of the ledger or of the workflows opens a connection, the server signs a new token for the host, the port and the user of `DATABASE_URL`, valid for 15 minutes, with the credentials of the AWS default credential chain, as the Bedrock provider and the object store take theirs, through the outbound proxy when `NODE_USE_ENV_PROXY=1` is set; the token is the password the connection signs in with. It signs for the region the host name names, such as `eu-west-1` above, or, for a host name that names none, for `AWS_REGION`. The connection always uses TLS and checks the database's certificate and host name, as `sslmode=verify-full` does, with or without `sslmode` in the URL. The server logs at start the user and the region it signs for, never a token.

With `DATABASE_CREDENTIALS=aws-iam`, the server builds each connection from the user, the host, the port and the database of the URL, and stops at start, naming the setting and never a value, when the URL holds a password, names no user, gives an `sslmode` other than `verify-full`, gives a TLS option such as `sslrootcert`, whose certificate authority goes in `NODE_EXTRA_CA_CERTS` instead, or gives any other option, or when neither the host name nor `AWS_REGION` names a region. A token it cannot sign, for credentials the chain cannot find, fails the connection with the chain's error, so at start the server stops, naming that error, as it does for a database it cannot reach. A token the database refuses, for a user without `rds_iam` or an identity without `rds-db:connect`, fails the connection with the database's error.

## Content on object storage

Set `CONTENT_STORE_URL` to an `s3://bucket/prefix` URL, and the server keeps the content a playbook keeps, a tool's arguments and answers among it, and a prediction function's uploaded datasets, the rows and the brief of each build and the model file of each version, in that bucket, one object for each content under its playbook and its SHA-256, instead of in the ledger's database; a build's candidates are staged under `<prefix>/staging/` and deleted when the build ends; every other record stays in the ledger. The server speaks the S3 API, so the bucket may be on any S3-compatible server:

| Variable                                    | Purpose                                                                                                                                                                                                                                                                                         |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CONTENT_STORE_URL`                         | The bucket and the prefix, `s3://bucket/prefix`; the bucket is 3 to 63 lowercase letters, digits, dots and hyphens, and the prefix may be empty                                                                                                                                                 |
| `AWS_ENDPOINT_URL_S3` or `AWS_ENDPOINT_URL` | The endpoint of an S3-compatible server, such as `http://storage.internal:9000`, addressed by path; the first is read before the second, which is the Bedrock provider's endpoint too unless `AWS_ENDPOINT_URL_BEDROCK_RUNTIME` is set, so with Bedrock configured name the server in the first |
| `AWS_REGION`                                | The region the requests are signed for, which the SDK otherwise reads from a profile; without either the server stops at start; S3-compatible servers commonly take `us-east-1`                                                                                                                 |

The credentials come from the AWS default credential chain, as the Bedrock provider's do: `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` in `auto-runtime.env`, a profile, a web identity, or the role of the container or the instance. The bucket must exist; the server creates none, and checks it at start: a bucket it cannot reach, for a refusal, a missing bucket, a missing region or an endpoint that does not answer, stops it at start, naming `CONTENT_STORE_URL`, the bucket, the endpoint's host and the store's answer, and never a credential. Its credentials need to read, write, copy and delete objects under the prefix, list the bucket, and list and abort multipart uploads. Versioning is not required; on a bucket with versioning on, every delete keeps a noncurrent version, so give such a bucket a lifecycle rule that expires them. A lifecycle rule is otherwise optional: every hour the server deletes what puts that never finished left under `<prefix>/uploads/`. The server logs at start that content is kept on object storage, naming the bucket, the prefix and the endpoint's host. The [object storage README](../../../packages/object-storage/README.md) has the layout of the keys, how a put and a read go, and what was measured.
