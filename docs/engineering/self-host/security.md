# Authentication and security

Every path needs a caller, except `/health`, [the page the server shows a browser at `/`](#the-page-at-the-root) and, where an identity provider is configured, [the protected resource metadata](#discovery-and-challenges). A caller is one of three:

- a **key**, an API key of `API_KEYS`, for a machine, a pipeline, a trainer's agent, or a person whose company configures no identity provider;
- the **local developer**, every request in [local mode](#local-mode), on your own machine;
- a **signed-in person**, whom an identity provider of `IDENTITY_PROVIDERS` vouches for with an access token, which an agent gateway brokers or an agent obtains through the authorization flow.

## API keys

An API key is sent as `Authorization: Bearer <key>`. Each key belongs to one org and carries its permissions and the playbooks it may access. The key command creates one:

```bash
docker run --rm --log-driver none onauto/runtime:latest node packages/identity/src/key-command.ts --org <org>
```

Options are `--id`, `--permissions` (comma-separated, from `org:read`, `org:write`, `playbook:read`, `playbook:write`; all four by default) and `--playbooks` (comma-separated playbook ids, or `*` for every playbook, the default). The command prints the key once and the entry to add to `API_KEYS`, or to `api_keys` in the [configuration file](../self-host/configuration.md), where the entry as printed is one item of the list; only the key's SHA-256 is stored, so keep the key itself somewhere safe. Write the variable unquoted, for example `API_KEYS=[{"id":"…",…}]` in an env file. `--log-driver none` keeps the key out of Docker's log driver, which could otherwise store or ship it; the command still prints it to your terminal. The id `local` is the local developer's on the facts, and the org `local` is local mode's, so a key may have neither.

Following [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750), a request without an `Authorization` header gets `401` with `WWW-Authenticate: Bearer`, a key that is not valid gets `401` with `error="invalid_token"`, an `Authorization` header that is not exactly one `Bearer <key or token>` gets `400` with `error="invalid_request"`, and a key that lacks the permission, playbook or org a call needs gets `403` with `error="insufficient_scope"`. Where a provider is configured, the challenges say more, as [Discovery and challenges](#discovery-and-challenges) sets out.

Without `API_KEYS` and without a provider, and without local mode, the server rejects every path except those two with `401`, on any address, and warns at start-up that no request can authenticate. `API_KEYS=[]` is a list that is set and holds no key: it turns local mode off as any list does, so with no provider the server admits nobody, even with `LOCAL_MODE=true`, and its start-up line says that `API_KEYS` lists no keys and that `LOCAL_MODE` is ignored because `API_KEYS` is set.

## Signed-in persons

A company that signs its people in through an identity provider lists the provider in `identity_providers`, one entry for each org it admits people to, and sets `PUBLIC_URL`, the `https` URL the runtime is reached at; the [configuration guide](configuration.md#identity-providers) describes the entries. At start the server reads each issuer's metadata, from `/.well-known/oauth-authorization-server` and then `/.well-known/openid-configuration` at the issuer's origin, or, for an issuer with a path, from each of those with the path inserted after it and then from the OpenID Connect document under the path, the orders of the MCP authorization specification; the metadata must name the issuer as written and an `https` `jwks_uri`. It then reads the key set there, which must hold a key. An issuer whose metadata or key set cannot be used stops the start, naming the provider and each address it read. Each read waits at most 10 seconds for its answer, takes at most 64 KiB and follows no redirect: an address that answers one is refused as one that answers nothing.

A bearer token that is not a key is a JWT access token, which the runtime takes when it is:

- at most 8 KiB, its header naming one of `RS256`, `PS256`, `ES256` and `EdDSA` on `Ed25519`, and a `typ` of `at+jwt`, `application/at+jwt`, `JWT` or `application/jwt`, in any letter case, or none; `none` and every other algorithm are refused;
- signed by a key of the issuer's key set that verifies its algorithm, chosen by its `kid`; a `kid` the key set does not hold has the key set read again, once a minute has passed since the last read, and a key set that cannot be read then leaves the keys held before; an RSA key under 2048 bits, a key for encryption and a key named for another algorithm sign nothing;
- `iss` the issuer of an entry, `aud` holding `PUBLIC_URL`, alone or with a final `/`, or, on an MCP endpoint, `PUBLIC_URL` followed by that endpoint's path, `exp` not past and `nbf` and `iat` not ahead, each with 60 seconds of leeway;
- `sub` a non-empty string of at most 256 bytes, the bound of every reference on the facts, since it is the name the person acts under; the claim an entry names under `subject` is bounded the same way.

A token that fails any of these, an opaque token among them, is refused `401` `invalid_token`, and the problem's `detail` says why, such as `The access token was refused: ERR_JWT_EXPIRED on its exp claim` or `The access token was refused: its sub is not a non-empty string of at most 256 bytes`, naming the rule or the claim it failed and never a value the token holds. A token that passes is the signed-in person, whom each entry of its issuer admits to that entry's org when the token holds the entry's `membership`, names a subject under the entry's `subject` claim and its `grants` give at least one permission; an entry whose `subject` claim the token does not hold does not admit it. The person's permissions in the org are those of every value of the grants' claim, and their playbooks likewise, `*` winning. A person admitted to no org is authenticated and refused everywhere with `403`, `insufficient_scope`; a person admitted to some orgs is refused the others with `403`, over HTTP and on the MCP endpoints, and `/mcp` serves them the org of the first entry that admits them, in the order of the setting.

A signed-in person acts under the name `person:<provider>/<subject>`, the provider's `name` and the subject the entry names, `sub` by default, as it is. That name is the `by` of every fact the person records, among them the activation of a version of a prediction function they ask for, and the `created_by`, `started_by`, `answered_by` and `approved_by` of what they create, start, answer and approve, so a reader tells a person from a key and one provider's subject from another's. A run event sent without a source has the source `/callers/` and that name, percent-encoded as one segment of a path.

### The audience of a token

The runtime takes only a token whose `aud` names it: `PUBLIC_URL`, or `PUBLIC_URL` followed by the path of the endpoint the request reached, such as `https://runtime.example.com/orgs/acme/mcp`, the resource a standards client asks a token for when the metadata of that endpoint names it. A token issued for another service of the company, an identity token sent by mistake, and a token another resource server received and passes on are each refused, whoever signed them. This is the check a public server needs: a request reaches it through proxies and under any `Host`, and the audience binds the token to the runtime, not to the name the request arrived under. Local mode trusts every request without a credential, so the `Host` check is what stops a page in a browser from reaching it through a name that resolves to the loopback address; a public server, whose callers present credentials, does not check the `Host`.

### Providers that issue a JWT access token for an audience you name

The runtime verifies a token itself, so the provider must issue the access token as a JWT whose audience is the runtime; a provider's access token for its own services, or for no audience, is opaque or names another audience, and is refused. The common providers issue one once the runtime is registered with them as an API, or resource server, whose identifier is `PUBLIC_URL`:

| Source                                                                                                                                                                                                                                                                                | What to turn on                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Okta: Create an authorization server](https://developer.okta.com/docs/guides/customize-authz-server/main/)                                                                                                                                                                           | A custom authorization server whose Audience is `PUBLIC_URL`; its issuer is `https://<domain>/oauth2/<server id>`                                                                                                                                                                                                                  |
| [Auth0: Register APIs](https://auth0.com/docs/get-started/auth0-overview/set-up-apis), [Auth0: Access tokens](https://auth0.com/docs/secure/tokens/access-tokens)                                                                                                                     | An API whose Identifier is `PUBLIC_URL`, signed with RS256 or PS256 and not HS256; a token asked for that API is a JWT                                                                                                                                                                                                             |
| [Microsoft identity platform: Access token claims reference](https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference), [App manifest](https://learn.microsoft.com/en-us/entra/identity-platform/reference-microsoft-graph-app-manifest#api-attribute) | An app registration that exposes an API whose Application ID URI is `PUBLIC_URL`, with `requestedAccessTokenVersion` 1 or null: a version 1.0 token's `aud` can be the resource URI the request named, while a version 2.0 token's is always the API's client ID, which the audience rule refuses; the issuer is the token's `iss` |
| [Keycloak: Audience support](https://www.keycloak.org/docs/latest/server_admin/index.html#audience-support)                                                                                                                                                                           | An audience mapper on the client's scope whose Included Custom Audience is `PUBLIC_URL`, added to the access token; the issuer is `https://<host>/realms/<realm>`                                                                                                                                                                  |

Give the grants a claim the provider puts in the access token, such as `groups`, `roles` or `scope`; a provider whose groups are many may leave them out of the token, and the grants then find none. With `grants.claim: scope`, the provider's own policy decides which values a client may request, so grant permissions only to values the provider lets no client request freely.

### Discovery and challenges

With a provider configured, `GET /.well-known/oauth-protected-resource` answers the protected resource metadata of [RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728) without a key, and so does the same path followed by each MCP endpoint's path, `/mcp`, `/orgs/{org}/mcp` and `/orgs/{org}/playbooks/{playbook}/mcp`: `resource` is `PUBLIC_URL` followed by the path the metadata describes, `authorization_servers` the configured issuers, `bearer_methods_supported` `["header"]`, `scopes_supported` the four permissions and `resource_documentation` the [MCP reference](../../reference/mcp.md). A `401` then carries `WWW-Authenticate: Bearer resource_metadata="<PUBLIC_URL>/.well-known/oauth-protected-resource", scope="org:read org:write playbook:read playbook:write"`, with `error="invalid_token"` first when a key or token was presented and refused. A `403` carries `error="insufficient_scope"`, the `scope` the operation needs and the root metadata, and the MCP endpoints' own refusals, of an org or a playbook the caller may not reach, carry the four permissions and the metadata of that endpoint. Without a provider the server is no OAuth resource server: the metadata is not served, its path needs a key as every path does, and the challenges are those of [API keys](#api-keys).

A client that connects to an MCP endpoint without a token is challenged, reads the metadata, asks the authorization server it names for a token for that resource, and connects with it, as the authorization flow of the MCP specification runs; an agent gateway that brokers a person does the same as the runtime's client. Signing in through a browser, registering clients and refreshing tokens are the authorization server's; the runtime never issues a token, and it passes none it receives to a tool server, which it calls under that server's own credential.

### What a revoked person keeps

The runtime verifies a token on every request and keeps none, so a person the provider stops issuing tokens to is refused once their last token expires, and a provider that revokes a token earlier is not asked: keep access tokens short-lived. A workflow run keeps acting as the identity that started it, its permissions and playbooks among it, for as long as it runs, since a run is one unit of work that identity asked for; revoking the person stops their next request, not the runs they already started, which a caller who may write to the playbook can cancel.

## Local mode

Local mode is for development on your own machine. It is on only when `LOCAL_MODE=true`, the server listens only on a loopback address (`localhost`, `127.0.0.1` or `::1`), `API_KEYS` is not set and no identity provider is configured. Then every request acts as a local developer with every permission in whichever org it names, and no key is needed; the server logs a warning saying so when it starts. To stop a web page from driving it, local mode rejects a request whose `Host` header is not a localhost name, and, as always, a request whose `Origin` is neither the studio's nor in `ALLOWED_ORIGINS`.

> **Warning:** never enable local mode on a machine that can be reached through a proxy. A reverse proxy on the same machine, such as nginx with its default settings, forwards remote requests to the loopback address with a localhost `Host` header, so the server would trust every remote client as the local developer.

`LOCAL_MODE=true` with an address that is not loopback stops the server at start-up with an `InvalidLocalModeError`. With `API_KEYS` set, even to `[]`, or with an identity provider configured, credentials are enforced and the server warns that `LOCAL_MODE` is ignored, naming why. `pnpm dev` sets `LOCAL_MODE=true` and listens on `127.0.0.1`, so it runs in local mode; `pnpm key -- --org <org>` creates a key from a checkout.

## Calling from a browser

A page may call the API only from the studio, `https://studio.on.auto`, or from an origin listed in `ALLOWED_ORIGINS`; a request with any other `Origin` header gets `403`. The studio is always allowed, so [the page a server shows at `/`](#the-page-at-the-root) can open the studio on that server. Being allowed lets a page reach the API, not act on it: where credentials are enforced, the studio still has to send one. In local mode no key is needed, so a script served from `https://studio.on.auto` can act as the local developer. For an allowed origin the server answers CORS: a preflight (`OPTIONS` with `Access-Control-Request-Method`) gets `204` before any key is checked, allowing `GET`, `HEAD`, `POST` and `PUT` with the `authorization` and `content-type` headers, and every response carries `Access-Control-Allow-Origin` with that origin, `Vary: Origin`, and `x-request-id` among the headers the page may read. There is no wildcard and no credentials mode: the page sends its key or token in the `Authorization` header.

## The page at the root

A browser that opens the server's address gets a page saying the server is running, with a button that opens the studio on it. The server answers with the page only to a `GET /` that accepts `text/html`, and it needs no key, in local mode or not. Any other request to `/` is treated like a request to any other path.

The page tells a visitor only that an Auto Runtime server answers at that address; it shows nothing the server holds. It runs no script and asks no other server for anything: its styles, its icon and its typefaces are inside it, and its `Content-Security-Policy` allows nothing else. It may not be shown in a frame, and it is never cached.

The button goes to `https://studio.on.auto/?server=<this server's origin>`, and the studio then calls this server from the browser, which is why its origin is always allowed. The studio takes a server from such a link only when the address is on the visitor's own machine: `localhost`, `127.0.0.1` or `::1`.
