# Authentication and security

Every path needs a caller, except those that need no key: `/health`, the OpenAPI document at `/v1/openapi.json`, the guides at `/v1/guides/{guide}` and the API catalog at `/.well-known/api-catalog`, which name no secret and describe the API, [the page the server shows a browser at `/`](#the-page-at-the-root) and, where `PUBLIC_URL` is set, [the protected resource metadata](#discovery-and-challenges). A caller is one of three:

- a **key**, an API key of `API_KEYS`, for a machine, a pipeline, a trainer's agent, or a grant narrower than a signed-in person's;
- the **local developer**, every request in [local mode](#local-mode), on your own machine;
- a **signed-in person**, who signs in through the Auto identity service and calls with its access token, which an agent gateway brokers or an agent obtains through the authorization flow.

## API keys

An API key is sent as `Authorization: Bearer <key>`. Each key belongs to one org and carries its permissions and the playbooks it may access. The key command creates one:

```bash
docker run --rm --log-driver none onauto/runtime:latest node packages/identity/src/key-command.ts --org <org>
```

Options are `--id`, `--permissions` (comma-separated, from `org:read`, `org:write`, `playbook:read`, `playbook:write`; all four by default) and `--playbooks` (comma-separated playbook ids, or `*` for every playbook, the default). The command prints the key once and the entry to add to `API_KEYS`, or to `api_keys` in the [configuration file](configuration.md), where the entry as printed is one item of the list; only the key's SHA-256 is stored, so keep the key itself somewhere safe. Write the variable unquoted, for example `API_KEYS=[{"id":"…",…}]` in an env file. `--log-driver none` keeps the key out of Docker's log driver, which could otherwise store or ship it; the command still prints it to your terminal. The id `local` is the local developer's on the facts, and the org `local` is local mode's, so a key may have neither.

Following [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750), a request without an `Authorization` header gets `401` with `WWW-Authenticate: Bearer`, a key that is not valid gets `401` with `error="invalid_token"`, an `Authorization` header that is not exactly one `Bearer <key or token>` gets `400` with `error="invalid_request"`, and a key that lacks the permission, playbook or org a call needs gets `403` with `error="insufficient_scope"`. Where `PUBLIC_URL` is set, the challenges say more, as [Discovery and challenges](#discovery-and-challenges) sets out.

Without `API_KEYS`, without `PUBLIC_URL` and without local mode, the server rejects every path with `401` but `/health`, the OpenAPI document, the guides, the API catalog and the page at `/`, on any address, and warns at start-up that no request can authenticate. `API_KEYS=[]` is a list that is set and holds no key: it turns local mode off as any list does, so without `PUBLIC_URL` the server admits nobody, even with `LOCAL_MODE=true`, and its start-up line says that `API_KEYS` lists no keys and that `LOCAL_MODE` is ignored because `API_KEYS` is set.

## Signed-in persons

People sign in through the Auto identity service at `https://clerk.on.auto`, the one Studio signs them into. A company whose people sign in through its own identity provider connects that provider to the identity service in Studio, not in the runtime, so the runtime trusts one issuer whichever provider a person used. A person belongs to an organization in the identity service, and the org id of a runtime is that organization's id: a person of the organization whose id is `acme` there acts in the org `acme` here.

Setting `PUBLIC_URL`, the URL the runtime is reached at, turns sign-in on; without it the runtime takes only keys and local mode, and serves no metadata. `PUBLIC_URL` is an `https` URL with no path, query or fragment, such as `https://runtime.example.com`, or, on a server whose `HOST` is a loopback address, an `http` URL whose host is `localhost`, `127.0.0.1` or `[::1]`, such as `http://localhost:5555`, so a runtime on a laptop signs people in like any other. An `http` URL with another host, or on a server that listens beyond the loopback address, stops the start with an `InvalidSettingsError`, since a token sent over plain HTTP between machines can be read on the way. `IDENTITY_ISSUER` is the identity service, `https://clerk.on.auto` when it is not set; a development runtime sets it to the development instance of the service. It is an `https` URL with no path, query or fragment, and any other value stops the start.

At start the server reads the identity service's metadata, from `/.well-known/oauth-authorization-server` and then `/.well-known/openid-configuration`, the order of the MCP authorization specification; the metadata must name the issuer as `IDENTITY_ISSUER` writes it and an `https` `jwks_uri`. It then reads the key set there, which must hold a key. A service whose metadata or key set cannot be used stops the start with an `UnusableIdentityServiceError`, naming the service and each address it read. Each read waits at most 10 seconds for its answer, takes at most 64 KiB and follows no redirect: an address that answers one is refused as one that answers nothing.

A bearer token that is not a key is a JWT access token, which the runtime takes when it is:

- at most 8 KiB, its header naming one of `RS256`, `PS256`, `ES256` and `EdDSA` on `Ed25519`, and a `typ` of `at+jwt`, `application/at+jwt`, `JWT` or `application/jwt`, in any letter case, or none; `none` and every other algorithm are refused;
- signed by a key of the service's key set that verifies its algorithm, chosen by its `kid`, or, for a token without one, the only key of its type in the set, a token without a `kid` that several keys fit being refused; the key set is read again for a `kid` it does not hold once 60 seconds have passed since the last read that succeeded, and at the first token after it is ten minutes old, so a key the service removes is trusted for ten minutes at most; a key set that cannot be read again for an unknown `kid` leaves the keys held before, and one that cannot be read once ten minutes have passed refuses every token, so an identity service unreachable for longer than that keeps sign-ins out until it answers; an RSA key under 2048 bits, a key for encryption and a key named for another algorithm sign nothing;
- `iss` the issuer, `aud` as [The audience of a token](#the-audience-of-a-token) sets out, `exp` not past and `nbf` and `iat` not ahead, each with 60 seconds of leeway;
- `sub` a non-empty string of at most 256 bytes without control characters, unpaired surrogates or noncharacters, the bounds of a name on the facts, since it is the name the person acts under;
- `org_id`, the org claim, an org id of 1 to 64 letters, digits, `_` and `-` other than `local`: the id of the organization the person signed in to.

A token that fails any of these, an opaque token among them, is refused `401` `invalid_token`, and the problem's `detail` says why, such as `The access token was refused: ERR_JWT_EXPIRED on its exp claim` or `The access token was refused: ERR_JWT_CLAIM_VALIDATION_FAILED on its org_id claim`, naming the rule or the claim it failed and never a value the token holds. The org comes from `org_id` alone: a token without it is refused, and no org is taken from the subject or from anything else the token holds.

A token that passes is the signed-in person, admitted to the org its `org_id` names with every permission there, `org:read`, `org:write`, `playbook:read` and `playbook:write`, over every playbook. Every other org refuses them with `403`, `insufficient_scope`, over HTTP and on the MCP endpoints, and `/mcp` serves them the org their token names. Keys remain for what a sign-in does not give: a machine, a pipeline or a trainer's agent, which signs in nowhere, and a grant narrower than every permission over every playbook, such as reading one playbook.

A signed-in person acts under the name `person:<subject>`, the token's `sub` as it is. That name is the `by` of every fact the person records, among them the activation of a version of a prediction function they ask for, and the `created_by`, `started_by`, `answered_by` and `approved_by` of what they create, start, answer and approve, so a reader tells a person from a key. A run event sent without a source has the source `/callers/` and that name, percent-encoded as one segment of a path.

### The audience of a token

The runtime takes only a token whose `aud` names it: `PUBLIC_URL`, alone or with a final `/`, or, on an MCP endpoint, `PUBLIC_URL` followed by the path of the endpoint the request reached, such as `https://runtime.example.com/orgs/acme/mcp`, the resource a standards client asks a token for when the metadata of that endpoint names it. A token the identity service issued for another service, an identity token sent by mistake, and a token another resource server received and passes on are each refused, though the same service signed them. This is the check a public server needs: a request reaches it through proxies and under any `Host`, and the audience binds the token to the runtime, not to the name the request arrived under. Local mode trusts every request without a credential, so the `Host` check is what stops a page in a browser from reaching it through a name that resolves to the loopback address; a public server, whose callers present credentials, does not check the `Host`.

### Discovery and challenges

With `PUBLIC_URL` set, `GET /.well-known/oauth-protected-resource` answers the protected resource metadata of [RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728) without a key, and so does the same path followed by each MCP endpoint's path, `/mcp`, `/orgs/{org}/mcp` and `/orgs/{org}/playbooks/{playbook}/mcp`: `resource` is `PUBLIC_URL` followed by the path the metadata describes, `authorization_servers` the one issuer, `IDENTITY_ISSUER`, `bearer_methods_supported` `["header"]`, `scopes_supported` the four permissions and `resource_documentation` the [MCP reference](../reference/mcp.md). A `401` then carries `WWW-Authenticate: Bearer resource_metadata="<PUBLIC_URL>/.well-known/oauth-protected-resource", scope="org:read org:write playbook:read playbook:write"`, with `error="invalid_token"` first when a key or token was presented and refused. A `403` carries `error="insufficient_scope"`, the `scope` the operation needs and the root metadata, and the MCP endpoints' own refusals, of an org or a playbook the caller may not reach, carry the four permissions and the metadata of that endpoint. Without `PUBLIC_URL` the server is no OAuth resource server: the metadata is not served, its path needs a key as every path does, and the challenges are those of [API keys](#api-keys).

A client that connects to an MCP endpoint without a token is challenged, reads the metadata, asks the authorization server it names for a token for that resource, and connects with it, as the authorization flow of the MCP specification runs; an agent gateway that brokers a person does the same as the runtime's client. Signing in through a browser, registering clients and refreshing tokens are the authorization server's; the runtime never issues a token, and it passes none it receives to a tool server, which it calls under that server's own credential.

### What a revoked person keeps

The runtime verifies a token on every request and keeps none, so a person the identity service stops issuing tokens to is refused once their last token expires, and a token the service revokes earlier is taken until it expires, since the runtime does not ask. A workflow run keeps acting as the identity that started it, its permissions and playbooks among it, for as long as it runs, since a run is one unit of work that identity asked for; revoking the person stops their next request, not the runs they already started, which a caller who may write to the playbook can cancel.

## Local mode

Local mode is for development on your own machine. It is on only when `LOCAL_MODE=true`, the server listens only on a loopback address (`localhost`, `127.0.0.1` or `::1`), `API_KEYS` is not set and `PUBLIC_URL` is not set. Then every request acts as a local developer with every permission in whichever org it names, and no key is needed; the server logs a warning saying so when it starts. To stop a web page from driving it, local mode rejects a request whose `Host` header is not a localhost name, and, as always, a request whose `Origin` is neither the studio's nor in `ALLOWED_ORIGINS`; the paths that need no key, `/health`, the OpenAPI document, the guides and the API catalog, skip both checks.

> **Warning:** never enable local mode on a machine that can be reached through a proxy. A reverse proxy on the same machine, such as nginx with its default settings, forwards remote requests to the loopback address with a localhost `Host` header, so the server would trust every remote client as the local developer.

`LOCAL_MODE=true` with an address that is not loopback stops the server at start-up with an `InvalidLocalModeError`. With `API_KEYS` set, even to `[]`, or with `PUBLIC_URL` set, credentials are enforced and the server warns that `LOCAL_MODE` is ignored, naming why. `npx @on.auto/runtime` sets `LOCAL_MODE=true` and listens on `127.0.0.1`, so it runs in local mode; `npx @on.auto/runtime key --org <org>` creates a key without Docker.

## Calling from a browser

A page may call the API only from the studio, `https://studio.on.auto`, or from an origin listed in `ALLOWED_ORIGINS`; a request with any other `Origin` header gets `403`, but on the paths that need no key, `/health`, the OpenAPI document, the guides, the API catalog and, where `PUBLIC_URL` is set, the protected resource metadata, which skip the `Host` and `Origin` checks. The studio is always allowed, so [the page a server shows at `/`](#the-page-at-the-root) can open the studio on that server. Being allowed lets a page reach the API, not act on it: where credentials are enforced, the studio still has to send one. In local mode no key is needed, so a script served from `https://studio.on.auto` can act as the local developer. For an allowed origin the server answers CORS: a preflight (`OPTIONS` with `Access-Control-Request-Method`) gets `204` before any key is checked, allowing `GET`, `HEAD`, `POST` and `PUT` with the `authorization` and `content-type` headers, and every response carries `Access-Control-Allow-Origin` with that origin, `Vary: Origin`, and `x-request-id` among the headers the page may read. There is no wildcard and no credentials mode: the page sends its key or token in the `Authorization` header.

## The page at the root

A browser that opens the server's address gets a page saying the server is running, with a button that opens the studio on it. The server answers with the page only to a `GET /` that accepts `text/html`, and it needs no key, in local mode or not. Any other request to `/` is treated like a request to any other path.

The page tells a visitor only that an Auto Runtime server answers at that address; it shows nothing the server holds. It runs no script and asks no other server for anything: its styles, its icon and its typefaces are inside it, and its `Content-Security-Policy` allows nothing else. It may not be shown in a frame, and it is never cached.

The button goes to `https://studio.on.auto/?server=<this server's origin>`, and the studio then calls this server from the browser, which is why its origin is always allowed. The studio takes a server from such a link only when the address is on the visitor's own machine: `localhost`, `127.0.0.1` or `::1`.
