**Status:** accepted (2026-10-09); designed on 2026-10-08 against `origin/main` at c4377676 with [decision 0010's amendment, a function owns its delivery](0010-interaction-functions.md#amendment-2026-10-08-a-function-owns-its-delivery-and-channels-go), and the per-server tool lists of decision 0003's amendment it builds on, read as merged, and [decision 0020](0020-replies-through-a-channel.md), replies, read as that amendment's section 8 amends it; written in the words of [decision 0007](0007-one-vocabulary.md), each file cited under the name that rename gave it, at the line read at c4377676; built on 2026-10-09 on `origin/main` at b753ded3, with the amendments from the build after the appendix

## Context

A workflow often needs data from a system, or an effect on one, with nothing to reason about between the asking and the answer. The only way today is a reasoning function whose prompt says "call this tool and answer with the rows it gives": the computation reference teaches exactly that, "A workflow reaches an MCP server only through a reasoning function's tools, so the first function reads the rows and passes them on unchanged" (`docs/reference/computation-format.md:181`), with a function whose prompt reads "Call ads/campaign-costs for the month {{ input.month }} and answer with the rows it gives, exactly as it gives them. Do not add, round or calculate anything." (`:213`). It costs a model call for every read, puts a tool's answer through a model that may drop, reorder or invent rows, exposes the run to whatever text the tool returns, and still hands the workflow a shape only the prompt promised. The owner decided: this is an interaction function in the shape "ask a system, answer now". Its document names the tool of a tool server it calls, the arguments as templates over its input, where in the tool's answer the data is, and what the data must look like; a run makes one recorded call through the brain's one call path, reads, checks, bounds and records the answer, and ends at once with the data as its output or with a rejection a workflow can catch. No new capability, no bare tool step in the workflow language, no model; MCP stays the transport and its raw result never reaches a workflow. An interaction function then has three shapes, which share one document format and one run path wherever they do the same thing: **ask a system now** (this record), **ask a party and take the answer later** through a tool, `deliver` and `replies` (0010's amendment, 0020), and the **inbox**, which names neither.

### How products call a system without a model

Read on 2026-10-08 from each product's public reference; this record names no vendor or platform, so each product is named for what it is, and its pages are cited by what they say. The open workflow standard whose DSL 1.0 the workflow format follows names the task `call`: it "Enables the execution of a specified function within a workflow, allowing seamless integration with custom business logic or external services", with HTTP, OpenAPI, gRPC, AsyncAPI, A2A and MCP calls, the last written `call: mcp` with `with.method: tools/call` and `parameters` holding the tool's `name` and `arguments`, a reusable function declared once under `use.functions` and called by its name, an HTTP call's `output` of `raw`, `content` ("outputs the content of HTTP response, possibly deserialized", the default) or `response`, a task's output reshaped by `output.as` in jq, and errors caught by `catch.errors.with`, "a static filter, used to catch only the errors whose properties match the specified values", over standard types such as `communication` and `runtime`. A cloud provider's workflow service has an HTTP task, "a type of Task workflow state state that you can use to call HTTPS APIs in your workflows", its credentials in a connection that "helps you avoid hard-coding secrets"; its "HTTP task requests will timeout after 60 seconds", it sends `Range: bytes=0-262144`, retries and catches by names declared on the state for a status such as 429 or 503, and fails as a runtime error when "The response can't be read as a valid string"; a state's parameters "can either be static values that you include in your state machine definition, or selected from either the input or the Context object with a path", and a result selector "lets you create a collection of key value pairs, where the values are static or selected from the state's result" before a result path places it. A durable-execution engine's activity "is a normal function or method (an Activity Definition) that executes a single, well-defined action", recommended idempotent "so retries can be processed without duplicate side effects", and retried by default, an activity that fails being retried automatically with "the maximum attempt of retries ... set to zero which is evaluated as unlimited", and bounded by a start-to-close timeout, "the maximum time allowed for a single Activity Task Execution", whose expiry writes "an ActivityTaskTimedOut Event ... to the Workflow Execution's mutable state". A scripting platform's scripts "have input parameters defined by a JSON Schema", validated "During script execution", and a flow step's inputs "can be configured in three ways: Templatable string, Dynamic, or Static". A GraphQL gateway's connector directive "defines the API data source of a GraphQL schema field", its `selection` "Used to map an API's JSON response to GraphQL fields", in which "A leading `$.` is required when unwrapping a single property". An automation tool's HTTP request node lets a workflow "make HTTP requests to query data from any app or service with a REST API"; "By default, the node returns success only when the response returns with a 2xx code", it has Pagination "for handling query results that are too big for the API to return in a single call", and Retry On Fail is a setting under which "the node reruns until it succeeds". An event-driven function platform's `step.fetch()` is "a shorthand for making HTTP requests from within" one of its functions and offloads the request to the platform, and `step.run()` runs code "as a retriable step in your function", "All data returned from `step.run` is serialized as JSON". The Model Context Protocol returns structured content "as a JSON object in the `structuredContent` field of a result", says "a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block", and reports tool execution errors, "API failures", "Invalid input data" and "Business logic errors", "in tool results with `isError: true`", apart from protocol errors such as an unknown tool or invalid arguments (https://modelcontextprotocol.io/specification/2025-06-18/server/tools).

What the comparison settles, point by point:

1. **The word is `call`.** The open workflow standard names the task `call` and its MCP form calls `tools/call`, the protocol's own method; the HTTP task exists "to call HTTPS APIs". The other words name something else: `fetch` an HTTP read, where a call may write; `connect` a standing binding of a field to its source, not one act; `invoke` is the HTTP task's resource name and would be a second word for the act. This repository already says it: a workflow step is `call: run_definition` with `with` (`workflow-format.md:209`), the facts are `tool_call_started` and `tool_call_answered`, the bound is `toolBounds.callMs` (`packages/mcp/src/bounds/call-bounds.ts:11`). So the block is `call`, a verb beside `with`, as `deliver` is for the shape that asks a party (amendment §1, "The word."), and the facts, the bound and the words keep the one word they have.
2. **Selecting is a place, and reshaping lives where it already lives.** Every product that selects lets the selection reshape: key-value pairs over the result, a mapping language, jq over the output. Here reshaping has two homes, a workflow's `output.as` in jq and a computation function with its own bounds (0005), and the document format names places in a tool's answer with JSON Pointers, `deliver.sent` and `replies.read`, because a tool's answer is data and never instructions (0003 §3; 0020 §2). So `read` is one JSON Pointer (RFC 6901), checked for its shape at save, and a call answers with the value it points at, as it is.
3. **Arguments keep their types.** A static value goes as written and a selected one keeps its type: the HTTP task's static or path-selected values, the three kinds of step input, "Templatable string, Dynamic, or Static". So `with` takes values as written, text templates that render text, and a template that is one `{{ }}` and nothing else, which sends the value it reads as it is.
4. **A failure is the workflow's to retry, by what it is.** The HTTP task declares its retries and catches on the state, the open standard on the `try`, the node opts into Retry On Fail; only the activity is retried by default, and it is told to be idempotent for that reason. Whether a tool may be called again is the server's own word, its `readOnlyHint`, trusted as far as the operator's `allowed` admitted the tool (0018 §3). So a run makes one call and never retries it; its ending is one of the outcomes that exist; a failure after sending, a tool's `isError` among them, which the protocol uses for "API failures" that may pass, is an `unavailable` a workflow may retry when the tool only reads, and a `conflict` that no retry on 503 repeats when it may write.
5. **A call is bounded in time and in what it keeps.** 60 seconds and 256 KiB for the HTTP task; here 10 s to open, 30 s to answer and 64 KiB kept as the output, the bounds a run's call and an interaction function's answer already have (§4).

## Decision

### 1. The document: `call`, `read` and `output.schema`

A function that asks a system names in **`call`** a tool of a tool server the brain may use, the arguments the call takes and, in `read`, where in the tool's answer its data is; `output.schema` says what that data must look like. It sends no message and makes no request, so it writes no body, no `to`, `expires`, `deliver`, `replies`, `from` or `reply`.

```markdown
---
description: Read the replies of a thread in the team chat, oldest first
call:
  server: chat
  tool: thread_replies
  with:
    channel: '{{ input.channel }}'
    ts: '{{ input.thread }}'
    limit: 100
    inclusive: false
  read: /messages
input:
  schema:
    type: object
    required: [channel, thread]
    properties:
      channel: { type: string }
      thread: { type: string }
output:
  schema:
    type: array
    maxItems: 100
    items:
      type: object
      required: [user, text, ts]
      properties:
        user: { type: string }
        text: { type: string }
        ts: { type: string }
---
```

The names `channel`, `ts`, `limit` and `inclusive` are the chat tool's own, as its `input_schema` gives them, and the brain knows none of them; `limit` and `inclusive` go as the number and the boolean they are written as. `list_tool_servers` lists the tool with `readOnlyHint: true`. Tested with `test_tool_call` and `{ "channel": "C0123", "ts": "1728379900.000050", "limit": 100 }`, the tool answered the `text` "2 replies in the thread." and the `answer` `{ "ok": true, "messages": [ { "user": "member-17", "text": "Shipped the fix to staging.", "ts": "1728380000.000100" }, { "user": "member-42", "text": "Thanks, closing the ticket.", "ts": "1728380100.000200" } ], "has_more": false }`, its structured content, so `read` is `/messages` and the output schema is a list of those objects; a message's other fields pass through, since the schema allows them. A workflow calls it as any function:

```yaml
- replies:
    try:
      - read:
          call: run_definition
          with:
            type: interaction
            name: thread-replies
            input: { channel: '${ .channel }', thread: '${ .thread }' }
    catch:
      errors:
        with: { status: 503 }
      retry:
        delay: { seconds: 5 }
        limit:
          attempt: { count: 2 }
```

Its server marks the tool read-only, so a failure after the call was sent ends the run `unavailable` as `tools_unfinished`, and the retry on status 503 matches it, as it matches `mcp_server_failed` and `tool_not_offered`, which sent nothing; it never matches `unworkable`, nor the `effect_unknown` of a tool not so marked, both of which raise 409 (§2).

**The document a call reads.** The **document** of a tool's answer is its `structuredContent` when the answer has one; otherwise the text of its first text block, read as JSON when it is JSON and as that text when it is not; an answer with neither has no document. One function says it, `answerDocument(result)`, in the module that says what a model sees, `resultText` (`result-text.ts:62-67`), so the two readings of one answer are written side by side and compared in one test: they agree whenever the tool repeats its structured content as JSON text in one block, as the protocol asks; they part where the tool gives both and its text is not that JSON, where `resultText` shows the text and the document is the structure; where it gives several text blocks, which the model reads joined and the document reads the first of; and where it gives only content that is not text, which the model sees as placeholders and the document does not have. 0020's pointers read the same document: its rule said text that is not JSON has none, and a pointer that is not empty finds nothing in a text either, so every reading it describes ends as it said (§9). A test shows what a model sees, which is not what `read` points into where the two part, so `test_tool_call` answers the document as well, in a field **`answer`**, "the document a call's `read` points into: the structured content, else the first text block parsed as JSON, else that text", built by the same `answerDocument`, scrubbed as `text` is, and left out when the answer has no document or its JSON takes more than 64 KiB, the bound `text` has. It amends 0018 §1, in the paragraph of the appendix, which the build appends to that record.

**Arguments.** A tool takes typed arguments, an integer `limit`, a boolean `inclusive`, an object of filters, and the rule that every argument is rendered text (`channel-arguments.ts:44,50`) cannot send them. The rule of every `with` of the document format, a delivery's, a reading's, a telling's and a call's, is therefore one, and it is being built with the delivery now, in the amendment's one renderer, `renderedArguments(templates, variables)` (§4), which answers JSON values: a value written as a number, a boolean, `null`, a list or an object goes as written, its texts rendered in place; a text renders as text, refusing a structure among its text as today (`run/text-rendering.ts:29-44`); and a text that is one output and nothing else, `'{{ input.filters }}'`, takes the value the output yields, which the emitter already sees before it becomes text (`text-rendering.ts:33`). `{{ x | json }}` still renders text, so a template that renders text sends what it sends today. This record adds no second renderer: a call's `with` is rendered by that one, over the call's variables.

### 2. The run: one recorded call, and the endings it may meet

A run of a function with `call`:

1. validates the input against `input.schema` (`run/run-input.ts:12-25`);
2. renders the arguments with `renderedArguments` over `momentVariables(input, at)`, `{ input, today, now }` at the run's moment, the one function the request's `to` and message and the amendment's `deliveryVariablesOf` read (§5); an argument reading what the input lacks is `invalid_input` with the words of `request-rendering.ts:48-53`, a text template rendering a structure or arguments over 16 KiB `conflict` `unworkable`, before anything is sent;

### 3. Guards

- **Who may write it** is who may write the brain, `brain:write`, the permission a reasoning function naming the same tool needs; anyone who may write a brain can already read and change whatever the tool reaches by writing that function and running it, so nothing new is reachable (0018 §3; amendment §2). The call reaches less than that function: its arguments are written by its author and rendered from its input, never chosen by a model reading the tool's answers.
- **What it may call** is what the server's `allowed` names on the server's entry (0003's per-server amendment), checked live by `namedLinks` at every run, before anything is appended.
- **What is kept.** `record_content` decides, per server, whether the call's arguments and answer are kept in its facts, as for every call (0003 §5). The run's output is not a fact of the call: it is the value the function's author chose with `read` and `output.schema`, kept and shown to every reader of the brain as every run's output is, as a reasoning function's answer may repeat what its tool answered under the same rule. A server whose content must not be kept is one whose tools a brain's writers should not be allowed to call, which `allowed` says.
- **Secrets.** A template may not hold `${` and a server is named by name; `callOnce` scrubs the result, content and structured content alike, with every server's secrets, in the JSON and JSON-escaped forms the scrubber knows (`bounds/secrets.ts:14-33`), before the run reads it, so the output and the words are scrubbed too.
- **What a client is told.** `run_definition` is destructive, and the capability reaches outside, while any tool server is configured, `ToolAccess.configured`, as the amendment has it (§3) and as a reasoning function's `mayChangeOutside` is (`capabilities/reasoning/src/capability/reasoning-function.ts:71`). Its description's sentence "A reasoning function that names tools may change something outside the brain…" (`packages/definitions/src/operations/run-definition.ts:17`) reads "A function that calls a tool may change something outside the brain…", 789 characters of 800.

### 6. What is not built

- **No retry inside the run.** One call, answered or failed; the workflow's `catch` and `retry` are the one retry, as the open standard and the HTTP task place it (Context, point 4). `forwarded`'s resend of a request a server refused to take or forgot is the call path's, shared by every caller, and is not a retry of a call.
- **No model**, no prompt, no body.
- **No request**: no deferral, no `list_interactions` row, no expiry, no open-requests count, so `requests_full` is never checked, and `answer_interaction` on such a run answers "The run is not a request of an interaction function that waits for an answer" (`requests/answer-interaction.ts:52-54`).
- **No pagination.** A tool that pages answers one page for each run. Its function answers with the part of the answer that holds both the items and the cursor, leaving `read` out or pointing at a parent of both, with an output schema of that object, and a workflow calls it again with the cursor while there is one, keeping what it read in `$context` with `export.as` and jumping back with `then`, or with `for` and `while` (`workflow-format.md:168-191`); each page is a recorded run of its own, within 64 KiB, and the workflow's output stays within its own bound. A call that follows a cursor itself is a later record's (§10).
- **No direct HTTP.** MCP stays the transport; a system without a tool server is reached through one.

### 10. What this record does not decide

A call that follows a tool's cursor itself; a call of two tools, one resolving what the other takes, which a workflow of two calls or a reasoning function does; whether the operator's `testable`, which vouches that a tool may be tested, should also make a failure after sending safe to retry, where this record reads the server's `readOnlyHint` alone; a workflow retry that waits as a server asked, which needs an error to carry a wait; how `get_definition` and `list_definitions` show a definition's shape, which the pending record on definition fields decides; a call's answer kept between runs; bounds per function; a call that answers binary content or a resource link; the hosted runtime, which offers interaction functions when it offers tool servers (amendment §3); the rename of the wire names (0007), which touches `call` nowhere.

## Consequences

- A workflow reads from and acts on a system through a function saved, versioned and checked like every other: one recorded call, its arguments written and typed, its answer read at a named place, checked against a declared shape and bounded, with no model asked, no prompt to trust and no tool output read by a model; the computation reference's reading function becomes this.
- An interaction function has three shapes in one format and one run path: a call answers at once, a request through a tool and a request in the inbox answer later. They share the tool blocks, the renderer, the variables, the answer check, the call path, the recorder and the document of an answer; the request's schedule, projection and route stay the request's.
- Every ending is an outcome that exists but one, with one because added; a retry on status 503 matches what is safe to try again, a run whose tools only read and a call that sent nothing, and never a definition, an input or an answer that is wrong, nor a run whose tool may have acted; a call that reached its tool is never made again under its id.
- One rule for every run that called tools and could not finish, reasoning and call alike: `tools_unfinished`, 503, when every tool it called is read-only, and `effect_unknown`, a `conflict` at 409, when any is not, so no retry on 503, the workflow reference's own example among them, repeats a tool that may already have posted, paid or written.
