# 0012 — Prediction functions: a playbook predicts from a model file a trainer built on its own history, which the playbook scores, shadows and activates

**Status:** proposed (2026-10-11), revised 2026-10-12 with a target accumulated to a period's end after a read of the earlier platform's model catalog; not built

Designed against `origin/main` at 12f58163, with facts in the ledger (0023) merged. Decisions 0014 (the warm worker pool) and 0022 (TypeScript is the language) reserved this number and name what they left to it.

## Context

A playbook reasons, interacts, predicts, recalls and computes. Four of the five run today; prediction is a README that says a prediction function "defines a predictive capability, including creating an ML model and using it to make predictions" (`capabilities/prediction/README.md`), the terminology page lists lifecycle labels that "apply only when those lifecycle controls exist", and the availability table says "Planned" (`docs/concepts/functions.md:14-17`).

**What the earlier platform did.** A model was a program in Python, written by coding agents the platform ran over an operator's uploaded dataset, tried in several versions and scored on held-back periods against two baselines it walked itself, `persistence` and `seasonal-naive`, on `mase` by default with `winkler` and `crps` available, an 80% interval and a coverage floor of 0.7; the winner was packed into an archive, every build activated its winner, rollback activated an earlier version, and a prediction started a Python process from the archive under a time and a memory limit. Its limits were what a model was and where the work happened: every prediction executed a stranger's program inside the platform, every machine needed Python and its numerical libraries, a prediction was not recorded as a fact, datasets came only from an upload, and a build could not be scheduled.

**What the owner decided**, one question at a time over the design overview, each with the alternatives named for what they compromised:

1. The dataset is a projection of the playbook's own history at the forecast's grain, with an upload for the cold start; a recall function's view, bounded at 512 KiB, was never the way to hand a trainer 200,000 rows.
2. Model files and datasets live behind the one content port, with the ledger's database and object storage as its two backings; nothing kept is deleted.
3. A held model is a file in the industry's portable format, ONNX, run by the native ONNX Runtime in a child process the operating system bounds, one kept warm per model; a WebAssembly build was considered and rejected, since the published build cannot cap its own memory and brings only slower inference once the process is the wall.
4. A build is a run of the prediction function that waits for its trainer through the playbook's request mechanism; the person who asks for a build need not be the one who trains; training happens outside the playbook, on a machine with the skills and the tools; scoring is the playbook's, one candidate at a time, under `PREDICTION_BUILDS_AT_ONCE` and `PREDICTION_BUILDS_PER_DAY`.
5. A new version runs in shadow beside the active one and activates under one of two rules, `automatic` or `approved`; the win is held to a bootstrap confidence so that noise does not activate a model; a version carries a card a reader can rebuild it from; one prediction shape, a forecast of one series, with typed questions left to a later record. A function's first version has no active version to shadow and activates on its holdout; the shadow is for replacing an active version.
6. The baselines are walked in scoring as the earlier platform walked them; a callable default forecast is a new feature and is deferred.
7. The hosted runtime runs the same container image as a self-hosted server. This record removes the isolate as a design constraint: the image is the one runtime, so the design has one answer for both, and the records that assumed an isolate platform are amended by this one. What the hosted product offers, and when, is the private repository's to say, so the public pages keep saying what is offered where.
8. A served model, a prediction service the playbook asks over the network, is deferred: the port is built for it, nothing of it ships.

## Decision

### 1. The definition

A prediction function is a document of the shape every function has: front matter in YAML, then a body. The body is the **brief**, a Liquid template over the dataset's facts, which a build renders for the trainer. `PredictionFunctionDefinition` is the resource, `PredictionFunctionDefinitionDocument` the parsed document, `makePredictionFunctionAdapter` the capability, type `prediction`, media type `text/markdown`, guide `prediction-function`.

| Part         | What it says                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `predicts`   | `target`, the name of the quantity; `period`, one of `day`, `week`, `month`, `quarter`, `year`; `season`, the length of a season in periods, 2 to 366, or left out; `horizons`, 1 to 8 whole numbers from 1 to 52, each once, or in its place `accumulates`, one of `week`, `month`, `quarter`, `year`, longer than `period`, for a target summed from the period after the origin to the end of that enclosing period; `unit`, text for the card                                                                                                                                                                                                                                         |
| `data`       | Either the projection: `events`, 1 to 8 filters in a recall function's vocabulary, the fact types and context attributes with a `data` test over `$data`; `time`, `event` for the fact's time or a JSON Pointer into its data holding an ISO 8601 time; `series`, a pointer to the value that names the series; `target`, `{ of, as }` with `as` one of `count`, `sum`, `last`, `mean` and `of` a pointer, which `count` leaves out; `features`, at most 40 of `{ name, of, as }`; `given`, the names among `features` a question supplies for the horizon; `window`, the periods of history a model is trained on. Or `dataset`, the digest of an uploaded dataset in the same row shape |
| `evaluation` | `holdout`, the periods held back; `metric`, `mase` by default, `winkler` or `quantile`; `coverage_floor`, 0.5 to 0.99, default 0.7; `baselines`, `persistence` by default, `seasonal-naive` when a season is named; `confidence`, 0.5 to 0.99, default 0.9; `shadow_periods`, 0 to 52, default 0; `activate`, `automatic` or `{ approved: <interaction function> }`                                                                                                                                                                                                                                                                                                                       |
| `source`     | Where a build's request goes: `inbox`, the default, or `{ through: <interaction function> }`; `to`, the party, default `trainer`; `expires`, an ISO 8601 duration from 1 minute to 30 days, required                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `rules`      | Lines in words the trainer must follow and the card must state                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| the body     | The brief, a Liquid template reading `dataset` (rows, series, periods, window, holdout, features, horizons) and `function` (name, target, unit, rules) alone                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

The playbook derives the schemas, as it derives a computation function's types from its schemas. The input is one of two shapes: a **question**, `{ series: string, horizon: <one of the horizons>, given?: { <name>: number } }` with the names of `given` and nothing else; or a **build**, `{ build: {} }`. The output of a question's run is the **prediction**, `{ series, origin, period, horizon, value, low, high, coverage: 0.8, version }`, `origin` the last observed period and `period` the predicted one, both in the period's ISO 8601 form (`YYYY-MM-DD`, `YYYY-Www`, `YYYY-MM`, `YYYY-Qn`, `YYYY`); the output of a build's run is `{ version: number | null, winner: string | null, candidates: [{ sha256, verdict }] }`. `describeOutput` says each in words.

**A target accumulated to a period's end.** A question such as where a quarter will land from the days so far is a sum, not a value at a horizon, so `predicts.accumulates` names an enclosing period, `week`, `month`, `quarter` or `year`, longer than `period`, and takes the place of `horizons`. The target is summed from the period after the origin to the end of the enclosing period that next period falls in, so a question asked at a quarter's close predicts the next quarter whole. `target.as` is `count` or `sum`, since a sum of means or of last values says nothing. The question is `{ series, given? }` with no horizon; the prediction's `period` is the enclosing period in its ISO 8601 form, `horizon` the periods summed, and `value`, `low` and `high` the total. The longest horizon is the most grain periods an enclosing period holds, 7, 31, 92 or 366 for days and 13, 53, 3 or 12 for weeks and months, and the bounds of section 13 apply to it, which admits a day to a week, a month or a quarter, a week to a quarter or a year, and a month to a quarter or a year, and refuses the rest at save. The `given` rows cover the periods summed. The dataset, its grid and the CSV files are unchanged: the trainer sees the same rows and fits a model of the total.

Saving validates the document and each refusal names its line, through the shared document reader as every function's save does: a repeated horizon; a holdout under twice the longest horizon or under 8, or over half the window; a window under the holdout plus two seasons, or plus twice the longest horizon when no season is named, or over 1,000; `seasonal-naive` named without a season; a `given` name not among `features`; a feature or the target named `series` or `period`, or a feature named as the target, since the rows' header carries them; `time` or `series` pointing where none of the named event types carries a value, which the check reads from the filters' `type` as a recall function's check reads its events; `count` with `of`, or another aggregation without it; `activate.approved` naming a function that is not an active interaction function, whose `input.schema` does not admit `{ function: string, version: number, card: object }`, or whose `output.schema` is not an object whose one required property `decision` is the enum `approve`, `reject`; `source.through` naming a function that is not an active interaction function whose request takes an answer with `output.schema` `{ candidates: string[] }` and whose `input.schema` admits `{ build: object }`; `rules` past 32 lines or 256 bytes a line; a body that does not compile or reads a name not in `dataset` or `function`; a rendered brief past 64 KiB on the largest dataset the bounds admit. The two checks that read another definition read the registry through the port the coordination capability validates called functions with at save (0011). Saving builds nothing: a build is always a request.

A playbook keeps at most `PREDICTION_MAX_FUNCTIONS` active prediction functions, 32 by default, through `mostActive` as recall does.

### 2. The dataset is a projection kind of its own

A forecast is at a grain and the ledger holds events one by one, so the dataset is a fold of the playbook's history into rows keyed by series and period. The playbook's projections today are its own tables folded by its own code; a dataset is folded by the playbook's code too, since the `data` part is a description and not a program, but its table is per `data` part and its rows are many, which neither a keyed projection nor a recall view is. It is a third kind, kept by the host's projector beside the recall views, folded by the prediction capability's code.

**The tables.** `prediction_datasets`, one row per playbook and `data` digest, the SHA-256 of the canonical JSON of the `data` part, which several definition versions may share: `phase` (`waiting`, `rebuilding`, `live`, `stalled`), `checkpoint` and `checkpoint_at` as a recall view keeps them, `saved`, the order the row was made in, which the projector's slots follow, `rows`, `series`, `first_period`, `last_period`, `events_folded`, and the `data` part as text so the folder reads it without the registry. `prediction_rows`, keyed by playbook, `data` digest, series and period: `target REAL`, `events INTEGER`, the events folded into the row, and `features TEXT`, the feature values as a JSON array in the definition's order, `null` for a feature with no event. Both are the folder's tables, in the ledger's database, declared in the folder's `tables` and created, idempotently, when the store opens, beside the host's own. A dataset keyed by its `data` digest means a definition edit that leaves `data` alone changes nothing, and one that changes it starts a new dataset. One drop rule: a dataset is dropped when no active definition names its `data` part; a version built on a dropped dataset is refused `data_changed` at a question, as section 7 says, so nothing reads it.

**The folder.** The projector takes a **folder** per definition type at composition, as it takes the recall folding today: `Folder { tables, rebuildsAtOnce, playbooksWithRows, rowsOf, reconcile, dropped, phased, fold, write }`: the tables it keeps, how many of a playbook's rows may rebuild at once, the rows of a playbook to pass, which rows a playbook's definition stream wants added and dropped, how a row is dropped and its phase set, how a page is folded and how the changes are written; the slots are the projector's, one rule for every folder, and a folder's write and a row's dropping run in one transaction of the host database when they take more than one statement. The recall folder is today's, a page folded in a pool worker and one JSON view written per row; the prediction capability supplies a folder that runs in the server's process, since the fold is the playbook's arithmetic over values the page already decoded, and the host knows of periods, pointers and aggregations nothing. What generalises: `playbook-pass.ts` is written over `ViewRow`, `foldedPage` and a single view per row, and becomes generic over the folder's row and change; `view-reconciling.ts` keys rows by function name and drops a row when the function goes, where a dataset is keyed by its `data` digest, made when a saved definition first names the part and dropped when none does, and takes a `rebuildsAtOnce` slot while it rebuilds as a view does; `change-writing.ts` writes one conditional statement per view, where a dataset page writes its row upserts, up to 1,000, and its checkpoint in one transaction conditional on the checkpoint it read. For each event of a page that a dataset's filters match, in the order the ledger appended them, the folder reads the time at `time`, in UTC, with the week starting Monday and the quarter on calendar months, finds the period, reads the series at `series`, refuses an event whose series is not text of at most 256 bytes or whose target or feature values are not finite numbers, which it counts and notes as `record_passed_over`, and advances the row: `count` adds one, `sum` adds the value, `last` takes the value of the latest event by time, `mean` keeps the sum and the count and the reader divides. Its checkpoint and phase show in `get_definition`'s standing beside the versions.

**The grid.** The window is a dense grid of periods ending at the last closed period. A period without a row is 0 for `count` and `sum`, a real observation of nothing, and missing for `last` and `mean`, written as an empty cell and never fed to a baseline or a metric; a series with fewer than the holdout plus one observed period is left out of a build, and the card says how many were.

**A build reads content, not the live table.** At a build's start the playbook reads the rows over the window at the dataset's checkpoint, in keyset pages of 1,000, and writes them out as two CSV files through the content port, each under its digest: the **training rows**, with the held-back periods left out, and the **scoring rows**, whole. The trainer reads the first; the scorer reads both; the card names both digests and the checkpoint; and nothing else produces "the dataset's digest". The CSV is UTF-8 per RFC 4180 with the header `series,period,<target>,<feature>...` in the definition's order, periods in the ISO 8601 form of the grain, values as JSON numbers or empty, rows sorted by series then period, one row per series and period.

**Upload covers the cold start.** `PUT /v1/orgs/{org}/playbooks/{playbook}/datasets/{sha256}` under `playbook:write`, body `text/csv` with `Content-Length`, at most 64 MiB, in the grammar above with any header, kept through the content port, which computes the digest as it streams and refuses a body whose digest is not the path's; that, a header, a period form, an order or a number that fails, or rows past the dataset's bounds, is refused `invalid_input` with the line number at the first fault, and nothing is kept. A definition names it as `data.dataset`, and such a function has no projection; its `get_definition` standing says so.

### 3. A build is a run of the function that waits for its trainer

A build spends someone's time, so it is always someone's request: a caller or a workflow runs the function with the input `{ build: {} }`, through `run_definition` as every run is asked, so a schedule, a workflow step and a person's agent ask for one the same way, and no tool is added.

**The contract learns the input.** Whether a run finishes later and how long it may run depend on the input here, a question or a build, and the capability contract declares them per parsed definition alone. So the contract gains `longestRunFor(parsed, input)` and `finishesLaterFor(parsed, input)` beside `longestRunOf(parsed)` and `finishesLater(parsed)`, the pair for a known input defaulting to the pair for any, so that no declaration mistakes an unknown input for one; `PreparedDefinition` exposes `longestRunMs`, `longestRunMsFor(input)` and `finishesLaterFor(input)`, since nothing reads whether a definition finishes later for an input it does not have; the start records `finishes_later` from the input it has; and the coordination capability resolves a call's limit from the call's literal input where it has one and from the definition's longest otherwise, which amends 0011. A question is `finishesLater: false` with 10 s; a build is `true` with `source.expires` plus the scoring bound, eight candidates at ten minutes, plus the start. Two definition types, one that predicts and one that builds, were rejected: one function is the owner's decision 5, and a build is of the function.

The run of a build:

1. Refuses as its first act, so the run's stream holds `run_started` and `run_rejected` and nothing else: a build in flight for the function (`conflict`, kind `build_in_flight`, naming the run), the day's builds spent (`unavailable`, kind `builds_full`), the deployment's builds at once spent (`unavailable`, kind `builds_full`), a dataset that is `waiting`, `rebuilding` or `stalled` (`unavailable`, kind `dataset_not_ready`), or one past its bounds (`conflict`, kind `dataset_too_large`, with the figure).
2. Assembles the dataset as section 2 says and records `dataset_assembled` with the two digests, the rows, the series, the first and last period, the window, the holdout, the checkpoint and the `data` digest.
3. Renders the brief over the dataset's facts and keeps it through the content port, at most 64 KiB; records nothing for it beyond the deferral.
4. Defers. With `source: inbox` the deferral's record is a **request** in the one shape every request has (section 10): `to` from `source.to`, the message, `answer_schema` `{ candidates: string[] }`, `expires_at` and `requested_at`, and beside them `build: { brief_sha256, brief_bytes, training_sha256, training_bytes, routes }`. The message holds, within the 8 KiB a message has, the build's run id, the three paths below and the brief's opening; the whole brief is read over its route. With `source: { through: <function> }` the record is `{ waiting_for: { run: <child id> }, expires_at, build }` and no request of its own, so the listing shows one request a build, the child's.

**Children are started by the due work under derived ids.** A build's children, the `/request` run of the interaction function it goes through and the `/approval` run of section 6, have ids derived from the build's run id and the reference, as a workflow's children have (0011), so the record names the child before it exists, and the builds projection makes the row due at once. The due work starts the child through the port the host's executor starts child runs through, `dispatchToPlaybook` with `calledBy: { runId: <build>, reference: '/request', run: 1 }`, the build's `callDepth` plus one within `mostCallDepth`, and the input `{ build: { run_id, function, brief_sha256, routes, expires_at } }`; a start repeated after a crash meets a run under that id and records nothing, so there is no window that leaves an orphan. The child's own request carries the build to a party through its `deliver` and takes `{ candidates }` as its answer; the trainer answers the request the listing shows.

**The trainer's three routes**, each under the caller's own key with `playbook:read` for a read and `playbook:write` for the upload, each working only on a build that stands waiting for its answer, each refusing another run (`conflict`, kind `not_a_build`) and a build that has ended (`conflict`, kind `build_ended`):

- `GET /v1/orgs/{org}/playbooks/{playbook}/runs/{run_id}/build/brief`, `text/markdown`, the brief whole.
- `GET /v1/orgs/{org}/playbooks/{playbook}/runs/{run_id}/build/rows`, `text/csv`, the training rows streamed from the content port.
- `POST /v1/orgs/{org}/playbooks/{playbook}/runs/{run_id}/build/candidates`, body `application/octet-stream` with `Content-Length` required, at most 64 MiB, refused with 413 before the body is read when the length says more or 411 without one; the body is staged under the build's run (section 9) as it streams, the port answering its digest and size, then checked in a model process (section 8): a file the runtime does not load, one whose signature is not the playbook's (section 4), or one past the eight a build takes is refused, recorded as `candidate_refused` with `because` `failed_to_load`, `wrong_signature` or `too_many` and its digest, and dropped from staging. A file that loads is `candidate_uploaded` with its digest, size, opset and signature, and the route answers `{ candidate: <sha256>, bytes, opset }`. The same bytes again answer the same digest and record nothing.

These are operations served over HTTP alone, with bodies that are not JSON, which the catalog cannot say today; section 12 adds the declaration. The answer is the tool the playbook already has.

**The answer continues the build; it does not settle it.** `answer_interaction` records `request_answered` on the run (section 10), caused by the request's message, and the capability that owns the run takes it from there: the prediction capability's builds projection folds it and the due work scores. An answer naming a digest no `candidate_uploaded` of the build carries is `invalid_input`, naming it. With `source.through`, the child's `run_succeeded` carries the answer as its output, and the builds projection folds it by the child's `calledBy.runId` as it folds `request_answered`.

**The builds projection and the due work.** `prediction_builds_1` is a keyed projection over run streams, one row per build run: the function and its version, the `data` digest, the standing (`starting_request`, `waiting_for_trainer`, `scoring`, `in_shadow`, `awaiting_approval`, `ended`), `requested_at`, `expires_at`, the candidates uploaded and scored, the winner, the model version, the shadow's periods and the period last graded, `next_due_at`, and `open`. It is made by `run_deferred` of a prediction run; `request_answered`, and a child's `run_succeeded` whose `calledBy.reference` is `/request` (keyed by `calledBy.runId`), set `scoring` and make the row due at once; a child's `run_started` at `/request` moves `starting_request` to `waiting_for_trainer`; `candidate_scored` and `candidate_disqualified` count and make it due again; `version_built` moves it to `in_shadow` or `awaiting_approval`; a child's ending at `/approval` records the decision and makes it due; the build's own ending closes it. Its indexes are by function and open, and across playbooks on `next_due_at`. The day's builds are counted by reading the function's rows newest first by `requested_at`, at most the setting plus one, since a keyed projection's count takes equalities alone. `buildsDue({ ledger, content, models, runs })` is its due work, `runs` the port above, in the lane that does not call out: a perform starts a child, scores the next unscored candidate, makes the shadow's predictions at a period's close, grades the ones whose period has closed, decides the shadow, or activates, each as sections 5 and 6 say, each one fact and one row change, so a restart carries on from the last fact. A perform that finds no scoring permit free ends at once and the row is due again in a minute; a perform whose fact meets a run that has ended, cancelled meanwhile, takes `runEnded` as done. The open requests' due work expires a request as it expires any, which ends the run `rejected`, reason `unanswered`, kind `expired`, and closes the row; a build through a function expires when its child does; a cancel through `cancel_run` ends it `rejected` `cancelled` through the capability's `cancel` decision, which answers the same for a build starting, waiting or scoring. A build's request counts among the playbook's open requests under `INTERACTION_OPEN_REQUESTS`.

**The build's ending.** When every uploaded candidate is scored or disqualified, the playbook records the baselines' scores, picks the winner (section 5), records `version_built` on the model's stream when there is one, and settles the run `succeeded` with the output `{ version, winner, candidates }` as the playbook, `playbook:<playbook>`; with no candidate uploaded by the answer, or none that won, `version` and `winner` are `null` and the run still succeeds, since the build did its work and a workflow branches on the output. The shadow and the activation that follow are the model's lifecycle, not the run's, so the build's longest run is `source.expires` plus the scoring bound; a workflow's remaining duration caps the call as it caps any (0011), so a workflow that asks for a build with a long `expires` late in its life has it cancelled with the kind `deadline`.

**Bounds on asking.** One build in flight per function, counted on the projection's open rows; `PREDICTION_BUILDS_PER_DAY` per function over the trailing 24 hours; `PREDICTION_BUILDS_AT_ONCE` per deployment, counted across playbooks, which also bounds the scoring permits of section 8 and must be below `PREDICTION_PROCESSES` so that a question always finds a process.

### 4. A held model is a file in a signature the playbook publishes

A trained model saved as ONNX is numbers and a graph of operations, which the training libraries export to; no trainer's code ever runs inside the playbook. The playbook requires one signature, which the guide publishes and the upload checks by reading the model's inputs and outputs:

| Tensor  | Shape       | Type    | What it holds                                                                                                          |
| ------- | ----------- | ------- | ---------------------------------------------------------------------------------------------------------------------- |
| `y`     | `[1, L]`    | float32 | the last `L` observed values of the series, oldest first, `L` at most the window, a missing value as `NaN`; an input   |
| `x`     | `[1, L, F]` | float32 | the features over the same periods in the definition's order, present when `features` is non-empty; an input           |
| `given` | `[1, H, G]` | float32 | the `given` features for the `H` periods ahead, in the definition's order, present when `given` is non-empty; an input |
| `q`     | `[1, H, 3]` | float32 | the 10th, 50th and 90th percentiles for each of the `H` periods ahead, `H` the longest horizon; the output             |

Dynamic axes are allowed where the table has `L`, `H` or `1`; the opset is 13 to the newest the runtime supports; a model with other inputs or outputs is `wrong_signature`. The playbook reads the step it needs from `q`: `value` the 50th, `low` the 10th, `high` the 90th, so `coverage` is 0.8 by construction and measured in scoring. A model that needs more than the signature carries is the trainer's to fit within it, which the brief says. With `accumulates`, the signature gains `h`, `[1]`, int64, the periods remaining to the enclosing period's end, and `q` is `[1, 1, 3]`, the percentiles of the total over those periods; the upload checks that shape instead.

**Staging and the winner.** A candidate is staged under its build for the build's life (section 9) and never written to the kept content until it wins; the winner is written through the content port under its digest, which is what the version holds, and the losers are dropped with the build, their digests, sizes and scores on the build's facts. A kept file is never deleted, as nothing kept is.

**The cache.** A model process loads a file from the server's cache, `/var/tmp/auto-runtime/models/<sha256>.onnx`, written by rename after the whole file is read from the content port and verified against its digest, at most 1 GiB a server, least recently used out, rebuilt from the port whenever a file is missing. A file that fails the digest is a defect, as content that does not match its digest is today.

### 5. Scoring

When the request is answered, the playbook scores each uploaded candidate on the held-back periods the trainer never saw, one at a time, in a model process under 10 minutes and the process's memory limit:

- **One job, one walk.** A scoring job is one message to the model process, `{ walk: { rows: <path to the staged scoring rows>, window, holdout, horizons } }`, and the child walks the origins: for each series and each held-back period as an origin, it feeds the rows up to that origin and answers every origin's `q`, as one typed array per series. The server computes the metrics and the baselines from the answer; nothing crosses the pipe one origin at a time.
- **Rolling origin.** Each held-back period is an origin; from each origin the candidate forecasts every horizon that still lands within the holdout; a holdout of at least twice the longest horizon and at least 8 periods gives every horizon at least as many pairs as half the holdout.
- **An accumulated target** is scored the same way with the total as the quantity: from each held-back origin the candidate answers the total to the end of the origin's enclosing period, the truth is the realized sum of those rows, and a pair counts only when that end lies within the holdout; `persistence` becomes the run-rate, the mean of the enclosing period's periods observed so far, or of the last as many periods when none is, times the periods remaining, with its interval from the empirical quantiles of its own in-sample errors of that total; `seasonal-naive` is the same periods' sum one season earlier; `mase` is scaled by the run-rate's in-sample mean absolute error.
- **Metrics**, each per horizon and averaged over the series: `mase`, the mean absolute error of the 50th percentile divided by the in-sample mean absolute error of the seasonal-naive forecast, or the naive one when no season is named, over the training window of that series; `winkler` at α = 0.2 over the 10th and 90th percentiles; `quantile`, the pinball score summed over the three percentiles the signature carries, in place of `crps`, which needs a distribution the shape does not have. `coverage` is the share of truths within `[low, high]` over all pairs.
- **The baselines** are walked over the same origins by the playbook's own code, series by series: `persistence` carries the last observed value forward with an interval from the empirical quantiles of its own in-sample errors; `seasonal-naive` takes the value one season earlier likewise, and skips a series with fewer than a season of observed rows before an origin. Each is `baseline_scored` with its metrics, coverage and `series_walked`, or `baseline_not_walked`, `because: too_short`, when no series could be walked.
- **Confidence.** For each named baseline, the per-origin difference between the candidate's and the baseline's primary metric is resampled by a moving-block bootstrap, block length the season or ⌈n^(1/3)⌉ when no season is named, 1,000 resamples, seeded from the build's run id so that the figure is reproducible; `p_better` is the share of resamples in which the candidate's mean is lower. A candidate **beats** a baseline when `p_better` is at least `evaluation.confidence`.
- **The verdict.** A candidate that could not be scored is `candidate_disqualified` with `because` `timed_out`, `out_of_memory`, `crashed`, `not_loaded` or `answered_badly`, the last for a tensor of the wrong shape or a non-finite number; one whose coverage is under the floor, or that does not beat every walked baseline, is `candidate_disqualified` with `coverage_below_floor` or `not_better`; the rest are `candidate_scored` with their scores, coverage and `p_better` per baseline, and the one with the lowest primary metric wins. The baselines' scores sit on the build's stream beside the candidates, as the earlier platform carried them on its build.

### 6. Shadow and activation

A winner becomes a **version** of the model, `version_built` on the model's stream, `models/<function>`, numbered from 1, with its card. Activation follows the definition's rule after its shadow.

**The shadow is for replacing an active version.** A function with no active version has nothing to shadow: its first version activates on its holdout, `shadow_passed` recorded at once, and `evaluation.shadow_periods` applies from the second version on. For a function with an active version, for `shadow_periods` closes of the period after the version is built, the playbook itself, as due work at each close, asks the challenger and the active version, each in one `walk` job over every series with rows in the window from the scoring rows as they then stand, for every horizon, and records each version's answers as one `shadow_predicted` fact with the origin, the count and the predictions as content under `predictions_sha256` and `predictions_bytes`, which is the forward test no trainer could have read. At each later close it grades the predictions whose period has closed against the dataset's rows, one `shadow_graded` per version and period with the metrics and the pairs graded and missing, and a truth that arrives after that close is not graded. When the last horizon of the last shadow origin has been graded, the verdict is one fact: `shadow_passed` when the challenger's primary metric over the graded pairs is no higher than the active version's, `shadow_failed` otherwise, each with the two figures. With `shadow_periods: 0`, `shadow_passed` is recorded at once and the holdout alone decided. With `accumulates`, the closes the shadow counts are the enclosing period's, each prediction is the total from one close to the next, and it is graded when that next close arrives.

**The rule.** `automatic` records `version_activated { version, rule: automatic }` on a passed shadow, the playbook the actor in the context. `approved` has the due work start a run of the named interaction function as the build's child under its derived id, `calledBy: { runId: <build>, reference: '/approval', run: 1 }`, with the input `{ function, version, card }`, which that function delivers as it delivers any request; its answer `{ decision }` settles the child, the builds projection folds the child's ending by `calledBy.runId`, and the due work records `version_activated { version, rule: approved, approved_by }` or `activation_refused { version, because: approver_rejected, refused_by }`; a child that expires or is cancelled is `activation_refused { because: unanswered }`. A failed shadow is `activation_refused { because: shadow_failed }` and no approval is asked. A version refused stays built and may be activated by hand.

**Activation by hand, and rollback.** `activate_version`, `POST /v1/orgs/{org}/playbooks/{playbook}/definitions/prediction/{name}/activate` with `{ version }`, under `playbook:write`, records `version_activated { version, rule: requested }` for any built version of the function, the caller the actor in the context, so rollback is the same fact; a version that is not built is `not_found`, the active version again is `conflict`, kind `already_active`. It is served over HTTP alone in this version, by the declaration of section 12, since the tool listing stands at its bound (0016, amended 2026-10-11); the tool follows when that record makes room.

**The models projection.** `prediction_models_1` is a keyed projection over model streams, one row per function: the active version and the `data` digest it was built on, the latest version, the versions built, the challenger in shadow and when its shadow ends. A question's run reads the active version from it in one read.

**The card** is the data of `version_built`, bounded so that it fits the 4 KiB a page serves without a cut: the build's run id; who trained it, the answer's actor; the dataset's two digests, rows, series, periods, window, holdout and checkpoint; the file's digest, size and opset; the features and `given` used; the scores per horizon and the coverage; `p_better` per baseline; the baselines' scores; and the rule it will activate under. The trainer's recipe and limitations in words, as the answer may carry them, `recipe` and `limitations` text of at most 8 KiB each, are content under `recipe_sha256` and `limitations_sha256` with their `_bytes`, read whole through `get_event`. The shadow's result and the activation are their own facts and the standing joins them: `get_definition` of a prediction function answers the active version, the latest, the build in flight, the challenger and its shadow, and the dataset's phase and checkpoint.

### 7. A prediction

A question's run validates its input and refuses, as its first act, a function with no active version (`conflict`, kind `no_active_version`: "The function has no active version yet; ask for a build with the input `{ build: {} }`"), one whose active version was built on another `data` part (`conflict`, kind `data_changed`: "The data part changed since version n was built; ask for a build"), a series the dataset does not hold (`invalid_input`, naming it), and a `given` value for a name the definition does not list. It reads the series' last window of rows from the dataset at its checkpoint, feeds `y`, `x` and `given`, takes a model process from the pool, warm when one holds the version's file, within 10 s in all (`unavailable`, kind `model_process_busy` when none is free in time), runs the session, reads the step from `q`, and succeeds with the prediction as its output and `{ version, origin, dataset_checkpoint, duration_ms }` as its record. A process that dies or answers a non-finite number ends the run `unavailable`, kind `model_process_failed`, and the process is let go. Every prediction is therefore a fact, `run_succeeded`, with its version, so a recall function folds predictions and the outcomes that arrive and grades the model, as the overview has it; the playbook's own grade is the shadow's. With `accumulates`, the question names no horizon: the run feeds `h`, the periods from the origin's next period to the end of its enclosing period, and answers their total, so a question asked at an enclosing period's close predicts the next one whole.

### 8. Where it runs: the model process pool

A model file comes from outside the playbook, and the runtime that parses it has had vulnerabilities, so a model never runs in the server's process. It runs in a **model process**, a child the operating system bounds:

- **Memory.** The child is started as `prlimit --core=0 --data=<bytes> node <module>`, `RLIMIT_DATA` set to `PREDICTION_PROCESS_MEMORY`, so the native runtime's allocations and V8's alike fail at the limit and the process dies, the server untouched, and the kernel writes no core file. `RLIMIT_DATA` counts the process's writable private address space, which V8 reserves eagerly for its code range and heap: the model process's entry starts under no less than 704 MiB on amd64 and 448 MiB on arm64, measured in the image on each architecture on 2026-10-12, so the setting's floor is 768 MiB, which every build of the image proves by loading the entry under the limit, and the default is 1,280 MiB, the floor plus the room a loaded 64 MiB session and its tensors take. Resident memory stays far below the limit, and the container's own limit bounds it. The limit is Linux's; on a development machine without `prlimit` the process runs unbounded and the test that reaches the bound runs on Linux.
- **Time.** A job has a deadline by its kind: `check`, a file loaded and its signature read, 30 s; `run`, one question, 10 s; `walk`, a scoring or a shadow over many series and origins, 10 minutes. At the deadline the pool sends `SIGKILL`, the `exit` event carries the signal, the job ends `timed_out`, and the warm session dies with the process.
- **Reach.** The child is started with an empty environment and no handle to the ledger, so it holds no key; it has the container's network, which this record does not isolate, and the wall is that a hostile file reaches that child alone. Its one channel is the IPC pipe to the server: `{ check: <path> }` answers the signature, `{ run: { y, x, given } }` answers `q`, `{ walk: { rows, window, holdout, horizons } }` answers every origin's `q` per series, as JSON with typed arrays as base64.
- **Threads.** The child sets the session's intra-op threads to the larger of 1 and the cores divided by `PREDICTION_PROCESSES`, so four processes do not oversubscribe the machine.

The pool is the roster, shelf and fleet of 0014 over a process-backed `Thread`, keyed by the model's digest as a worker is keyed by its module, with `poolSlots` of its own, `PREDICTION_PROCESSES` permits, so a scoring job never takes a computation permit; 0014's constants hold, a process let go after a minute idle, after its 1,000th job and after any job that killed it, and a job waits for a permit within its deadline. `walk` jobs hold at most `PREDICTION_BUILDS_AT_ONCE` of the permits, so a question always finds one. The engine's pool is generic over a `Thread` and knows neither the runtime nor the module: `capabilities/prediction` depends on `onnxruntime-node` and holds the child module, `src/process/model-process.ts`. The baselines and the dataset's fold run in the playbook's own code; nothing of a model runs there.

**The image** gains `onnxruntime-node`, pinned, installed with the `--ignore-scripts` the Dockerfile already passes, its binaries for the other platforms pruned as sqlite3's build leftovers are, 46 MB on amd64 and 26 MB on arm64, measured when it is built, with the capability's two `COPY` lines; and a build-time check that `prlimit` runs as the image's user, since the base image's `util-linux` carries it.

### 9. The content port takes bytes, streams, and stages

The content port of 0023 was text, whole, in memory; a 64 MiB model read through it would sit in the server's heap. The port becomes bytes, and it computes the address: `put(playbook, { stream, mediaType, expected? })` reads the stream, computes the SHA-256 of the bytes and their size, and answers `{ sha256, bytes }`; `expected` is a digest or a size the caller asserts, and a mismatch fails with a typed error, `not_its_digest` or `not_its_size`, as a stream that fails is `stream_failed`, so a route that takes a digest from a caller refuses a mismatch as `invalid_input` without a second path. `get(playbook, sha256) → { stream, bytes, mediaType } | undefined` verifies the digest before it hands over the last chunk. For text the digest is the SHA-256 of its UTF-8, as today, so every digest a fact carries stands; the digest is Node's `createHash`, one function for the repository, and the ledger's portability rule of the isolate era, which forbade Node's modules in its main entry, is retired with it (section 16). The database backing keeps chunks of at most 1 MiB as `BLOB` on SQLite and `bytea` on PostgreSQL in `recorded_content_chunks`, keyed by the put that wrote them, with the head written last naming that put and carrying the size, the chunk count and the media type, so two puts of one digest never interleave, the first head wins, and a put that fails, is refused or loses the race deletes its own chunks. The object-storage backing speaks the S3 API, the de facto interface of object stores, which the Bedrock settings' `AWS_ENDPOINT_URL` and the default credential chain already configure: `CONTENT_STORE_URL`, an `s3://bucket/prefix` URL, one object per digest under `<prefix>/<playbook key>/<sha256>`, the object's presence the head, written through an upload keyed by the put and a conditional copy, so two puts of one digest at once leave identical bytes and, on a store that ignores the condition on a copy, the later media type; the server checks the bucket at start and refuses to start without it. The two are two adapters behind one port, chosen at composition, and the hosted runtime configures the second.

**Staging** is a second namespace of the same port, keyed by a run, since the port knows runs and not builds: `stage(playbook, run, { stream, mediaType, expected? })`, `staged(playbook, run, sha256)` and `unstage(playbook, run)`, kept in `staged_content` with the build's run id in its key on the database, removed in one transaction where the store has one, under `<prefix>/staging/<playbook key>/<build>/<sha256>` on object storage, read by the scorer on whichever server holds the lease, and removed when the build ends. Nothing kept is deleted; what is staged is deleted with its build.

### 10. The request is the playbook's, and an answer is one fact

A request was the interaction capability's: its record shape in `capabilities/interaction/src/run/request-record.ts`, the open-requests projection admitting a deferral by definition type, and two answer paths, `answer_interaction` settling at once and a reply recorded as `reply_taken` and settled by due work. A build waits for a person or an agent as an interaction run does, so the request moves to where every capability can open one, and the two answer paths become one:

- `RequestRecordSchema` moves to `@beonauto/definitions`, `{ to, message, answer_schema?, answerer?, reply?, expires_at, requested_at, deliver?, replies? }`, with `deliver` and `replies` as JSON objects there and typed by the interaction capability's own schemas where it reads them; `isRequestRecord` reads it.
- The open-requests projection makes a row for any `run_deferred` whose record is a request, whatever the definition type, and keeps the type in a column; `list_interactions` describes `function` as "The function that asked" and shows its type, and its `to` filter finds a build by `source.to`.
- **An answer is always a fact on the run**, `request_answered { answer, claimed_for?, reply? }`, its actor and time in its context: `answer_interaction` records it, with `claimed_for` as today, and a reading records it with `reply`, the reply's identity, in place of `reply_taken`, which goes. The decider admits it as the work of a deferred run once; a second with another digest is `conflict`, the same again records nothing; the state keeps the answer in place of `broughtAnswer`. What follows is the capability's: the interaction capability settles the run from the recorded answer in its due work, whoever recorded it, within the host's sweep, a second by default; the prediction capability scores. `answer_interaction` answers the recorded fact, and its description says it answers "a request a function's run waits on; the run takes the answer within the host's sweep, a second by default". An answer is refused once a cancel is asked, and a cancel asked after an answer settles against it, one rule in the decider.
- The expiry and the delivery of a request stay the open requests' due work, for any type; a build in the inbox has no delivery, and a build through a function has the child's.

### 11. Facts

Each fact is named for what happened, one type per outcome, with its data and nothing else, its context in the metadata (0023). On the build run's stream: `run_started { input: { build: {} }, finishes_later: true }`; `dataset_assembled { data_sha256, training_sha256, training_bytes, scoring_sha256, scoring_bytes, rows, series, first_period, last_period, window, holdout, checkpoint }`; `run_deferred { record }`; `request_answered { answer, claimed_for?, reply? }`; `candidate_uploaded { sha256, bytes, opset, inputs, outputs }`; `candidate_refused { sha256, bytes, because }`; `candidate_scored { sha256, scores, coverage, against, duration_ms }`; `candidate_disqualified { sha256, because, detail? }`; `baseline_scored { baseline, scores, coverage, series_walked }`; `baseline_not_walked { baseline, because }`; `run_succeeded { output, record }`, or `run_rejected` with `unanswered` `expired` or `cancelled`. On the model's stream, `models/<function>`, a stream kind of its own, keyed by the function's name, whose decider `capabilities/prediction` owns: `version_built`, `shadow_predicted`, `shadow_graded`, `shadow_passed`, `shadow_failed`, `version_activated { version, rule, approved_by? }`, `activation_refused { version, because, refused_by? }`. On a question's run: `run_started`, `run_succeeded` with the prediction, or a rejection.

**Where a capability's facts live.** The run events and the run commands are closed unions in `@beonauto/definitions`, and the interaction's delivery and reply facts sit in the core union, which is the debt. A capability declares the schemas of its own run facts and of its own stream kinds on its `CapabilityDeclaration`; the run decider's event schema, the playbook's reserved names and the presenters are built from the capabilities composed; and `@beonauto/definitions` gains a `work` command, `{ type: 'work', fact }`, admitted while `takesSettlement(state)` holds and refused `runEnded` otherwise, through which a capability's due work and routes append their facts. The interaction's facts move out of the core union by the same declaration. Every type is refused on `publish_event` and `send_run_event` with the playbook's reserved names, and none is a playbook event a trigger matches, as the interaction facts are not today.

### 12. Operations, routes and refusals

### 14. Guards

A trainer is given the training rows and the brief, never the held-back periods and never the playbook's keys; the three routes work on the build they were opened for alone, under the caller's own key; the build ends only through its answer, its expiry or a cancel; every file and answer a trainer gives is validated as any input is, a model file is checked in a bounded process before it is accepted and runs only there, started with an empty environment, bounded in memory by the operating system and in time by a kill; the shadow is the playbook's and reads rows no trainer saw; a version activates only under the definition's rule or a caller's `playbook:write`; nothing builds at save; a build's request message never holds the brief whole or any row; and the kept content of a model is proved by its digest on every read.
