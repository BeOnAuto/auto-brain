# 0018 — Testing a tool call: an agent tries one tool of a tool server through the brain, as a run would call it

**Status:** accepted (2026-10-08), designed against `feat/speaking-to-agents` at 09b727a2 and verified again against `origin/main` at f4a7d7f6, where that branch has merged; built on 2026-10-08, with the amendments from the build after the appendix and the verifications of the record against the code at the end

## Context

On 2026-10-07 a person who does not code asked Claude Desktop, connected to nothing but a brain's MCP endpoint, to build a brain that reads a search-analytics service through a gateway-style tool server: five generic tools, `search`, `introspect`, `execute`, `validate` and `dry_run`, with the real knowledge one level down, in the graph the gateway fronts. To learn which operations existed and what shape they had, the agent created a throwaway reasoning function, `explore-graph`, whose prompt told the model to use the tools and report back, ran it once, and wrote the real functions from the model's summary. It worked. It also left a one-off function and a run in the brain, cost a model call, and gave the agent a paraphrase where it needed exact shapes. The same gap made the person put a chat channel's id in a prompt instead of `#random`: resolving a name takes one lookup call, and the agent had nowhere to make one. The rule stands: the person talks to brains and nothing else, so connecting the agent to the tool server directly is not an option.

What the brain gives an agent today, measured on the branch: `list_tool_servers` answers each server's tools as `{ name, description, input_schema }` (`packages/mcp/src/listing/tool-server.ts:12-20`), with a server that cannot be asked as `{ name, type, unavailable, because }` (`tool-server.ts:29-38`), and nothing an agent could call. The server's own account of a tool, its `annotations`, is dropped where the listing is decoded: `ListedToolSchema` keeps `name`, `description` and `inputSchema` and nothing else (`packages/mcp/src/bounds/result-text.ts:18-22`), so the brain does not know which tools a server marks read-only. A run reaches a tool in one way, `ToolAccess.open` (`packages/mcp/src/access/tool-access.ts:20-29`): it takes a connection from the server's link, lists the server's tools once and keeps the slot (`connectedTo`, `packages/mcp/src/access/server-listing.ts:27-48`; `openedRun`, `packages/mcp/src/access/run-opening.ts:30-49`), refuses a server not configured for the brain or a tool the operator does not allow before connecting (`namedLinks`, `packages/mcp/src/access/tool-naming.ts:53-75`), and offers each named tool as a `call` (`caller`, `packages/mcp/src/calls/tool-caller.ts:25-59`) that admits the call against the bounds (`admission`, `packages/mcp/src/bounds/call-bounds.ts:79-87`), records `tool_call_started` through the run's journal before sending and `tool_call_answered` after, forwards it with the retry, reopening and restart rules (`forwarded`, `packages/mcp/src/calls/tool-calls.ts:149-152`), and shapes the answer for the model, scrubbed of secrets and cut at 64 KiB with a note (`replyOf`, `packages/mcp/src/calls/call-replies.ts:44-52`; `shownResult`, `call-bounds.ts:93-99`); the run lets the slots go through the `close` of the tools it opened, however it ends (`RunTools.close`, `packages/mcp/src/calls/run-tools.ts:64-66`; `withTools`, `primitives/inference/src/tools/tool-opening.ts:51`). A delivery of an interaction function's request reaches a tool a second way, `callOnce` (`packages/mcp/src/delivery/call-once.ts:28-57`), which forwards through the same `forwarded` but takes its slot, checks its names and shapes its answer with code of its own. The listing reaches a server a third way, `toolServersOf` (`packages/mcp/src/access/tool-servers.ts:41-56`), through `connectedTo`. The bounds are one table, `toolBounds` (`call-bounds.ts:3-16`): 16 KiB of arguments, 64 KiB per result, 30 s per call, 10 s to open, 4 KiB of recorded content where an entry says `record_content`.

Over MCP a full key lists 24 tools on `/mcp`, the bound (`packages/api/src/bounds/served-bounds.ts:13`, enforced at `packages/api/src/mcp/mcp-connection.ts:55-56`, pinned by `packages/server/src/mcp/served-tools.test.ts:81`), and the instructions take 1,948 characters on `/mcp`, 1,473 on `/orgs/{org}/mcp` and 1,908 on `/orgs/{org}/brains/{brain}/mcp`, under a bound of 2,000, built per connection from the tools the key lists (`packages/api/src/mcp/instructions.ts:177-193`). A tool's annotations come from what its operation declares: `readOnlyHint` from its kind, `destructiveHint` from `irreversible` or `mayChangeOutside`, which `execute_spec` takes from the primitives it runs (`packages/api/src/tools/tool-definition.ts:22-35`; `packages/specs/src/operations/execute-spec.ts:29-30`; `primitives/inference/src/primitive/reasoning-function.ts:71`). Anyone who may write a brain may already read whatever its tool servers' credentials reach, by writing a function that names a tool and running it; a key with `brain:read` alone may not run anything (`packages/operations/src/caller/permission.ts:11-15`).

The Model Context Protocol says of annotations that `readOnlyHint` means a tool "does not modify its environment", that `destructiveHint: false` means "the tool performs only additive updates" and is "meaningful only when `readOnlyHint == false`", that `destructiveHint` and `openWorldHint` default to true when absent, and that "Clients should never make tool use decisions based on ToolAnnotations received from untrusted servers" (https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2025-06-18/schema.ts), that "clients MUST consider tool annotations to be untrusted unless they come from trusted servers", that "there SHOULD always be a human in the loop with the ability to deny tool invocations", and that clients should "Log tool usage for audit purposes" and "Show tool inputs to the user before calling the server" (https://modelcontextprotocol.io/specification/2025-06-18/server/tools).

What the comparison decides, point by point:

1. **The word is "test".** Zapier, Pipedream, Windmill and Retool say it, and Redpanda calls the one-tool runner a "Direct test"; Make says "run once", n8n "execute step", the API clients "send". The operation is named with it: `test_tool_call`, "Test a tool call". It is a call, not a run, and the name says so.
2. **A test is live, and the builders are told.** Zapier says twice that "Testing is live and may result in changes made in your app"; Retool lets writes run only when triggered and offers a confirmation; Apollo says to point Sandbox at non-production endpoints only. Nobody fakes the call. So the brain makes the real call, through the real credentials, and refuses the call rather than faking it where a tool may write: the guard is the server's own `readOnlyHint`, or the operator's word.
3. **The test feeds the next step.** Make's "look at its bundles", Windmill's "suggested as inputs for further steps", Pipedream's autocomplete, n8n's "fill in its input data": the point of a test is what the builder does with the answer. The agent's next step is a prompt the model will follow, so the test answers exactly what a run's model would see, shaped and cut as a run shapes and cuts it, and nothing the model would not see.
4. **The test is recorded, apart from production.** Postman keeps every request in History and responses only when asked; n8n keeps manual executions in the editor, out of the production list; the Inspector keeps the transcript with "Secrets masked". So the brain records a test in its history as two small events of their own kind, never as a run, with content only where the operator records content for calls, scrubbed as calls are scrubbed.
5. **Annotations are trusted by whoever chose the server.** The specification says hints are untrusted "unless they come from trusted servers"; Codex's `writes` mode and OpenAI's `read_only` filter trust `readOnlyHint`; Claude Code, Cursor and VS Code ask a person instead. An operator who configured a server and allowed its tools has chosen to trust it as far as `allowed_tools` goes; its `readOnlyHint` is trusted that far and no further, and the operator extends the list by name where a server marks nothing.
6. **An agent probing through a generic executor is an accepted pattern.** Stripe's and Sentry's agents reach a catalogue through one call tool; the Inspector's CLI exists for "coding agents"; Redpanda offers the runner beside the Playground. One operation on the brain, under the brain's own permissions and bounds, is that pattern.
7. **Sampling and skipping are not for us.** Zapier's sample records and "Skip tests", n8n's pinning, stand in for a live call where one would write. A tool that may write is not tested here at all; a function the person asked to run calls it, as today.

## Decision

### 1. One operation, `test_tool_call`

`test_tool_call`, "Test a tool call", is a command of the brain, `POST /v1/orgs/{org}/brains/{brain}/tool-servers/{server}/tools/{tool}/test` over HTTP and the MCP tool of the same name. It calls one tool of one tool server with the arguments the caller gives, as a run of a reasoning function would call it, and answers what that run's model would see.

Inputs:

| Field       | Where                        | What it holds                                                                                                                                                                           |
| ----------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `server`    | the path; an argument on MCP | The tool server, as `list_tool_servers` names it and a function writes it before the slash: 1 to 32 lowercase letters, digits and hyphens, starting with a letter (`serverNamePattern`) |
| `tool`      | the path; an argument on MCP | The tool of that server, as `list_tool_servers` lists it and a function writes it after the slash: 1 to 128 letters, digits, underscores, hyphens and dots (`isToolName`)               |
| `arguments` | the body                     | The arguments of the call, an object in the shape of the tool's `input_schema`; `{}` when left out; at most 16 KiB as JSON, the bound a run's call has (`toolBounds.argumentBytes`)     |

Output, `succeeded` whenever the call was made, however the tool answered:

| Field               | What it holds                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `test_id`           | The id of the test, a UUID, under which its two events are recorded                                                                                                                                                                                                                                                                                                                                       |
| `server`, `tool`    | As given                                                                                                                                                                                                                                                                                                                                                                                                  |
| `outcome`           | `result`, `tool_error` (the server answered with `isError`, or refused the arguments, which a run's model is told as a tool error it may recover from), `server_failure` or `timed_out`: four of the five outcomes a run records for a call (`CallOutcome`, `packages/mcp/src/calls/recorded-calls.ts:8`); the fifth, `cancelled`, arises only when the caller has gone (section 2), so it reaches nobody |
| `text`              | What a reasoning function's model would see: text content as text, structured content as JSON only when there is no text content, other content as a one-line placeholder, an `isError` text as it is, scrubbed of the server's secrets and cut at 64 KiB at a code point with the run's note (`resultText`, `shownResult`); for a failure, the words a run's model gets, at most 300 characters          |
| `result_bytes`      | The size of the whole result, `content` and `structuredContent` as the client hands them back, before the cut; `null` when there is none                                                                                                                                                                                                                                                                  |
| `duration_ms`       | How long the call took                                                                                                                                                                                                                                                                                                                                                                                    |
| `server_request_id` | The server's own id of the request, where the entry's `request_id` names where it carries one; absent otherwise                                                                                                                                                                                                                                                                                           |
| `tested_at`         | When the call was made, in ISO 8601 UTC                                                                                                                                                                                                                                                                                                                                                                   |

The answer is what the model would see and not the raw wire result, because the next thing the agent does with it is write a prompt the model will follow; a field the model never gets, such as `structuredContent` beside text content, would mislead that prompt. The agent that needs the structure asks the tool for it, as the model would.

The plain words of a success name the tool and the server and say what came back: "The tool “search” of “graph” answered in 312 ms with 1,204 bytes; what a reasoning function's model would see is in the details." For a `tool_error`: "The tool “search” of “graph” answered an error, as a run's model would see it; the details show what it said." For `server_failure`: "The tool server “graph” failed to answer the test: ‹the words›. It may or may not have received the call." For `timed_out`: "The tool server “graph” did not answer the test within 30 seconds; it may still have received the call." Each within 400 characters.

### 2. The call path is the run's, and there is no second one

The rule of this record: **the one way a tool is called is `ToolAccess` in `packages/mcp`, and a test is `open` with one reference, one `call`, and the `close` of the tools `open` answered** (`RunTools.close`, `run-tools.ts:64-66`), never `ToolAccess.close`, which stops every link of the server (`linked-access.ts:33-35`). Nothing is forwarded, admitted, recorded, scrubbed, cut or retried by code of its own. Concretely:

1. The test asks `access.open(context, [{ server, tool }])` with a context whose `id` is the test's id and whose `journal` is the test's journal (section 4). `namedLinks` refuses a server not configured for the brain or a tool the operator does not allow before any connection is made; `connectedTo` takes the connection and lists the server's tools within the open bound; `unlistedOn` refuses a tool the server does not list; one tool is offered.
2. The test checks the testing guard (section 3) on the listed tool's annotations, and lets the connection go without calling when the guard refuses.
3. The test calls `offered.call({ callId: test_id, input: arguments }, signals)` inside `Effect.promise`, with the interruption signal `Effect.promise` hands it as both `signal` and `cancelled`, as the delivery takes it (`delivery-call.ts:22`); `settle` arms that interruption from the request's own signal over HTTP and MCP alike (`packages/operations/src/dispatch/settle.ts:31`, `packages/api/src/operations/operation-routes.ts:47`, `packages/api/src/tools/tool-callback.ts:44`). `admission` admits the call, since a test's tally is empty and the input schema bounded its arguments (section 6); the journal records the start before the call is sent, and the call is not sent if that fails (`tool-caller.ts:43-47`); `forwarded` waits out a 429 within the longest wait, reopens a session the server forgot once and restarts a `stdio` process that exited once; the journal records the answer unless the caller went away meanwhile (`tool-caller.ts:53-56`); and `replyOf` shapes the answer as the model would see it. A caller that goes away mid-call interrupts the test, so the `cancelled` outcome `forwarded` then answers (`tool-calls.ts:85-87`) reaches nobody and is recorded nowhere: the stream keeps a start without an answer.
4. The test lets the slot go through `close`, in an `ensuring` that runs on interruption too, once the forwarded call has settled, as `releasedOnceSettled` waits for a listing a run was interrupted in (`run-opening.ts:21-28,35`) and as `withTools` ensures a run's `close` (`tool-opening.ts:51`): an `http` session no run holds is ended, and a `stdio` process stays up until the server stops, as after a listing (`server-links.ts:120-125`). Without the `ensuring`, a request abandoned mid-call would leave the link's holder count at one and the session open for good.

So a test of an `http` server that no run holds costs it six requests: initialize, its notification, the stream `GET`, `tools/list`, `tools/call` and the `DELETE` that ends the session; five for a server that issues no session id. The listing of tools is needed, since the guard reads the tool's annotations from it and a run lists before it calls too.

What the test needs that the path does not give today, each a small change to the path and never a copy of it:

- `OfferedTool.call` answers more than `{ text, isError }`: a `CallReply` that also carries the recorded `outcome`, `resultBytes`, `durationMs` and `serverRequestId`, and `not_sent` as the outcome of the two replies a run's path makes without sending, a call refused inside the brain or not recorded (`tool-caller.ts:7-12`), which a test never meets (sections 5 and 6) but which keeps the type whole, so the test builds its output from one answer and the model path keeps reading `text` and `isError` (`packages/mcp/src/calls/call-replies.ts:7-10`, `run-tools.ts:12-17`).
- The metadata a call carries is given by whoever opens, not built from an execution id: `metaOf` (`packages/mcp/src/calls/tool-calls.ts:110-114`) goes, `Forwarding.meta` is a field, and the context a caller opens with carries its `meta`. A run gives `{ "com.beonauto/execution_id": id }`, a delivery adds `com.beonauto/delivery_id`, and a test gives `{ "com.beonauto/tool_test_id": test_id }` and no execution id, since there is no run for a receiver to correlate with. `RunContext` becomes `CallerContext`, `{ id, org, brain, journal, meta }`, since a test is not a run, and `Replying`, which reports a failed call to the operator with the run's id (`call-replies.ts:12-17,34-38`), takes what the opener gave.
- A server message reported to the operator names what the call was for: `ServerMessage` carries `tool_test_id` beside `execution_id`, one of them null, so the log line of a failed test names the test as a run's names the run (`packages/mcp/src/access/run-context.ts:12-16`).
- `ListedToolSchema` keeps `annotations`, the four hints as optional booleans and nothing else (`packages/mcp/src/bounds/result-text.ts:18-22`), which the listing and the guard both read; `title` stays dropped until something reads it.

### 3. Guards, and who may call

A test is made only when all of these hold, in this order, each refused in the words of section 5. Before the operation runs, the dispatcher refuses a caller without its permission (`packages/operations/src/dispatch/authorization.ts:17-26`) and a command on a retired brain (`authorization.ts:79-86`), and the input schema refuses what does not fit; then, in the handler:

1. **The caller may write the brain.** The operation is a command, so `brain:write` permits it, as running a function needs (`permissionFor`, `packages/operations/src/caller/permission.ts:13-15`). Anyone who may write a brain can already read whatever its servers' credentials reach by writing a function and running it, so this opens nothing new; a key with `brain:read` alone is refused `forbidden`, is not offered the tool on its connection (`permittedTo`, `packages/api/src/mcp/mcp-server-factory.ts:53-60`), and sees no sentence about it in its instructions. A workflow cannot call it: its steps call `execute_spec`.
2. **The server serves the brain, and the operator allows the tool.** The checks a run makes, `mcp_server_not_configured` and `tool_not_allowed`, before any connection; what `allowed_tools` does not allow a function, it does not allow a test.
3. **The server lists the tool.** `tool_not_listed`, as a run finds it when it connects.
4. **The tool can be tested.** Either its server marks it `readOnlyHint: true`, or the operator lists it in `testable_tools` (section 11). A tool with no annotations is, by the specification's defaults, one that may write, and is not tested; so is one marked `destructiveHint: false` without `readOnlyHint: true`, which the specification reads as a tool that "performs only additive updates", a write all the same. A tool marked read-only and destructive at once is read-only: the specification says `destructiveHint` is "meaningful only when `readOnlyHint == false`". The hint is trusted exactly as far as the operator trusted the server: the specification's "trusted servers" are, for a brain, the servers in `mcp_servers`, `allowed_tools` says how far that trust goes, and the brain acts on `readOnlyHint` alone, never on another hint.

Nothing else is asked. A person's confirmation before the call is the client's to give, which the tool's annotations make possible (section 7), as the specification asks of clients and not of servers.

### 4. Two events of their own kind, recorded as a run's calls are

A test is recorded on a stream of its own, `tool-tests/<test_id>`, under the brain's prefix, as two events:

| Event                | Fields                                                                                                                                                                                                                                |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tool_test_started`  | `test_id`, `server`, `tool`, `arguments_bytes`, `arguments_sha256`, `arguments_json` only where the entry says `record_content`, scrubbed and cut to 4 KiB as stored; `by`, the caller's id; `at`                                     |
| `tool_test_answered` | `test_id`, `outcome`, `result_bytes`, `result_sha256`, `duration_ms`, `jsonrpc_id`, `server_request_id` where the entry names `request_id`, `result_json` only with `record_content`, scrubbed and cut to 4 KiB as stored; `by`; `at` |

They are the facts of `tool_call_started` and `tool_call_answered` with the test's id in place of the run's id, the call's number and the model's call id, which a test does not have. The facts are built by the builders a run uses, `callStarted` and `callAnswered` (`packages/mcp/src/calls/recorded-calls.ts:69-101`), fed by the same `Recording` the caller makes from the entry's `record_content` and `request_id`, so content is recorded, scrubbed and cut exactly where and as a run records it, and never otherwise; the test's journal leaves out the `call_id` the builder writes, since the test gives its own id as the call's and the event carries it once as `test_id`. The ledger reads a brain's events by its prefix and not by the kinds it knows (`selectedOf`, `packages/ledger/src/recorded/recorded-statements.ts:88`, answers `{ kind: 'brain' }` for everything), so the new streams reach `list_brain_events` with no change to the ledger. The four rules of decision 0003 §5 hold at no cost: one test is one call, so nothing needs a permit; the start is recorded before the call is sent and the call is not sent when the start cannot be recorded; the stream's decider takes a start once and an answer once after it and refuses anything else; a caller that goes away mid-call, or a server that dies between the two, leaves a start without an answer, which reads, as it does for a run, as an outcome unknown, and nothing settles it later, as nothing settles a run's call in flight at cancellation (0003 §5, rule 3). The events are appended through `BrainWriter.execute` with a decider of the stream's own, as the run's journal appends (`tool-call-journal.ts:43-48`). The second event names the first as its cause, as the run's journal does with `messageIdOf` (`packages/specs/src/tool-calls/tool-call-journal.ts:18-20,47-50`); the first has no cause, as a run the caller started has none.

`list_brain_events` shows them, with `type` `tool_test_started` and `tool_test_answered`, through a presenter for the stream kind `tool-tests` beside the presenters for `executions`, `specs` and `events` (`packages/brains/src/feed/list-brain-events.ts:77-79`), each within 4 KiB of data and recorded content shown at 2 KiB as a call's is (`mostContentBytes`, `packages/specs/src/presenting/event-data.ts:19`); their summaries say who tested which tool of which server and how it answered, in the outcome phrases a run's calls use. `get_execution_history` never shows them, since there is no run; a recall function never folds them and an event trigger never fires on them, since a test is not a fact of the brain's work any more than a run's tool calls are: the follower that feeds both passes over every stream kind but `events`, `executions` and `specs` without a note (`packages/workflow-host/src/follower/followed-events.ts:85-93`), and `brainFactOf` answers nothing for any other kind (`packages/specs/src/events/brain-facts.ts:100-108`); the two type names join the types a published event may not claim (`packages/specs/src/events/reserved-attributes.ts:32-55`). No run, no definition, no version: nothing in `list_specs`, `list_executions` or the analytics changes because a tool was tested.

### 13. What this record does not decide

## Consequences

- An agent that needs to know what a tool server offers tests its tools and reads exactly what a run's model would read, in one call, recorded, bounded and scrubbed as a run's call is; it makes no function, starts no run and spends no model call to look. A name a prompt needs is one test away.
- Nothing new is reachable: the permission is the one running a function needs, the tools are those `allowed_tools` allows, and a tool that may write is tested only where the operator has said so, in a setting that is checked at start and that makes `test_tool_call` destructive to a client that honours hints.
- The call path stays one: the three callers, a run, a delivery and a test, share `namedLinks`, `takenSlot`, `forwarded`, the admission, the recording, the scrubbing and the cut, and the build removes two copies that exist today rather than adding a third.
- The brain's history gains a kind of event that is not a run's, read by `list_brain_events` and ignored by `get_execution_history`, the analytics and recall; what a server says of its tools reaches the agent through the listing.
- The cost: a 25th tool on `/mcp`, and the bound moves with it; the instructions grow by a clause of 42 characters; a test of an `http` server costs it six requests; the fake server learns annotations; and `packages/specs` depends on `packages/mcp`.
- The hosted runtime, which configures no tool server yet, serves the tool and the setting and answers every test as it answers the listing, with words that say what is not set up.
