# 0015 — Several triggers: a workflow starts on an event and on its schedules, each trigger kept and matched on its own

**Status:** accepted (2026-10-08), with the amendments from the build at the end

## Context

Verified against the code at 3a47712. A workflow's `schedule` names one trigger, `on`, `cron` or `every`, and the policy refuses two together with "A workflow has one trigger" (`primitives/orchestration/src/document/workflow-schedule.ts:22,114`), a rule of the reactions record (0004, "one trigger kind, not both"), not of the specification: the DSL 1.0 schema's `schedule` is an object of four independent fields, `every`, `cron`, `after` and `on`, with no choice among them (`@openworkflowspec/sdk`, `"schedule": { "unevaluatedProperties": false, "properties": { every, cron, after, on } }`). A person who needed a workflow to start on an event and at a time switched its trigger back and forth. Around that rule, several things are wrong in ways this record fixes rather than works around:

- the saved definition says only `reacts: true` (`primitives/orchestration/src/document/workflow-summary.ts:13`; `packages/specs/src/registry/spec-events.ts:9`), so the host reads the trigger again from the YAML source (`packages/server/src/workflows/reaction-dependencies.ts:50`; `packages/workflow-host/src/reactions/spec-records.ts:17-20`), a second parse of the same document; a version whose source it cannot read is deactivated without a word (`spec-records.test.ts:32-33`), and a spec record it cannot decode at all is passed in silence (`spec-records.ts:22`) where an unreadable event is reported (`follower/record-steps.ts:56-57`); the trigger's shape is written three times in the host, as a type (`reactions/reaction-options.ts:8-11`), a timing type (`schedules/schedule-times.ts:3-5`) and two schemas (`reactions/subscriptions.ts:21-38`), and the orchestration imports the type from the host to read a document (`workflow-schedule.ts:14`);
- the host keeps one row per workflow, `PRIMARY KEY (brain_key, workflow)` (`packages/workflow-host/src/database/host-tables.ts:81-91`), replaced at every version with the anchor moved and `running` reset (`subscriptions.ts:76-81`), so an `every` slips at each save of the body and the one-run-at-a-time rule lapses across a save;
- a run started by an event names the event's record as its cause and takes its id from the workflow, the version and the record (`reactions/subscription-starts.ts:55-63`; `reactions/reaction-ids.ts:5-7`); a run started by a schedule has `cause: null` (`schedules/schedule-firing.ts:83`) although every event names its cause (#107); the start fact names the call that started a nested run, `called_by` (`packages/specs/src/execution/execution-events.ts:11-19`), carried on the in-process request beside the lineage (`packages/operations/src/dispatch/request.ts:18`; `dispatch/brain-binding.ts:21,39`; `caller/call-lineage.ts:11-16`), and nothing names a trigger, so a history reads "A run of the workflow “x” started." for both (`plain-language/event-words.ts:23-25`); `started_by` is the actor, `brain:<brain>` (`caller/caller.ts:21-22`; `execution/execution.ts:69`), which the smoke asserts (`.github/workflows/ci.yml:453,457`);
- `reacts` and `reacts_since` (`registry/spec.ts:30-35,57-62`; `operations/get-spec.ts:34-37`) are in no reference (nothing in `docs/reference/http.md`), and `reacts_since` is described as "the first record of the brain it reacts to"; a trigger filter stores `dataNeedsVariables` (`subscriptions.ts:28`) that save refuses to be true (`workflow-schedule.ts:46`); the same filter written twice in `any` is accepted; the tests write a JSON trigger as a spec's source and decode it with a stand-in parser (`reaction-testing/brain-writes.ts:58-62,79`).

Elsewhere, triggers are keyed things a run names: GitHub Actions keys them by event name, takes a list of crons, and tells a run which one by name; Temporal keeps a schedule as a named thing apart from the code version, with one run at a time by policy, and stamps a started run with the schedule's id and the due time; Argo Events names every dependency and trigger.

## Decision

### 1. The document: `schedule` names up to three triggers, one of each kind, each identified by its place

```yaml
schedule:
  on:
    any:
      - with: { type: com.acme.ledger.closed, data: '${ .region == "eu" }' }
  cron: '0 9 * * 1-5'
  every: PT15M
```

`on`, `cron` and `every` are each a trigger of their own, kept and matched on their own, any one, two or three of them; the one-kind rule goes, `after` stays refused, and each field is checked as today, the `cron` check through `cronRejectionOf` of the host as today (`workflow-schedule.ts:14`), which the build leaves there, since the host owns the time arithmetic the check must agree with. A trigger is identified by its kind, `event`, `cron` or `every`, and its reference in the document, `/schedule/on`, `/schedule/cron` or `/schedule/every`: the specification's own words, which no edit renumbers or renames, so a run names its trigger exactly and two versions compare their triggers like with like. `on` stays one event trigger with `one` or `any` filters, and no trigger carries an input mapping of its own: a run's input is the list holding the event, or `{ "schedule": { "due": <time> } }`, as today, two shapes a workflow tells apart with `input.from` or a `switch`. Refused at save, beside today's rules: a filter written twice in `any`, two filters whose parsed `type` and `attributes` are equal; and more than 64 filters in one trigger. Two keys of one name cannot be written, since the YAML reader refuses them (`packages/config/src/yaml/yaml-reading.ts:89`).

### 2. The facts: a saved definition carries its triggers, named `triggers`

The summary a workflow gives at save, the `content` of `spec_created` and `spec_updated`, and the definition `get_spec` and `list_specs` answer carry `triggers`, the list of parsed triggers in document order, in place of `reacts: true`, which goes with `reacts_since`: `{ kind: 'event', reference, filters: [{ reference, type, attributes }] }`, `{ kind: 'cron', reference, expression }` or `{ kind: 'every', reference, milliseconds }`. One schema in `@beonauto/specs`, beside `details`, replaces the host's type, its timing type and its two schemas; `kind: 'events'` becomes `event`; `dataNeedsVariables` goes, so the engine's `matchEvent` takes `Pick<LiteralFilter, 'reference' | 'attributes'>` (`packages/workflow-engine/src/filters/event-filter.ts:151-158`) while `LiteralFilter` stays for listeners. The host's `triggerOf` option goes: `specChangeOf` answers the triggers, a spec record it cannot decode is reported through `parts.unreadable` as an unreadable event is, the stand-in parser of the tests goes, and nothing reads a source twice. `get_spec` adds `triggers_since`, one id per definition, the record from which the current version is what its triggers start; that it is one id and not one per trigger is a compromise of the view, since each trigger's own activation record is in the host's rows and shown nowhere yet. The bound on reacting definitions counts definitions whose `triggers` is not empty, as today.

### 3. The read models: one row per trigger, kept across versions while the trigger is unchanged

`workflow_subscriptions` is keyed by brain, workflow and trigger reference, with the kind, the rule, the id and time of the record that activated it, and for a schedule its next due time and running run; `workflow_subscription_types` is unchanged, since only `on` names types. When the follower passes a spec record, in the ledger's order (`record-steps.ts:118-123`), or replays the records at a rebuild (`follower/brain-discovery.ts:65-72`), it compares the version's triggers with the workflow's rows by reference and rule: an unchanged trigger keeps its row with the version moved on, so its anchor, its next due time and its running run survive a save of the body; a changed schedule trigger moves its anchor and its next due time to that record and keeps its running run, so one run at a time holds whichever version started that run; a changed event trigger and an added trigger of any kind get a row activated by that record; a removed trigger, a version without a schedule and a retirement delete the rows. A trigger therefore applies from the record that activated it in its current form, starts the version current at each record, and ends at the record that removes it: nothing earlier is matched, and a match before the removing record starts the version then current. A record is matched by at most one trigger, since only `on` matches records and it gives one verdict per record (`subscription-starts.ts:24-31`); a start's id is derived from the workflow, the version, the trigger's reference and the record id or the due time, so a record or a due time starts one run per trigger, and a redelivery starts nothing again.

### 4. The run's start: the trigger on the fact, the actor unchanged

The host's start carries the trigger on the in-process request beside `calledBy`, through the call lineage into `startOf` (`operations/execution-running.ts:63-76`), and the start records it on `execution_started` as `trigger: { kind, reference }` beside `called_by` (`execution-events.ts:11-19`); every finish copies it as it copies `called_by`; `brainFactOf` puts it in the fact's data (`events/brain-facts.ts:19-28,65-86`), so a trigger filter can test `.trigger.kind`; the history shows it, and its words key on the kind, "A run of the workflow “x” was started by its event trigger", "by its cron schedule" or "by its every schedule" (`event-words.ts:23-25`; `presenting/execution-presenter.ts:129-134`), the name quoted as every summary quotes it and the reference never in a summary, which the internal-terms check refuses (`packages/api/src/testing/internal-terms.ts:17`), so the specs package never learns the document's layout. `started_by` stays the actor, `brain:<brain>`: the Run schema is every function type's, and who acts is not what fired. A run an event started is caused by the event's record, as today; a run a schedule started is caused by the record that activated its trigger, which may precede the record of the run's `spec_version` when the trigger was kept across versions, and the HTTP reference says so beside the run's cause (`docs/reference/http.md:180`); no run of the brain is then without a cause. `get_execution`, `list_executions` and analytics are unchanged.

### 5. Bounds and guards

A schedule trigger has one running run; a filter that fails is said once per trigger and version; the depth bound is per record, unchanged; the start rate and its backlog stay per workflow by design (`docs/reference/workflow-format.md:158,444`; 0004 §4), counting the event trigger's starts across its filters, and schedule starts stay outside the rate as today, since they never pass it (`reactions/reacting.ts:21`; `schedule-firing.ts:83`; `subscription-starts.ts:55`); refusals are counted per workflow and minute as today, every reason naming the trigger by kind, and the `reaction_refused` words say "its triggers". The self-guards are per workflow: a run any trigger started is the workflow's own, so its facts, the facts of runs it started and the events it emitted start no trigger of that workflow. A schedule and an event due in one moment start two runs, under two ids, by design; `cron` and `every` due at one instant start two runs too.

| Bound                                | Value                                                    | Why                                                                                                   | When reached                                   |
| ------------------------------------ | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Triggers of a workflow               | 3: one `on`, one `cron`, one `every`                     | the specification's `schedule` has one field for each kind, and `on` takes a list of filters          | a fourth cannot be written; `after` is refused |
| Filters of an event trigger          | 64                                                       | every filter is evaluated for every event of a type it names, for the life of the version             | refused at save                                |
| Workflows with triggers in a brain   | 1,024, at most 3,072 trigger rows                        | unchanged; rows grow by at most three                                                                 | saving one more is `conflict`                  |
| Starts a minute, per workflow        | 60, then 1,000 waiting for a later minute                | unchanged; the event trigger's starts count, schedule starts stay outside it                          | deferred, then refused and said                |
| Running runs of a schedule trigger   | 1, kept across versions                                  | a time due while the trigger's last run still runs is skipped, whichever version started that run     | skipped and said                               |
| Reaction depth                       | 8, per record                                            | unchanged                                                                                             | refused and said                               |
| Schedule triggers fired in one round | 64                                                       | unchanged                                                                                             | the rest fire in the next rounds               |
| `every`                              | at least a minute, counted from the trigger's activation | a trigger kept across versions keeps its anchor; a changed one counts from the record that changed it | refused at save                                |

### 6. Vocabulary and surfaces

The terminology page says a workflow's schedule may name an event trigger and schedule triggers of both kinds (`docs/concepts/terminology.md:58`); the format reference's trigger section, refusal table and limits (`docs/reference/workflow-format.md:117-159,389,442-446`) and the concept page (`docs/concepts/workflows.md:43-46`) say three triggers, the kind and place that identify each, the filter bound, and that `every` counts from the trigger's activation; the HTTP reference documents `triggers`, `triggers_since`, `trigger` on a start and a scheduled run's cause with its caveat (`docs/reference/http.md:180`); the engineering reference and the host's README describe the rows and the comparison (`docs/engineering/reference/workflow-format.md:9,129`; `packages/workflow-host/README.md:50,128-132`); the MCP reference is unchanged, no tool is added, and `get_spec`'s `standing` is untouched. The smoke saves one workflow with `on` and `every`, publishes the event, and reads two runs, each history naming its trigger's kind (`.github/workflows/ci.yml:413-459`).

### 7. What this record does not decide

Several schedules of one kind, such as two crons, which the specification's `schedule` cannot write; `after`; `on.all`; a view of each trigger's activation record, next due time and last run; an input mapping per trigger; time zones; a rate per trigger instead of the workflow's 60.

## Consequences

- A workflow starts on an event and at its times without switching; each trigger is a row of its own, a run says which trigger started it, and the words, the facts and the run graph say so too.
- The trigger is parsed once, at save, and travels on the fact: the host reads no document, the orchestration imports no host type to read one, a definition's triggers are visible in `get_spec`, and one schema in specs replaces four shapes.
- Debts paid: a scheduled run has a cause; a save of the body no longer moves an `every` nor forgets a running run; an undecodable spec record is reported; `triggers`, `triggers_since` and the trigger of a start are documented; the stored filter carries only what is matched; a filter twice over is refused; the tests' stand-in parser goes.
- The engine changes one signature, `matchEvent` over a filter's reference and attributes; no input, output or state format changes, since the machine never knew what started a run.
- Three trigger rows per workflow at most, so the follower's reads per record are unchanged in count, and the schedule firing has at most two rows per workflow due.

## Verification the build must include

- A workflow with `on`, `cron` and `every` saved once: a published event starts one run, a due time of each schedule starts one run, each start fact and history names its trigger's kind and reference, each fact's data carries it, the event-started run is caused by the event and the scheduled ones by the activation record; `cron` and `every` due at one instant start two runs; a redelivery and a repeated due time start nothing again; on both stores and through HTTP and MCP.
- Versions: a saved body with the triggers unchanged keeps the anchor, the next due time and the running run, and the next run is of the new version; a changed `every` counts from the new record and still skips while the old version's run runs; a changed `on` matches nothing before the new record and a match before it starts the old version; a removed `cron` fires no more while `every` goes on; a version without a schedule and a retirement stop every trigger; a rebuild from the spec records gives the same rows; an undecodable spec record is noted and passed.
- Save: two kinds together accepted, `after` refused, a filter twice refused, 65 filters refused, the reacting-definitions bound still per definition.
- Bounds and guards: 60 a minute per workflow with a schedule's start not counted, one running run per schedule trigger across a version change, a failing filter said once per trigger version, the depth bound, the self-guards for a run the schedule started whose emission the event trigger of the same workflow would otherwise match; every refusal's reason naming the trigger's kind; no reference in any summary, through the internal-terms check.
- `get_spec` and `list_specs` showing `triggers` as the list and `triggers_since`; the smoke with one workflow and two runs.
- Measured and recorded in the host's README: timer lateness and reaction latency with 1,000 workflows that each carry the three triggers, and the firing of 1,000 `every` schedules due in one minute, on both stores.

## Amendments from the build

Built on 2026-10-08 on `main` at f4a7d7f, where the code the context cites had moved since 3a47712 in its line numbers only. Each change from the text above is below.

- **Where the rows live.** The rows of the triggers, their comparison at a spec record and the words that name a trigger have a folder of their own in the host, `src/triggers` (`trigger-rows.ts`, `trigger-changes.ts`, `spec-records.ts`, `trigger-words.ts`), since `src/reactions` already held more files than a concept folder should; `reactions/subscriptions.ts` became `triggers/trigger-rows.ts`. The comparison is a pure function, `triggerChangesOf(kept, saved)`, over Effect's structural equivalence of `TriggerSchema`, so a filter's attributes written in another order are the same rule.
- **A spec record that cannot be decoded.** As the follower passes it, it is noted once as `record_unreadable` and passed over before any consumer is offered it, so a trigger that names `spec_created` no longer meets it as an unreadable fact as well. At a rebuild the host reads the spec stream with the stream read, which gives each record's data and id but not its stored type, so the note gives the type the data names, or `unknown` when the data names none.
- **The table keeps its name and changes its key.** The host makes its tables with `CREATE TABLE IF NOT EXISTS`, so a database made by an earlier build keeps the old `workflow_subscriptions`, without `reference` and `activated_by`. On such a database the read of the due schedules, which selects `activated_by` (`schedule-rows.ts`) and comes first in every round of the follower (`follower-loop.ts`), fails, so every round fails: no trigger starts a run, no run that listens is offered an event, and no waiting call is answered, nor any cancel given, while the host says only that the follower failed and tries again. Nothing is live, so no migration is written: the database is deleted before this build runs on it, `packages/server/.data/ledger.db` for `pnpm dev`, or else the file `LEDGER_FILE` names or the PostgreSQL database `DATABASE_URL` names, and the server makes it again, empty.
- **`get_spec`'s description** gains one sentence, "For a workflow it also returns its triggers, the event trigger and the schedules that start it on its own.", at 600 characters and five sentences against the bounds of 800 and eight, so that an agent knows the field is there; the MCP reference is otherwise unchanged and no tool is added. The `schedule` recipe says a schedule names one trigger or up to three, and that a run's history says which started it. `TriggerSchema` describes a reference as a JSON pointer without naming the document's keys, so the specs package does not learn the document's layout in its descriptions either.
- **The words.** `reaction_refused` says "The workflow “x” was not started every time its triggers called for it in a minute". Each reason names the trigger by its kind: "could not be started by its event trigger", "An event matched the event trigger of the workflow at reaction depth 9", "The filter of the workflow's event trigger failed", "The run its every schedule had due at … was skipped: the run its every schedule started before still runs", "The runs its cron schedule had due from … to … came while the server was down".
- **Telling the inputs apart.** The format reference shows how a workflow with both kinds tells a list holding the event from `{ "schedule": { "due": … } }` in `input.from`, with `if type == "array"`, and a test of the orchestration runs that example on both inputs.
- **Measured, and the read of the event triggers.** The record says the follower's reads a record are unchanged in count. The first build kept main's read, every event trigger of the brain once a batch of 100 deliveries, which in a brain of 1,000 workflows with event triggers is ten reads of 1,000 rows a record, and left 1,000 events published back to back 28 to 94 s behind. The host now reads only the event triggers that name the record's type, through `workflow_subscription_types` and a new index on its brain, type and workflow, a page of the deliveries still left plus one (`triggers/trigger-rows.ts`, `reactions/subscription-starts.ts`): a filter's type is written out, so no other trigger can match, and a filter's data expression is no longer evaluated on events of other types. Measured on 2026-10-08 with `measure triggers`, once with the first read and twice with the read by type, under a load average of 4 to 81 from other work (the host's README has the table): reaction latency at the median went from 14.6 to 17.5 s to 0.77 to 1.26 s on SQLite and from 21.9 to 23.8 s to 0.13 to 1.09 s on PostgreSQL, and every event started its run within 1.3 s on SQLite and 1.2 s on PostgreSQL; three triggers each cost 0.2 to 0.8 s more at the median than one, which the measurement does not break down; with three triggers each, timers fired within 67 ms at most on either store; and 1,000 every schedules due at one time all started within 0.2 s on SQLite and 0.6 s on PostgreSQL, but for one round at a load of 73.2, which took 6.3 s. Two earlier rounds with the first read, at a load of 3 to 58, gave the same figures for it.
