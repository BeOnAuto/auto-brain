# 0002 — Reading the runs of a brain and what happened in it

**Status:** accepted (2026-10-05), revised twice after audit the same day

## Context

A brain records everything it does on the ledger, one stream per thing:

- Every run is a stream, `executions/<id>` under the brain's prefix `brain/<org>/<brain>/`, written by the execution decider: `execution_started`, `execution_deferred`, `execution_succeeded`, `execution_rejected` and `execution_failed`, each with who caused it and when. `get_execution` folds one such stream and shows the latest start. A caller may supply the id, a workflow's child runs get ids derived by hashing, and a run started again with the same id records a new start, so an id says nothing about order. A start carries the run's input, up to 256 KiB; a finish carries its output and record, up to 1 MiB together; both are tenant JSON that may hold any character, including U+0000.
- The brains of an org and the specs of a primitive are registries: one stream each, written by a decider, because they enforce an invariant, a unique name. A brain's own lifecycle, created, updated and retired, is recorded in the org's registry stream, outside the brain's partition.
- A workflow run also has the engine's run log, one stream per run (decision 0001): a state-transition log whose events, `input_applied`, carry the receipt of the input with its time, the steps it moved, the outputs it produced and the patch to the state. On the hosted runtime that stream lives in the run's own isolate, not in the brain's object, so a run's two streams share no position there.
- `POST /executions/{execution_id}/events` already exists: `send_execution_event` sends an event into a workflow.

The ledger port reads one stream and appends to one stream, through the event store's own operations only, with no SQL of its own. Both stores underneath, SQLite and PostgreSQL, keep for every message its stream, a global position and a recorded time; PostgreSQL also keeps the transaction id, and a position becomes visible before an earlier one has committed, which Emmett's own batch read handles by ordering by transaction id and position and reading behind the oldest open transaction. On PostgreSQL, reading a field out of an event's JSON fails the whole query when the event holds U+0000 anywhere in it. Several self-hosted servers may share one PostgreSQL database; the hosted runtime's shared database driver commits each statement on its own.

Nothing lists the runs of a brain or of a spec, nothing reads what happened inside one run, and nothing shows what happened in a brain. A caller learns a run id from the answer of `execute_spec` or from an event it sent.

In text a user reads, an execution is a run. Code and the API keep the word execution.

## Decision

### 1. Every read is a read of the ledger; no read model until a measured need

Three kinds of read, each the simplest thing that is correct:

- A **registry** enforces a rule across its members, so it stays a decider over one stream, as today.
- A **list of runs** is a query over the brain's partition of the ledger: the first message of every execution stream, newest first by its position, joined with the latest message of the same stream for the status. It is exact, it has nothing to rebuild, it needs no projection, and it works wherever the brain's record lives. A read model is the upgrade when the measurement in this record says a page is too slow; it is not built now.
- A **feed** and a **run's history** are the ledger's own order within the brain's partition.

### 2. The ledger port grows one read, bound to a brain

```
readRecorded(brain, selection, page) => { records: [{ id, stream, type, data, recordedAt }], hasMore, nextCursor }
  selection: everything in the brain | the streams of one run | the first and the latest message of every execution stream
  page: { cursor?, order: 'asc' | 'desc', limit, since?: time, types?: stored types }
```

- The brain is matched **exactly** on a key derived from the stream name, its name through the third `/`, never with a pattern: org and brain ids allow uppercase and underscores, SQLite's `LIKE` ignores case and `_` is a wildcard in both stores. `since` is the lower bound of a page in either order, by the store's time, which SQLite keeps to the second and PostgreSQL as the transaction's start. The list of runs reads the latest message of a stream through an index on the stream; nothing is read out of an event's JSON in SQL.
- Four indexes serve the read, so a page costs the same at any depth of any brain and of any run, in either order:
  - the brain key with the position on SQLite, and with the transaction id and the position on PostgreSQL: a brain's messages in order, from any cursor;
  - the brain key with the recorded time: where a page `since` a time starts, the first message recorded at or after it;
  - the stream with the position, and on PostgreSQL the transaction id: one run's two streams, each read in order from the cursor and merged. Without it, SQLite read a run of 100,001 messages through Emmett's unique index and sorted what it read, 24 ms for the first page newest first and 14 ms from the middle; with it, a page of that run reads in 0.24 to 0.28 ms on SQLite and 1.5 to 2.6 ms on PostgreSQL, in either order;
  - the first message of every stream, keyed by the name through its fourth `/`, the brain and the stream's kind such as `brain/acme/sales/executions/`, with the position: the list of runs walks it, so a page of runs costs the same however many messages the run logs of a brain hold between two runs. Without it, on a ledger of 598,362 messages, PostgreSQL estimated 845 runs where there were 60,000 and answered a page filtered by status with a scan of the whole table, in 122 to 126 ms against 1.4 to 3.5 ms with it. On SQLite the index is partial, the first messages alone; on PostgreSQL it holds every message with its position in its stream after the key, because the planner takes no statistics from the expression of a partial index: partial, it sorted 49,999 runs for a deep page of failed runs oldest first, in 73 ms, against 4.4 ms whole and with the table analysed. Because that key ends at the fourth `/`, no stream may be nested under `executions/`, by an adapter or the application.
- On PostgreSQL each statement matches its key with `= ANY` of a list that holds the key alone and orders by the key first, so the planner can take that order from the ledger's index on the key alone. Matched with `=`, the key of a large brain is a constant the planner deems common, and it walked Emmett's index on `(transaction_id, global_position)` instead, filtering out the messages of every other brain: a page of a brain newest first, behind a million newer messages of other brains, took 570 ms that way and 1.5 ms through the brain's index.
- On PostgreSQL the read orders by transaction id then position, as Emmett's batch read does, and keeps a **horizon** only where it is needed. A read **oldest first** follows the tail and goes on from its last record, so a message committed late below it would be skipped for good: it stays behind the oldest write still open in the ledger's own database, and a message behind it comes in a later page, once. A read **newest first** pages downward from a position and sees a late message on its next fresh read, so it keeps no horizon and shows every committed message. The horizon is the database's, not the server's: transaction ids belong to the whole PostgreSQL server, and Emmett's `pg_snapshot_xmin` is the oldest transaction open anywhere on it, so an idle write in another database on a shared server would hide new messages indefinitely. The read takes instead the oldest id among the transactions its own snapshot sees in progress, `pg_snapshot_xip`, leaving out the ids `pg_stat_activity.backend_xid` shows writing in other databases; an id in doubt stays in, one whose transaction ended between the snapshot and the lookup or one a role may not see, so the read never skips a message. Reading the oldest open id of this database from `pg_stat_activity` alone would not do: a write open when the read's snapshot is taken may end before the lookup, leaving the horizon above messages the snapshot cannot see. A transaction holds an id once it first writes, so one that only reads holds nothing back. The read never waits for the horizon: it answers at once with what lies below it, so a reader at the newest end, oldest first, cannot tell a quiet brain from one held back by a write open in its database. Only the tests wait: before each read, the PostgreSQL entry of the ledger's suite polls every 20 ms until no committed message of its own database lies behind the horizon, for at most 10 s, and fails the test past that; those tests have a timeout of 30 s. On SQLite appends are serialised and positions follow commit order.
- A **cursor is opaque** to callers and to the operations layer: an encoding of what the store needs to resume, the position and on PostgreSQL the transaction id, together with the brain key, verified on decoding. A cursor is `invalid_input` at `/cursor`, with a detail that says which: malformed when it does not decode as one, and not given by a read of this brain when it names another. The encoding is not encrypted: a caller who decodes it learns a position of the ledger, which on a shared self-hosted ledger says how much the whole ledger has written; the hosted runtime keeps one ledger per brain. Every response carries `next_cursor`, null when nothing remains, because hidden records and the filters can make a page empty while more remains.
- A page is bounded by what the store **examines** and loads, not by what it returns: it answers 1 to 100 records, 20 by default, and examines that many records without a filter; with a filter of types, or of status for the list of runs, it examines up to 1,000 records or runs and answers those that match, the first always delivered, so a rare type is reached in one page of 1,000 rather than in pages of `limit`. It loads at most 4 MiB of stored data, because one record may be 1.5 MiB, counted from the length of each stored JSON text before anything is loaded: on SQLite `octet_length(message_data)`, which reads the length alone, and on PostgreSQL `octet_length(message_data ->> 'json')`, the text inside the wrapper the ledger keeps each event in, which unpacks each large value it measures but never parses the event's own JSON. When a bound is reached the page ends with `next_cursor`, possibly with fewer records than asked or none, the way a budgeted scan answers.
- The read is added to `Ledger` and to `BrainReader`, bound to the brain in the brain binding, so a handler cannot read another brain, and to the in-memory ledger with the agreement suite that every store passes.
- The four indexes are the first the ledger adds to the store's table. When the ledger opens, it looks them up by name in the catalog, `pg_class` or `sqlite_master`, which takes no lock on the messages table, and creates only those missing, with `CREATE INDEX IF NOT EXISTS`: on PostgreSQL in Emmett's migration hook, inside the migration's transaction and its migration lock, so servers that start together build each once, then analysing the table if it created any, so the planner has statistics on the keys at once; on SQLite, which serialises writers, just after Emmett's migration on the same connections, keeping the hooks a caller passes. A start that finds them all issues no `CREATE` and is not held up by an append in flight, where running `CREATE INDEX IF NOT EXISTS` would take the table's lock, wait for the appends in flight and hold new ones behind it: with an append left open for 2 s, the statement on an index that existed took 2,013 ms and an append begun after it waited 1,821 ms, while a start that looked first took 15 to 17 ms. The one-time build of all four took 4.6 s on PostgreSQL, with the analysis, and 2.9 s on SQLite for a ledger of 1,197,287 messages, about 3.9 s and 2.4 s per million at that size, and on PostgreSQL it blocks appends for as long. The ledger's portability section changes from "no SQL" to "one SQL read per store and its indexes, nothing on the write path".
- A SQLite database the ledger opens, the hosted runtime's adapter's included, must provide what the read uses: `octet_length` (SQLite 3.43 and later), window functions (3.25 and later), the JSON functions, of which the read uses `json_each` (built in since 3.38), and partial and expression indexes (3.8 and 3.9). Each statement of the read binds at most 15 parameters, taking a list as one JSON parameter, and none needs a transaction.

### 3. Public events are a presentation of recorded events, never the records themselves

Stored events are the domain's; what a caller reads is a public event, produced by a **presenter** that the package owning the stream kind supplies, in the way primitives supply their descriptions today:

```
present(recorded) => PublicEvent | null
PublicEvent { id, at, type, summary, data }
```

- `id` is the record's opaque cursor; `at` is the event's own time, so an event just before `since` by its own clock may appear, and an event's `at` and its store time differ by the time between deciding and committing. Stream names and positions are not fields of a public event.
- `type` is a stable public name independent of the stored one. A presenter declares which stored types it presents and under which public name; the `type` filter of the feed takes one public name, which the operation translates to the stored types before the read. Today every public name equals its stored name, `execution_started`, `execution_deferred`, `execution_succeeded`, `execution_rejected`, `execution_failed`, `spec_created`, `spec_updated` and `spec_retired`, the API keeping the word execution; the two are declared apart, so a stored type renamed later keeps its public name and they may diverge. After the read the feed also keeps only the events presented under the name asked for, so two stream kinds that store a type of the same name never mix.
- A record whose stream kind has no presenter is hidden; `null` hides a record of a known kind. Snapshots and the dispatch watermark are not events, and the Node adapter keeps them out of the brain's prefix.
- `summary` is plain words with no ids, positions or slashes. A count from one hundred to five hundred and ninety-nine is written in words, in a summary and in every operation's plain words, because the internal-terms check reads those digits as a status code and a page holds up to one hundred; other counts stay digits. `data` is at most 4 KiB, by these rules: an input, an output, a record, a spec document and its schemas appear as byte sizes; the steps an input moved and the issues of a rejection appear as a count and the first five; a rejection's detail is cut at a code point; a spec's description at 300 characters; its warnings as a count. The engine's `input_applied` presents as one public event per input: the kind and key of the input, its steps so bounded, and the kinds of output it produced; the patch is never shown.
- A test over the catalog of event schemas enforces that every event type of every registered stream kind has a presenter decision, and that no public event exceeds its bound at the largest stored record.

### 4. The three operations

All three are brain-scoped queries under `brain:read`, on HTTP and MCP, with the plain-language block first as every operation has.

| Operation               | Route                                    | Input                                                                      | Output                                                             |
| ----------------------- | ---------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `list_executions`       | `GET /executions`                        | `primitive?`, `name?`, `status?`, `limit?`, `cursor?`                      | `{ executions: [ListedRun], has_more, next_cursor }`, newest first |
| `get_execution_history` | `GET /executions/{execution_id}/history` | `cursor?`, `order?` (oldest first by default), `limit?`                    | `{ events: [PublicEvent], has_more, next_cursor }`                 |
| `list_brain_events`     | `GET /events`                            | `cursor?`, `since?`, `type?`, `order?` (newest first by default), `limit?` | `{ events: [PublicEvent], has_more, next_cursor }`                 |

- `ListedRun` is the execution as `get_execution` shows it, without its output, its record and the detail and issues of a rejection: id, primitive, name, spec version, status, who started it, when it started, when it finished, and of a rejection its reason, kind and because, without the detail. Runs are ordered by the position of their first start, which is unique, so two runs started in the same millisecond keep a fixed order across restarts.
- The list folds the first and the latest message of each execution stream, which is all the list of runs reads. When the latest message is a start, the listed run shows that start, as `get_execution` does. A run started again under the same id and since finished lists with its first start, its time, its caller and its spec version, while `get_execution` shows the latest: a finish carries no start, and the latest start lies between the two messages the list reads. Showing it would take a third message of every run, the latest start, from the ledger's read, or a read model; neither is built.
- The `status` filter is answered in the store from the latest message's type. The `primitive` and `name` filters are applied by the operation after decoding each first message, within the page's bounds, so a filter that matches rarely returns short or empty pages with `next_cursor` until it finds matches.
- `get_execution_history` merges the run's execution stream and, for a workflow run, its run log, by each record's own time, then stream, then stream version, within a page. A page is one read of the ledger's selection of the run, which reads both streams from one cursor and so pages on one ledger position across both; across pages the events follow the ledger's order, and an event whose own time is earlier than one on the page before stays on its own page. Within a stream the ledger's order is the stream's version order, so the merge keeps it without reading the version. Where the hosted runtime keeps a run's log in the run's isolate, the two streams share no position, and that step reads each stream from a cursor of its own, the page's cursor holding both, and merges them by their own time across pages as well. The history of a workflow run can show it finished while `get_execution` still says started, because the run log and the run's record are two writes (decision 0001, invariant 14); the record follows within the retry of the settle output.
- `list_brain_events` reads the brain's whole partition: specs created, changed and retired, runs started and finished, workflow inputs applied where the run logs live in the partition, and whatever a later decision adds. On the hosted runtime the run logs live in the runs' isolates, so the feed there shows a run's start and finish, and `get_execution_history` reads the run's own log.
- What the feed cannot show, and the records say so: the brain's own creation, update and retirement, which live in the org's registry stream.
- **Retired brains stay readable.** Every brain-scoped query may read a retired brain and every command is refused with the reason `update_brain` already uses for one. The brain registry port answers a status, active, retired or unknown, instead of a boolean, the dispatcher applies the rule by the operation's kind, and the in-memory registry follows. A brain's history survives its retirement.
- `limit` and `has_more` follow the list convention of the OpenAI API; `cursor` and `next_cursor` are the opaque continuation that Slack's and Notion's APIs use; `since` follows GitHub. Output envelopes keep noun keys, `executions` and `events`, as `specs` and `brains` do today.

### 5. What is not in this decision

A live tail of the feed over Server-Sent Events, resuming from `Last-Event-ID` as the opaque cursor, is additive on this design and waits for a change signal per store. An org-wide feed, counts and activity windows, retention and what a cursor older than the retention horizon answers, a link from a workflow's child run to its parent, encrypted cursors, and a read model for runs when the measurement demands it are later decisions.

## Consequences

- The list, the history and the feed are exact reads of the ledger: no lag, no rebuild, no projection to version. The ledger gains one SQL read per store and four indexes, and nothing on its write path.
- The cost is at read time and bounded by the page. On a ledger of 1,197,287 messages holding a brain of 100,000 runs, every 200th run with an input of 256 KiB and an output of 1 MiB, and a run of 100,001 messages, an unfiltered page reads in 1.1 to 3.1 ms on PostgreSQL and 0.2 to 1.2 ms on SQLite, at any depth of the brain or of that run and in either order, and in up to 9.2 ms on PostgreSQL when it loads a run of 1.25 MiB; a page of runs filtered by status reads in 2.6 to 4.9 ms on PostgreSQL, 11 ms when it loads such a run, and in 2.5 to 3.5 ms on SQLite, which examines its 1,000 runs at once; a page of the brain, of its runs or of that run, behind a million newer messages of other brains, reads in 1.2 to 2.2 ms on PostgreSQL and 0.2 to 0.4 ms on SQLite; a name filter that matches rarely costs pages, not time. The ledger's README records every page, and `measure.ts` at the root of the ledger package records them again.
- Nothing about a run leaves its brain: the brain key is matched exactly, the read is bound in the brain binding, and a cursor is verified to belong to the brain that reads it.
- The engine's run log becomes readable by people through its presenter only; its patches stay internal, and the engine's state formats and upcasters stay the only place that knows them. The run store takes the brain's address with the execution id, because execution ids are unique within a brain only.
- A primitive that keeps its own log of a run brings a presenter for it; presenters are passed to the operations the way primitives are passed to `makeSpecOperations`, so `@beonauto/brains` keeps depending on operations only.
- New code goes in new concept folders: the ledger has eleven files directly under `src` and the specs operations folder seventeen, both already at the rule's edge.

## Verification the build must include

- The partition read never returns another brain's message: a brain named with uppercase, one with an underscore, and a prefix lookalike all read only their own.
- On PostgreSQL, pages oldest first, of the brain and of its runs, taken while an earlier append's transaction is open and then after it commits deliver every message exactly once; a read newest first shows a message committed after that append while it is still open; and a write left open in another database of the same server hides nothing. On SQLite appends are serialised, so positions follow commits.
- Paging: no duplicate and no gap across pages while appends continue, in both orders; each bound ends a page with `next_cursor`; a filter of types examines up to 1,000 records, and a page it leaves empty still carries `next_cursor`; a malformed cursor and another brain's cursor are `invalid_input` at `/cursor`, each with its own detail.
- A start that finds the indexes issues no `CREATE`, and on PostgreSQL is not held up by an append left open.
- Ordering of runs: a caller-supplied id, a hashed child id and a run started twice all take their place by first start; the order is fixed across restarts.
- A run whose input or output holds U+0000 lists, filters and reads on both stores.
- Every event type of every registered stream kind has a presenter decision; the largest stored record of every kind presents within 4 KiB; a stream kind without a presenter is hidden.
- The plain words pass the internal-terms check, and the three operations answer through the real server over HTTP and MCP, including on a retired brain, where a command is refused.
- The in-memory ledger passes the same agreement suite as both stores for the new read.
- The measurement: a ledger of a million messages with a brain of 100,000 runs, inputs and outputs at their largest, a run of 100,001 messages, and the brain behind a million newer messages of other brains, with the time of a page of each operation recorded in the ledger's README by its `measure.ts`; the bar for staying without a read model is 50 ms for an unfiltered or status-filtered page.

## Build

1. `@beonauto/ledger`: the brain-bound recorded read in both stores, the indexes and their creation, the opaque cursor, the three bounds, the shared behaviour suite and the measurement. `@beonauto/operations`: the read on `Ledger` and `BrainReader`, the in-memory ledger, the brain registry's status and the dispatcher's rule for retired brains, the `PublicEvent` schema, the presenter type and the paging fields. Starts now, on main.
2. `@beonauto/specs`: `list_executions`, the presenters of execution and spec registry events, `get_execution_history`. `@beonauto/brains`: `list_brain_events` taking presenters as a parameter, and the brain registry answering a status. Starts after 1.
3. `@beonauto/workflow-engine` and the orchestration primitive: the presenter of `input_applied`, and the run store keyed by brain and execution, once the Node adapter writes run logs under the brain's prefix; on the hosted runtime, a cursor per stream for the history of a run. Waits for the machine.
