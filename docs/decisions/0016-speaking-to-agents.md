# 0016 — Speaking to agents: what the brain says when an agent connects, measured against the servers that do it best

**Status:** accepted (2026-10-07), with the amendments from the build at the end

## Context

Verified against `origin/main` at 40e4f82 and the branch `docs/recall-guidance` at 62ab044; every figure from another server was measured on 2026-10-07 from the source its row names. Everything an agent reads from the brain over MCP, the instructions, the twenty-one tool descriptions and schemas, the definition type texts, the refusal and outcome words, was written from our own judgement. On 2026-10-07 a person used Claude Desktop on a local brain, and six episodes show where that text fails: (1) asked "what is brains?", the agent recited the brain record's fields and id rules; (2) asked to create a brain for meetings, it answered with paragraphs on id immutability and event publishing; (3) asked to use Slack, it could not know the tool server's name; (4) asked to make the brain remember what it posted today, it built a recall function as a log every workflow must write into, having nothing that said what a recall function reads; (5) it quoted `specs`, `executions` and `primitive` to a non-technical person; (6) a 401 from a tool server and an empty channel history it diagnosed well from the refusal words, the one surface that worked. Since then main gained per-endpoint instructions, brain descriptions trimmed of rules and `list_tool_servers`; the branch adds a recall sentence to the instructions and a recall description saying the history already holds every run's output, which this record adopts. The episodes are evidence of failure; the design below is derived from the comparison.

## Decision

### 1. The standard: each kind of knowledge has one surface, as the generated-docs servers keep it

| Knowledge                                                                                                                                                 | Surface                                                                                                             | Set by                   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| What a brain is, each function type's purpose, the connection's scope, the orders the server requires, one context rule, the words to use with the person | the instructions, built per connection, always in context                                                           | GitHub, Supabase         |
| What a tool does, when to use it and when not, what each argument means, the caveats to know before calling, the alternative tool by name                 | the description, 3 to 8 sentences; argument rules in the schema's descriptions and keywords                         | GitHub, Linear, Sentry   |
| How a definition is written: format, examples, bounds; how a common task is done                                                                          | a guide, read on demand through a tool, also listed as a resource                                                   | Sentry, Supabase; GitHub |
| A recipe the person starts                                                                                                                                | a prompt, the same text as the guide                                                                                | GitHub                   |
| Why a call was refused and what to change; what a success did and what comes next                                                                         | the refusal and outcome words, as today                                                                             | Sentry                   |
| Configured facts: the models, the tool servers, the brains                                                                                                | the answers of `list_models`, `list_tool_servers`, `list_brains`, and one generated sentence in the reasoning guide | GitHub, Supabase         |

Nothing is said twice; a description never carries a format, a refusal catalogue or an order across tools; no text tells the agent how to behave beyond when to use a tool and, in the instructions, the words to answer in, which GitHub's project rules also shape. Where the leaders disagree I chose the generated-docs side, because drift between what the person reads and what the agent reads is what episodes 1, 2 and 5 are.

### 2. The tool list follows the key, and the instructions name only what is listed

A connection lists the tools its key may call: a key with `brain:read` alone sees the queries, as GitHub's `/readonly`, Linear's read-only endpoint and Supabase's `read_only` serve, and as the specification allows by authorization. The factory already builds a server per request from the caller (`packages/api/src/mcp/mcp-server-factory.ts:122-166`, `mcp-routes.ts:40-55`); the filter is the permission check of `packages/operations/src/caller/permission.ts` applied to each registration, and `instructionsFor` is built in the same closure from the tools listed, so a read-only connection reads instructions without `create_brain`. The three endpoints stay as they are.

### 3. The instructions, per endpoint

Built by `instructionsFor` from the tools listed and the definition types the server runs, a function-type sentence only for a type it runs, the models sentence only where `list_models` is listed, the workflow sentences only where `send_execution_event` is, and never a tool the connection does not list. The orders and the context rule are GitHub's and Supabase's practice; the sentence on words keeps a clause on ids, since the tutorials ask for a run's id. On `/mcp` with every tool:

> A brain is the complete system for a business responsibility. It holds the functions that do its work and the workflows that coordinate them, and it keeps every run with its result as its history. A reasoning function has a prompt and calls a language model. A computation function runs a program on its input and gives the same output every time. A recall function keeps a view folded from the brain's own history, every run's start and ending with its result when it succeeded and fit, the definitions saved and every event published to the brain, never a run's input or the tool calls it made, so nothing has to write into it. A workflow runs functions in steps, waits for input and can start on a schedule or on an event. This connection acts in the caller's own org: list_brains shows its brains and create_brain makes one, and every tool inside a brain takes the brain's id as brain. The tools call a definition a spec, a run an execution and a definition's type its primitive: inference for a reasoning function, computation for a computation function, recollection for a recall function and orchestration for a workflow. Before writing a definition, read its format with get_guide, which also holds the recipes: first-brain, remember, give-tools and schedule. A reasoning function names a model that list_models lists and may name tools that list_tool_servers lists. A workflow run answers started and ends later: read it with get_execution until its status changes, and give a run that waits for input its event with send_execution_event. Runs, history and events come a page at a time; read on only when the person needs more. When you tell the person what happened, say what was done and what they can do next, in the words of brains, functions, workflows and runs, not in the tools' names, fields or rules; give an id or a status only when the person needs it to act, as a run's id they will return to. ### 4. Tool descriptions and annotations

A description says what the tool does, when to use it and when not, what each argument means in a clause, the caveats to know before calling, irreversibility, work that finishes later, a run never run again under its id, and the alternative tool by name; the order across tools belongs to the instructions. The argument rules go into the schema's descriptions and keywords, as Linear's "Append-only; existing labels are never removed" and GitHub's `method` text do; the refusal catalogue goes, since the refusal words say why with the remedy; the format and the examples go to the guide, as Sentry keeps its examples short and sends the agent to `get_doc`; and no sentence instructs behaviour. The list of types in `create_spec` is generated from the registered primitives, each `Primitive` carrying the name of its guide in its contract (`packages/specs/src/primitive/primitive.ts`). Three rewritten descriptions:

`create_brain`: > Creates a brain in the org for one business responsibility, such as reviewing campaign briefs or keeping a team's meeting notes, and returns it, active and empty: its functions and workflows come next. Use it when the person wants a new brain; list_brains shows the brains that exist, and an id that is taken or retired is refused. `brain` is the id every tool inside the brain takes, `name` is what people call it, and `description` says what the brain is for, in the person's words.

`create_spec`, as served with four types: > Saves a new function or workflow definition in the brain from its document and returns it without running it. Use it once the person has agreed to the definition; update_spec changes one that exists, and a name is never reused in a brain. `primitive` is the definition's type and `name` is how workflows and other tools refer to it: inference, a reasoning function, guide reasoning-function; computation, a computation function, guide computation-function; recollection, a recall function, guide recall-function; orchestration, a workflow, guide workflow. `source` is the whole document in that type's format, which get_guide gives. A document that does not fit its format is refused with the line and what is wrong, and nothing is saved.

`execute_spec`: > Runs a function or workflow with an input and records the run. A function answers its result; a workflow answers started with an execution_id unless it ends before its first wait, and get_execution shows how it ended. Use it to run a saved definition at the person's request; a workflow's steps call it the same way. `primitive` and `name` say which definition, `input` is the value it takes, {} when left out, as the input_schema get_spec shows, and `execution_id` is optional: give the same id to retry safely, since a run that ended or waits answers as it stands and one that failed runs again. A reasoning function that names tools may change something outside the brain, so a run of one that did not succeed is never run again under its id; get_execution_history shows what it called.

Annotations follow Supabase's completeness: `readOnlyHint` and `openWorldHint` as today; `destructiveHint` from a new declaration on the definition, `irreversible`, true for `retire_brain`, `retire_spec` and `cancel_execution`, or from `mayChangeOutside`, true for `execute_spec` while a tool server is configured; `idempotentHint` true for every query and for a command declared `repeatable`, `update_brain`, `update_spec`, `retire_brain`, `retire_spec` and `cancel_execution`, whose repeat records nothing, false for `create_*`, `execute_spec`, `publish_event` and `send_execution_event`; the HTTP method decides nothing. The api README's table is corrected and pinned by test.

### 5. Guides: one complete public page per definition type, served through a tool and listed as resources

A guide is a Markdown text the server carries. `terminology` is derived from the terminology page's tables, the capabilities with their descriptions and the terms, stripped of markup and links and naming only the function types the server runs. `reasoning-function`, `computation-function`, `recall-function` and `workflow` are each the complete public reference page of a type the server runs, with relative links resolved to their published addresses or removed, the recall page as the branch writes it with the view over one function's runs second; the public reasoning page is made complete first, taking from the engineering page everything the served description holds today, `today` and `now`, the filters, the one-system-block rule and `provider_options`, so one page is the source for the person and the agent, as GitHub, Playwright and Sentry keep one. The configured facts the reasoning description generates today, the providers, the aliases and whether tool servers are configured (`primitives/inference/src/primitive/reasoning-description.ts:36-55`), are not deleted: `get_guide` appends them to `reasoning-function` as one generated sentence, "On this server…", built from the same offer, and `list_models` and `list_tool_servers` answer them in full. The four `*-description.ts` texts then go. `first-brain`, `remember`, `give-tools` and `schedule` are the recipes. The MCP layer serves every guide on every endpoint through one read-only tool, `get_guide`, whose `guide` argument is an enum of the names, Sentry's `get_doc` and Supabase's `search_docs` pattern, since documentation reaches the agent through a tool at every server where it reaches it at all: "Reads one of the brain's guides: what its words mean, how each kind of definition is written, with its format, examples and bounds, and how the common tasks are done. A format guide is read before a definition of that type is written, and a recipe before the task it names." The same guides are listed as resources, `guide://<name>`, `text/markdown`, annotated for the assistant, as GitHub lists repository content, for clients that let a person or a model read them directly; both answer the same text. The server refuses to start without the guide of a type it runs, as it refuses an operation without plain language.

A recipe is written for the agent in steps that name tools, what to ask the person and what to tell them, and names its format guide. `remember`: ask what the brain should remember and which function's runs hold it; say that a view holds what a run answered, never what it was given or the tools it called, so a function whose job is to post must answer what it posted; find or create the function; read `recall-function`; write a view over that function's succeeded runs whose `answer` gives what was asked; show it, save it with `create_spec`, run it once it answers, and if it is still being built, try again in a moment, since a new version rebuilds; tell the person it remembers from the brain's whole history on and sees nothing done outside the brain. `give-tools`: `list_tool_servers`, then a reasoning function naming `server/tool`, and when no server is listed, what whoever runs the server sets up. `schedule`: a workflow with a `schedule` from the `workflow` guide, then its runs read with `list_executions`. `first-brain`: the quick start's and the Studio's first prompt, served by the brain itself.

### 6. Prompts: the recipes the person starts

The four recipes are also MCP prompts, GitHub's pattern and the one surface a person reaches from the client's menu without pasting: `first-brain`, "Create your first brain", no argument; `remember`, "Make the brain remember something", argument `what`; `give-tools`, "Give the brain tools", optional `server`; `schedule`, "Run a workflow on a schedule", arguments `workflow` and `when`. A prompt answers one user message, the recipe with the person's words filled in, followed by the format guide it needs as an embedded resource. The quick start and the engineering reference point at the prompts; the Studio's owner is told that its first-run prompts are now served. Linear and Notion serve recipes through tools alone, so the agent's path is `get_guide` and the prompt is the person's.

### 7. The wire names

Every text uses the product's words for concepts and the tools' own names, `spec`, `primitive`, `execution`, `inference`, `orchestration` and `recollection`, only when naming a tool, a field or a value, with the one mapping sentence in the instructions and no sentence about renaming. Guides, prompts and resources are named in product words, so the rename (0007) touches them nowhere; when it lands, the mapping sentence is deleted and the tool names in the texts change with the tools.

### 9. What this record does not decide

Client-side skill packages, plugins or files an agent would install, as Stripe and Supabase do: every surface here is served over MCP alone. The rename (0007). Whether a run's input and its tool calls become events a recall function can fold: agents will keep expecting it, since "what it posted" is a tool call and a view can only hold what the function answered; the texts say what folds today and a later record decides. A catalogue pair as Sentry's, should the tools outgrow the bound. Search over the guides, icons, MCP Apps and elicitation before a destructive call, which Supabase does and Claude's client does not yet support. The descriptions of a brain's functions offered as tools (0013) follow §4 but belong to that record.

## Consequences

- A connection to `/mcp` receives under 2,000 characters of instructions and 22 descriptions under 800 characters each, in place of about 90,000 characters of repeated format text; a format is read once, for the type being written, as the agent reads a Sentry page.
- One complete public page per definition type, the source for the person and the agent, carried in the image; the four `*-description.ts` texts go, the configured facts stay as a generated sentence, and the bounds the pages state are checked against the code by test.
- A read-only key's connection lists only what it may call, so a client's tool picker and the instructions tell the truth before the first call.
- `retire_brain`, `retire_spec` and `cancel_execution` prompt for confirmation in clients that honour the hints, and `execute_spec` does while tools are configured.
- The cost: a 22nd tool; the image grows by five pages; the instructions are built per request instead of once; recipes are text to keep true as tools change, pinned by the replay test.
