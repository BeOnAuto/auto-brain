# 0024 — The runtime as a service and as a client: one catalog and its OpenAPI document, tool servers of two kinds reached through five tools, and a signed-in person's identity

**Status:** proposed (2026-10-13), designed against `origin/main` at 0e013a96 with the prediction documentation (#172) read as merged, and checked against that code the same day; answers two of the questions decision 0003 §8 left open, a person-backed credential and "the other direction, publishing the brain's own API to a gateway as a connector"; amends 0003, 0007, 0016, 0018, 0021 and 0023 as section 12 says; not built.

## Context

A company that governs what its agents may reach puts an agent gateway between every agent and every system. One such gateway was asked, through the key an operator of this runtime already holds for it, what it is: its server names itself `gateway` 0.1.4; its instructions say it "fronts the systems your organization has connected behind one GraphQL schema", that "everything is reached through these tools — `search`, `introspect`, `validate`, `dry_run`, `execute` — never by calling the underlying services or the GraphQL endpoint directly", and that "access is policy-governed", a denial answered by a token "you can submit as an access request"; its tools list five, and its connected scopes were a chat product, three analytics and document products and its own bootstrap service. Its vendor's documentation says how a system gets behind it and how a person's identity travels through it:

- "Your domain model lives in a service catalog and is accessed by agents through the search service"; "You'll be able to add first party and third party APIs alike to the catalog"; an existing GraphQL subgraph is added as it is, and a REST API through a Connectors subgraph that its Factory generates from "an OpenAPI or Swagger spec, or a link to the API's documentation" ([Introducing GraphOS Agent Services](https://www.apollographql.com/blog/introducing-graphos-agent-services), [Introducing GraphOS Factory](https://www.apollographql.com/blog/introducing-graphos-factory)). In its preview, a service outside its catalog is added by asking the vendor ([Connect Services](https://www.apollographql.com/docs/graphos-agent-services/guides/connect-services)): "The base URL must be HTTPS"; "keep the environment variable name for the API key"; "Turn **Per-user OAuth** on only when each person is required to connect with their own account".
- "Agents never hold upstream credentials; their identity is brokered by Agent Services"; "When a person is signed in, their identity travels with the request, brokered from the MCP client all the way to your upstream systems. Credentials are exchanged per person, so the agent reaches your system under the identity of the person that asked." Fields carry tags, and rules say per actor and client whether a field is allowed, masked, denied or requestable.

The owner's questions, in the order they were asked, and what this record answers to each:

1. Must the runtime work both behind such a gateway and connected to directly, with the same experience? Yes to both routes; the experience is the same where it can be, the operations, and differs where the gateway adds what the runtime does not do, governance per field and a person's own credentials on every system.
2. Must the runtime mirror the gateway's five tools over its own operations, so that an agent's client is not flooded with tools? No: the runtime's own operations stay one tool each, and the five tools are the shape of the runtime's own front over the playbook's tool servers, where tens of servers and hundreds of tools do live.
3. Must the runtime reach HTTP APIs directly, not only MCP servers? Yes: a tool server is of two kinds, and a function names a tool of either the same way.
4. Must the five tools execute, not only read? Yes: in a company without a gateway, the runtime's own governance, the caller's permissions, the operator's list and the ledger, is what a person acts under.
5. Is this the best architecture? The runtime is a service to a gateway and a client of tool servers, and never a gateway for persons; everything else follows from one catalog.

The code today, read on 2026-10-13:

- **One catalog, two surfaces.** Every operation is a registration with a scope, a kind, a route and its input as JSON Schema 2020-12 (`packages/operations/src/definition/registration.ts:12-30`, `json-schema.ts:12-15`), served as an HTTP route under `/v1/orgs/{org}` or `/v1/orgs/{org}/playbooks/{playbook}` (`packages/api/src/operations/route-table.ts:13-16`) and, unless `servedOverHttpAlone` is set (`registration.ts:32-50`), as an MCP tool (`packages/api/src/mcp/mcp-server-factory.ts:61-65`). There are 31 registrations under 30 names, 5 served over HTTP alone; `/mcp` lists 26 tools, 25 of them operations and one `get_guide`, which is not a registration (`mcp-connection.ts:64`), in 39,748 of the 40,000 bytes its bound allows (`packages/server/src/mcp/served-schemas.test.ts:89-93`, `packages/api/src/bounds/served-bounds.ts:17-21`). No output schema is kept on a registration, and no OpenAPI document exists; the only JSON Schema produced is the input's (`registration-parts.ts:77`), the playbook argument's and the configuration file's.
- **Tool servers are MCP servers.** The setting `mcp_servers` takes an `http` or `stdio` entry bound to an org and playbooks, with `allowed`, `testable`, `record_content`, `request_id`, secrets by reference and an `auth` block of client credentials (`packages/mcp/src/settings/server-entries.ts:31-101`, `entry-checks.ts`). A function names `server/tool` (`packages/mcp/src/names/tool-reference.ts:32-37`), the one call path is `ToolAccess` (`packages/mcp/src/access/tool-access.ts:29-42`), and every call is bounded, scrubbed and recorded (`bounds/call-bounds.ts:4-19`, `bounds/secrets.ts`, `calls/recorded-calls.ts:42-86`). Decision 0021 §6 says "No direct HTTP. MCP stays the transport; a system without a tool server is reached through one." (`docs/decisions/0021-asking-a-system.md:229`). An agent finds and tries tools through two operations, `list_tool_servers` and `test_tool_call`, in `packages/mcp/src/listing/` and `tool-tests/`; a test may call only a tool its server marks read-only or the operator lists as testable (`tool-tests/testing-guard.ts:5-7`), needs `playbook:write`, and records `tool_test_*` facts on a stream of its own (`tool-test-events.ts:10-14`).
- **A caller is a key.** `abk_<id>_<secret>` keys, stored as digests with an org, permissions and playbooks (`packages/identity/src/keys/api-key.ts:29-37`), verified in constant time (`verify-key.ts:13-16`), or the local developer on loopback (`access/authenticator.ts:25-39`). The MCP hand-off already shapes a caller as OAuth-style `AuthInfo`, `clientId` the caller's id and `scopes` its permissions (`packages/api/src/hand-off/caller-hand-off.ts:37-44`). No route serves OAuth protected-resource metadata, no challenge names one, and nothing verifies a token a third party signed. A fact records who acted as one id string in its context, `by` (`packages/operations/src/ledger/context.ts:49-69`, decision 0023 §3): a key's id, `local`, or `playbook:<id>` (`packages/operations/src/caller/caller.ts:21-29`). A workflow run keeps a copy of its caller's whole identity and dispatches its later calls as that copy (`capabilities/coordination/src/runs/run-attributes.ts:9`, `packages/server/src/workflows/host-work.ts:41-45`).

### What the standards require of a server behind an OAuth client

The MCP authorization specification, at the revision the runtime negotiates ([2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization); `served-schemas.test.ts:74`), makes a protected MCP server "an OAuth 2.1 resource server". "MCP servers **MUST** implement OAuth 2.0 Protected Resource Metadata ([RFC9728](https://datatracker.ietf.org/doc/html/rfc9728))", whose document "**MUST** include the `authorization_servers` field"; the server "**MUST** implement one of the following discovery mechanisms", the metadata URL in `WWW-Authenticate` on a 401, or the well-known URI at the endpoint's path or at the root, and "**SHOULD** include a `scope` parameter in the `WWW-Authenticate` header"; "MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience, according to [RFC 8707 Section 2](https://www.rfc-editor.org/rfc/rfc8707.html#section-2)"; "Invalid or expired tokens **MUST** receive a HTTP 401 response"; on insufficient scope the server "**SHOULD** respond with" a 403 carrying `error="insufficient_scope"`, `scope` and `resource_metadata`; and "The MCP server **MUST NOT** pass through the token it received from the MCP client" to an upstream. Authorization servers "**MUST** provide at least one of" OAuth 2.0 Authorization Server Metadata ([RFC8414](https://datatracker.ietf.org/doc/html/rfc8414)) and OpenID Connect Discovery 1.0; client registration, by Client ID Metadata Documents, pre-registration or dynamic registration, is the client's and the authorization server's. An agent gateway that brokers a person to an upstream is an OAuth client of that upstream, and the same metadata serves it.

## Decision

### 1. One catalog, and the three ways out of it

The operation catalog is the runtime's one contract. A registration gains its output beside its input, `output: JsonSchemaDocument`, produced from `definition.outputSchema` as `input` is from `inputSchema` (`registration-parts.ts:77`); an operation served over HTTP alone keeps what it has, a JSON answer with its schema, or a streamed answer with its media type and no schema (`definition.ts:91-94,147-161`). Three projections read the registrations and nothing else: the HTTP routes (`operation-routes.ts:82-89`), the MCP tools (`mcp-server-factory.ts`) and, new, the OpenAPI document of section 2. A test holds that the three agree: every registration has one route, one tool unless served over HTTP alone, and one operation in the document, and the description is the same text in all three. The instructions and `get_guide` are the MCP surface's own, as decision 0016 made them, and stay outside the catalog; the guides are served over HTTP as well, as section 2 says.

Nothing moves between the surfaces. The HTTP routes serve every operation, uploads and the trainer's routes among them; the MCP endpoints serve what they serve today plus section 5's tools and minus the two they replace; the document describes the HTTP surface whole.

### 2. The OpenAPI document

`GET /v1/openapi.json` answers the document, generated from the catalog at start and kept in memory, served without a key as `/health` and the landing page are, since it names no secret and is the documentation of the surface it describes; the path joins `publicPaths` (`packages/api/src/middleware/middleware-chain.ts:11`). It is OpenAPI 3.1.1 with `jsonSchemaDialect` of JSON Schema 2020-12, so every input and output schema the catalog produces is a Schema Object as it is, with its `$defs` kept inside it as `selfContainedSchemaOf` keeps them (`packages/api/src/tools/tool-schema.ts:69-72`) and an `$id` of its own, `https://on.auto/schemas/runtime/<operationId>/input` or `/output`, so that a `$ref` of `#/$defs/…` resolves within that schema and not against the document.

- `info`: title `Auto Runtime`, version the server package's version, description one sentence kept beside the generator. `servers`: `[{ url: "/v1" }]`, relative, so the document is true behind any host or gateway; the paths are the catalog's own form, `/orgs/{org}` and `/orgs/{org}/playbooks/{playbook}` (`packages/operations/src/catalog/catalog.ts:13-16`), not the route table's, which carries `/v1` already.
- `paths`: one path item per route, `{org}` and `{playbook}` as path parameters with their patterns (`packages/operations/src/caller/identifiers.ts:3,5`), one operation per registration: `operationId` the operation's name, and for the one name registered at both scopes the org twin's id is `<name>_in_org`, as the code names it (`list-tool-servers-in-org.ts`); `summary` the title; `description` the tool's description, the same text; `tags` one per resource, `playbooks`, `models`, `definitions`, `runs`, `events`, `analytics`, `interactions`, `tool-servers`, `prediction`; `parameters` the path fields and, for a query by `GET`, the input's other fields as query parameters with their schemas, decoded as the `strings` encoding decodes them (`codecs.ts:42-58`); `requestBody` for a command and for a query by `POST` (section 5), `application/json` with the input's schema less its path fields, or the streamed media type with the byte bound in its description (`http-body.ts:25-28`); `responses` the success status with the output's schema or the streamed media type, each declared reason at its status with `application/problem+json`, and the responses the operations share, written once under `components.responses`: 400, 401, 403, 404, 405, 413, 415, 422 for an input the codec refuses (`codecs.ts:21-30`) and 500 for every operation, and 409 for a command on a retired playbook (`authorization.ts:78-79`) for the playbook commands.
- `components`: the problem document's schema, the shared responses, and the security schemes: `bearer`, type `http`, scheme `bearer`, whose description says a key or, where section 7's providers are configured, a token of one of them; with providers, one `openIdConnect` scheme per provider naming its discovery URL; `security: [{ bearer: [] }]` on every operation. The problem document gets an Effect schema in `packages/api/src/problem/`, from which its TypeScript type, its table of reasons and statuses (`problem.ts:33-69`) and its JSON Schema all derive, so the document and the code cannot drift.
- `x-` extensions: none. What the specification cannot say, a byte bound or a cursor's meaning, the description says.
- **The guides over HTTP.** Each guide the shelf holds (`packages/api/src/guides/guide-shelf.ts`) is served at `GET /v1/guides/{guide}` as `text/markdown`, without a key as the document is, byte for byte the text the MCP resource `guide://<name>` serves; the document lists the route under a `guides` tag with the guide's name as an enumerated path parameter, so an agent gateway's search finds "the guide to prediction functions" and an agent behind it reads what an agent on MCP reads. The instructions stay MCP's, since they are built per connection from the tools it may use; on the gateway route the document's top-level description, one paragraph kept beside the generator, says what the instructions say first.

The document is for machines: an agent gateway's generator reads it, a company's tooling reads it, a client library can be built from it. The public reference page stays the page for people and links to the document's path on a running server; the engineering reference page (`docs/engineering/reference/http.md`), a second description of the same surface that lacks prediction functions, goes, and its index entry points at the public reference and the document.

Tests: each guide is answered over HTTP as `text/markdown` without a key, equal to its MCP resource, and listed in the document; the document validates against the published OpenAPI 3.1 schema, kept as a fixture, with a full JSON Schema 2020-12 validator as a development dependency of the api package, since the runtime's own compiler takes a bounded dialect without `unevaluatedProperties`, `if`, `dependentSchemas` or `$dynamicRef` (`packages/definitions/src/document/schema-shape.ts:20-40`) on purpose, for documents a person writes; every registration appears once with its description; the input schema of each operation equals the registration's less its path fields, under its `$id`; the document's text passes the vocabulary guard; a client built from the document by a generator creates a playbook and runs a definition through it; its bytes are measured and stated in the api README.

### 3. The runtime's own MCP endpoint keeps one tool per operation

The three endpoints, the listing that follows the key, the instructions, the guides as resources and the plain-language results stand as decision 0016 set them. Section 5 adds five tools and removes two: `/mcp` lists 29 (26 − 2 + 1 + 4, the org twin of `search` replacing the playbook one as today's listing twin does, `mcp-server-factory.ts:186-192`), the org endpoint 8, the playbook endpoint 23 (20 − 2 + 5); the count bound of 32 holds. The byte bounds move: `/mcp` 48,000, the org endpoint 12,000, the playbook endpoint 40,000. The reason the bound is bytes stands, "a listing is what an agent's client loads whole and holds for the connection" (0016, amendment of 2026-10-11); the figures move because the clients that load it have changed since, as the Context's sources say: a listing's cost in current agent clients is paid when a tool is used, not per connection. The bound keeps a listing within what a client without deferral loads at about 12,000 tokens, which the build measures and states in the api README beside the figures.

### 4. Tool servers of two kinds

The setting `mcp_servers` becomes `tool_servers` (environment `TOOL_SERVERS`), and the package that reaches them, `@on.auto/mcp`, becomes `@on.auto/tool-servers`, since it no longer speaks MCP alone. An entry's `type` is how the runtime speaks to it:

- `mcp`: a remote MCP server over Streamable HTTP, `url`, `headers`, `auth`, as `http` is today.
- `stdio`: a process, `command`, `args`, `env`, as today.
- `openapi`: an HTTP API described by an OpenAPI document, 3.0 or 3.1; a Swagger 2.0 document is refused. `document` is the `https` URL the document is read from at start, or a path under the configuration file's directory; `base_url` overrides the document's first server when given and is required when the document names none; `headers` and `query_params` carry credentials by reference, as a model gateway's do (`capabilities/reasoning/src/settings/gateway-settings.ts:37,84`); `auth` is the client-credentials block MCP entries have, with one difference the build must make: the token source discovers the token endpoint from the pinned issuer's own metadata, RFC 8414 or OpenID Connect discovery, through the SDK's hook for a known authorization server, because today it discovers through the server's protected-resource metadata and falls back to the server's origin (`packages/mcp/src/connections/token-source.ts:58`), which a REST API has none of. A 401 with an `auth` block mints once more before it fails, as it does for MCP (`token-source.ts:70-74`); no `_meta` is sent over HTTP.

Every entry keeps `org`, `playbooks`, `allowed`, `record_content` and `request_id` with the meanings they have (`entry-checks.ts`, `tool-lists.ts`); `request_id` names a response header. `testable` goes, for the reason section 5 gives, and with it `ToolAccess.testing` and the `reportUntestable` option (`packages/mcp/src/access/tool-access.ts:23,31`), the untestable noting (`tool-tests/testing-guard.ts:16-26`, `access/linked-access.ts:28`) and the log line that said a server could be tested nowhere (`packages/server/src/logging/mcp-server-logging.ts:13`, `composition/served-tools.ts:35`). A function names a tool of either kind as `server/tool` and nothing in a function says which kind it is.

**The bridge.** An `openapi` entry is a `ServerLink` like the others (`connections/server-links.ts:18-24`) over the connection contract `call`, `listTools`, `closed` and `end` (`connections/mcp-connection.ts:20-25`), so the rest of `ToolAccess`, the bounds, the scrubbing and the recording are the same code. What changes to admit it: the settings union and each switch on `type` (`settings/mcp-settings.ts:43`, `server-links.ts:43,130`, `bounds/secrets.ts:75-76`, `entry-checks.ts:39-43,188-218`), the opener (`server-links.ts:36-66`), the failure mapping that knows only the SDK's error classes (`connections/server-failures.ts:78-86`), the token source, the "MCP server" words, and the image, which copies the package by name (`packages/server/Dockerfile:16,65`); the observing fetch is reused as it is.

At start the document is read and decoded with a schema of the parts the bridge reads, paths, operations, parameters, request bodies, responses and their schemas, and `components` they reference, refusing what it cannot read and naming the place; a document that fails, or a `base_url` that is not `https` or loopback `http`, stops the server naming the entry. A 3.0 document's `nullable` becomes a `null` type and its boolean `exclusiveMinimum` and `exclusiveMaximum` the numbers 2020-12 takes, since the model and `validate` read JSON Schema 2020-12. Each operation becomes one tool:

- its name is the `operationId`, or `<method>_<path>` with `{x}` as `x` and `/` as `_` when there is none, lowercased, with any character outside the tool name grammar (`names/tool-reference.ts:10`) as `_`; two operations that would share a name stop the server;
- its description is the operation's summary and description, cut as descriptions are (`bounds/call-bounds.ts:122-124`);
- its input schema is one object: each path and query parameter by name with its schema, required when the parameter is, and `body` holding the request body's schema when the body is `application/json`, required when the body is; every component the parameters or the body reference by `#/components/schemas/…` is copied into the tool schema's `$defs` and the references rewritten to `#/$defs/…`, the one form the runtime's compiler reads (`schema-shape.ts:109-112`), so the schema stands alone for the model and for `validate`; an array query parameter is sent as repeated keys, the form the specification defaults to; an operation with a required header or cookie parameter, an object query parameter, or a body of another media type is left out at start with a log line naming it, because a function cannot write what a model cannot see;
- its annotations: `readOnlyHint` for `GET` and `HEAD`; `destructiveHint` for `DELETE`; `idempotentHint` for `GET`, `HEAD`, `PUT` and `DELETE`; `openWorldHint` always. The operator's `allowed` list applies by these names.

A call builds the URL from `base_url`, the path with its parameters encoded, and the query; sends the body as JSON with the entry's headers and `accept: application/json`; and reads the answer within the same `callMs` and `httpAnswerBytes` (`call-bounds.ts:4-19`). A JSON answer is the tool's `structuredContent` and its text; a `text/*` answer is text; another media type is noted and not shown, as MCP content of another type is (`bounds/tool-results.ts:77-90`). A status of 2xx is a result; 401 is the failure `key_refused`, 429 `rate_limited` with `Retry-After` honoured as it is for MCP, and 5xx `failing`, each counted toward the run's failures as a server failure is (`call-bounds.ts:8`); any other 4xx, 404 among them, is an error result carrying the body's text, a problem document where the API answers one, since to a REST API a 404 is an answer about the resource and not a lost session. The call facts' `jsonrpc_id` is `null` for a server of this kind, which has none, and the fact schema says so (`calls/call-facts.ts:21,37`). Listing a server of this kind touches no network; the document is the list.

### 5. Five tools over the playbook's tool servers

`search` with no terms lists the servers and, when they offer at most 100 allowed tools together, every tool; with more, the servers alone, each with its count of tools, and the words say to search by terms. With terms, each tool is scored: a word that matches the name, split at `_`, `.`, `-` and case changes, counts three; one that matches a property name of the input schema counts two; one that matches a word of the description counts one; tools with a score are answered best first, ties by name, at most 100. `only: read` keeps tools marked read-only, `only: write` the others. The four reads reach outside as `list_tool_servers` does today (`listing/list-tool-servers.ts:42`): they list the servers they need and send nothing to a tool. `validate` compiles the tool's input schema with the runtime's JSON Schema compiler and answers its issues; a schema the compiler cannot take answers `valid: null` with one issue saying why. `dry_run` answers what `execute` would check, in the order `execute` checks it, and `reachable` from the listing it just made. `execute` runs the one call path, `ToolAccess.open` and one journalled call under the meta key `auto.on/call_id` in place of `auto.on/tool_test_id` (`calls/call-meta.ts:5`), within the bounds a test has today, `callMs` and `testedAnswerBytes`, and records as section 6 says; its `outcome` words are today's test words with "test" gone (`tool-tests/tool-test-words.ts:46-57`), and its annotations are `reachesOutside` and `mayChangeOutside`.

`testable` goes because `execute` makes it meaningless: it marked the tools a test might call without being read-only, and a writer may now call any allowed tool, told by `read_only` what the call does. `allowed` is the operator's one list, for runs and for hand calls alike.

The JSON Schema compiler moves out of `@on.auto/definitions` into a package of its own, `@on.auto/json-schema`, holding `document/json-schema.ts`, `schema-shape.ts`, `json-bounds.ts` and `reference-loops.ts` as they are; the checked worker of `checking/`, which runs in the workflow engine's job loop, stays in definitions, since it is not a compiler. Definitions, computation, recall, interaction, the workflow host's testing and now tool servers import the compiler. The move is forced by a cycle, since definitions depends on `@on.auto/mcp` (`packages/definitions/package.json`), and it is right on its own: a compiler of documents is below the definitions it checks.

The instructions, the guides and the recipes say what the two operations said, in the five names: the reasoning guide's sentence "it may name the tools of the tool servers that list_tool_servers lists" (`capabilities/reasoning/src/capability/on-this-server.ts:30-34`) names `search`; the instructions' "test_tool_call shows what a tool answers" (`packages/api/src/mcp/instructions.ts:104-115`) says `dry_run` and `execute`; the `first-playbook` recipe calls `execute` where it called `test_tool_call` (`packages/server/src/guides/recipes.ts:14`) and the `give-tools` recipe calls `search`, `execute`, `create_definition`, `run_definition` and `get_run_history` (`recipes.ts:33-44`).

### 6. What a hand call records

A call made through `execute` is the same happening as a call a run makes, so it records the same facts, `tool_call_started`, `tool_call_answered` and `tool_call_failed` with the data decision 0023 gives them (`calls/call-facts.ts:5-53`), on a stream of its own, `tool-calls/<call_id>`, with the caller as `by` and an acted context, no `runId`. A run's three facts carry `number`, the call's place in the run, by which the answer and the failure find their start (`packages/definitions/src/runs/run-events.ts:42-44`, `tool-calls/tool-call-journal.ts:19-37`); a hand call's carry none, since one stream holds one call, and the stream kind tells the two apart, as the declarations allow: a fact's name is checked among the run's facts and a stream kind once each (`packages/definitions/src/run-work/declared-facts.ts:71-111`). The kind `tool-calls/` is declared by the reasoning capability, as `tool-tests/` is today (`capabilities/reasoning/src/capability/reasoning-function.ts:40`); `tool-tests/` and the facts `tool_test_*` go, and the presenter that read them (`tool-tests/tool-test-presenter.ts`) is the presenter of `tool-calls/`: "Someone allowed to change the playbook called the … tool of … by hand", "The tool answered", "The tool …". `record_content`, `request_id`, the scrubbing and the "record before acting" rule apply as they do to a run's call (`calls/tool-caller.ts:23,104-108`). `validate`, `dry_run`, `search` and `introspect` record nothing: they change nothing and reach nothing but a listing.

### 7. A signed-in person's identity

A caller is a key, the local developer, or a signed-in person a configured identity provider vouches for. Keys stay for machines, pipelines and a trainer's agent, and for a person without a provider; a signed-in person is what an agent gateway brokers and what a client connecting directly obtains through the authorization flow.

**The setting.** `identity_providers` (environment `IDENTITY_PROVIDERS`), a list; each entry:

- `name`: the provider's name in the runtime's name grammar, the one that appears on facts;
- `issuer`: the `https` URL the tokens' `iss` must equal, whose metadata is read at start from `/.well-known/openid-configuration` or `/.well-known/oauth-authorization-server`, in the orders the MCP specification gives for an issuer with and without a path, for its `jwks_uri` and the algorithms it signs with;
- `org`: the org this entry admits a person to; several entries may name one issuer, each for its org;
- `membership?`: `{ claim, value }`, the claim whose values must hold `value` for the entry to apply; left out, every token of the issuer applies;
- `grants`: `{ claim, by: { <value>: { permissions, playbooks } } }`, the claim whose values grant: a person's permissions in the org are the union of the grants of the values the claim holds, and their playbooks the union likewise, `*` winning; a token whose values grant nothing in any org is authenticated and forbidden everywhere, which the 403 says as `insufficient_scope`;
- `subject?`: the claim that names the person, `sub` by default.

`PUBLIC_URL`, new, is the runtime's canonical URI, `https` with no path, query or fragment; it is required when a provider is configured, and it is the base of every audience and every `resource` below.

**Verification.** A bearer token that is not a key is parsed as a JWT whose `typ` is `at+jwt` or `application/at+jwt`, as RFC 9068 requires of an access token, `JWT`, which the common providers issue for a custom audience, or absent; an identity token sent by mistake is refused by its audience, never by its `typ`. The header's `kid` selects a key of the issuer's JWKS, fetched at start and again on an unknown `kid` at most once a minute, which makes `authenticate` asynchronous (`authenticator.ts:11`, `authentication.ts:33`); its signature is verified with Node's `crypto`, no library added, for `RS256`, `PS256` with PSS padding and a 32-byte salt, `ES256` in the `ieee-p1363` encoding, and `EdDSA` on the `Ed25519` and `Ed448` curves the JWK's `crv` names; `none` is refused; `iss` must equal an entry's issuer; `aud` must hold `PUBLIC_URL` or `PUBLIC_URL` followed by the path of the endpoint the request reached, since a standards client asks for a token for the resource the metadata named, which carries that path; `exp`, `nbf` and `iat` are checked with 60 seconds of leeway. Then the entries of that issuer are applied, and the principal is the signed-in person, admitted to every org whose entry admitted them.

`Principal.callerIn(org)` answers the caller of that org or `undefined` for an org it does not admit, for a key's principal as for a person's (`packages/identity/src/access/principal.ts:6-19`); the MCP routes already refuse another org before the SDK runs (`packages/api/src/mcp/mcp-routes.ts:29-34`) and the HTTP routes, which take `callerIn(org)` unchecked today (`packages/api/src/operations/operation-routes.ts:46`), answer 403 the same way; the dispatcher's own org check (`authorization.ts:13-16`) stays as the authority every dispatch meets, the workflow host's among them. `/mcp`, whose org is the principal's own, serves a signed-in person the org of the first entry that admitted them, in the order of the setting. An opaque token is refused `invalid_token`; the security guide says which providers issue a JWT access token for a custom audience and how to turn that on. A token over 8 KiB and a JWKS over 64 KiB are refused.

**Discovery.** With a provider configured, `GET /.well-known/oauth-protected-resource` and, as RFC 9728 §3 allows for a resource with a path, the same under `/mcp`, `/orgs/{org}/mcp` and `/orgs/{org}/playbooks/{playbook}/mcp`, answer `{ resource, authorization_servers, bearer_methods_supported: ["header"], scopes_supported, resource_documentation }` without a key, the public paths matching that prefix rather than one exact path (`middleware-chain.ts:11-14`): `resource` is `PUBLIC_URL` with the metadata's own path, as RFC 9728 §3.3 requires, `authorization_servers` the configured issuers, `scopes_supported` the four permissions, `resource_documentation` the public MCP reference. A 401 is answered by the middleware before any route matches (`authentication.ts:26-39`), so it carries `WWW-Authenticate: Bearer resource_metadata="<PUBLIC_URL>/.well-known/oauth-protected-resource", scope="<the four permissions>"`, the root metadata and every scope the resource takes, which the client's consent narrows, plus `error="invalid_token"` when a token was presented and refused. A 403 carries `error="insufficient_scope"`, `scope` with the operation's permissions, which the routes pass to the response from the registration (`outcome-response.ts:9-13`, `operation-routes.ts`), and `resource_metadata`; the MCP routes' own 403s for another org or playbook (`mcp-routes.ts:23,52`) carry the four permissions as `scope` and the endpoint's metadata. Without a provider the challenge stays `Bearer` and the metadata route is not served, since a server of keys alone is not an OAuth resource server; the malformed-header words, which say "API key" (`packages/api/src/authentication/authentication.ts:13`), say a key or a token.

**Scopes.** The MCP hand-off's `scopes` are the permissions already (`caller-hand-off.ts:37-44`); a provider's `grants.claim` may be `scope`, so a company that issues `playbook:read` as a scope needs no mapping, and one that issues groups maps them.

**The person on the facts.** `by` is `person:<name>/<subject>`, the provider's name and the subject claim as it is, so a reader can tell a signed-in person from a key and one provider's subject from another's; `playbook:<id>` and a key's id stay as they are (0023 §3). `started_by`, `created_by`, `answered_by`, `approved_by` and `activated_by` show it as they show a key's id today. A URI made from a caller's id percent-encodes it where RFC 3986 requires, so the source `/callers/<id>` of a run event (`capabilities/coordination/src/events/send-run-event.ts:120-124`) holds a subject with any character and keeps today's `playbook:<id>` as it is. A key's id may not be `local`, as an org's may not (`api-key.ts:12-14`), so a key can never record the local developer's `by`.

**A run and its caller.** A workflow run keeps acting as the identity that started it (`run-attributes.ts:9`), signed-in person or key, because a run is one unit of work that identity asked for and its later calls are that work; a provider that revokes a person stops that person's next request, not the runs already asked for, and the security guide says so. What the run keeps is the identity, the id, the org, the permissions and the playbooks, as today.

**Who sets it up.** The setting is the runtime's, in its configuration file as `api_keys` is; a management plane may write it, through its own repository. Sign-in through a browser, client registration and refresh tokens are the authorization server's, which the runtime never is.

### 8. What stays with an agent gateway

- A person's own credentials on a tool server. The runtime calls a tool server with the entry's credential, the playbook's, as a run does, and the ledger records who asked. A company that wants each person on each system under their own account puts an agent gateway in front of its agents and lists the gateway as one tool server, which decision 0003 already allows.
- Policy per field, masking and access requests. The runtime's governance is the caller's permissions, the operator's `allowed` list, and the ledger.
- A catalog across systems. The runtime's `search` searches the playbook's tool servers; a gateway's searches the company.

The runtime is a service to an agent gateway through section 2 and a client of one through section 4, and it does not pass through a token it received: a call to a tool server goes out under that server's own credential, never under the person's token.

## Consequences
