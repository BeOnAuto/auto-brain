# 0022 — TypeScript is the language: the code a person writes inside the brain, in every place jq was accepted

**Status:** accepted (2026-10-09), proposed and revised twice the same day after two independent audits of the drafts, each with probes; built 2026-10-09, with the amendments at the end

Designed against `origin/main` at b753ded3, after the one-vocabulary rename (0007).

## Context

A person or an agent writes code inside the brain in four places, and in every one of them the language is jq:

- **A computation function** is a jq program over its input (`capabilities/computation/src/run/computation-run.ts:27-57`), checked at save against a dialect that refuses what would read the clock, the environment or the host's time zone, or write outside the program (`capabilities/computation/src/document/program-dialect.ts:11-35`), and run in the engine's worker pool under 64,000,000 units of work, 10 seconds, 256 MiB and four workers (`capabilities/computation/src/run/run-bounds.ts:4-17`).
- **A recall function** is a jq fold, `(view, event) → view`, a jq answer over the view and the run's input, and filters whose `data` may be a jq expression over the event's data (`docs/reference/recall-format.md:125-137,140-180`), under 16,000,000 units a fold, a fold deadline of 10 seconds with twenty overtimes, a page budget of 2 seconds and a view of 512 KiB checked after every fold (`:232-254`; `capabilities/recall/src/run/recall-bounds.ts:10-18`; `packages/workflow-engine/src/folds/fold-page.ts:117-123`); the host folds pages of events through the pool's fold job (`program-pool/fold-job.ts:21-40`, `program-pool.ts:82-87`, the folding at `folds/fold-page.ts:247-258`).
- **A workflow's expressions**, every `${ … }` of `when`, `if`, `switch`, `set`, `with`, `input.from`, `output.as`, `export.as`, `for`, `while`, `raise` and the durations, are jq over `.`, `$input`, `$output`, `$context`, `$task`, `$workflow`, `$runtime`, `$item`, `$index` and `$error` (`docs/reference/workflow-format.md:347-371`), evaluated synchronously inside the engine's pure `decide` with a work budget of 8,000,000 units an expression and 16,000,000 an input (`packages/workflow-engine/src/dsl/expressions.ts:21-33,99-112`; `dsl/evaluation.ts:30-55`; `machine/limits.ts:15-17`), with `now` injected as the time the run recorded for the task, and no deadline, since `decide` reads no clock.
- **Filters** are matched outside `decide` too: a trigger's and a listener's filters in the host (`packages/workflow-host/src/reactions/subscription-starts.ts:25`, `reactions/listener-offers.ts:59-60`; `packages/workflow-engine/README.md:112`), through the same evaluator, with a free-variable analysis that decides whether a listener's filter can be matched later without its task's variables (`README.md:110`; `capabilities/recall/src/document/source-filters.ts:67` shares it).

All of it runs on one evaluator, `packages/workflow-engine/src/programs`: `compileProgram` parses the jq, refuses a nesting deeper than 128, checks the dialect and validates the tree (`programs/program-compiling.ts:29-71`); `run` evaluates it under `maxWork`, `maxSteps`, `maxDepth`, `maxOutputs` and `maxValueDepth`, with a deadline read from a clock the caller injects where it gives one (`programs/program-running.ts:13-19,68-82`; `folds/fold-page.ts:148-150`). The work is counted by a patch of the jq library, `patches/@gabrielbryk__jq-ts@1.7.0.patch`, 2,644 lines of which 968 are added, that price every visited value, object entry, evaluation step, regular-expression position, thread and instruction, character encoded and character searched, replace the library's search with a linear one, measure a value's depth without recursion, and read the deadline's clock every 4,096 units (`:39-205`). The engine's README makes the budget the reason the machine decides the same way wherever it runs (`README.md:65-77`), its rule 4 says `evolve` applies a recorded patch and nothing else, so a replayed history never evaluates an expression again (`:296`), and its rule 20 allows the jq library alone, beside the pool, to be anything but pure portable code (`:312`).

jq was chosen in 0005 for one property and one convenience: a model must never do the arithmetic, so the brain needed a language with no clock, no environment, no files and no network, bounded in work; and the workflow language already evaluated jq, since the open workflow standard the engine implements names jq as its default expression language. The property was right. The convenience has cost more than it saved: the dialect deviates from jq in eleven documented places (`docs/reference/computation-format.md:126-136`), `label` and `break` give wrong answers and are refused, keys sort or do not sort depending on the builtin, and every person and agent who has met the format since has said the same thing, in the words that reached the owner this week: they do not understand jq. Agents write TypeScript fluently and jq badly, and a function an agent writes badly is a function it tests badly. The owner decided on 2026-10-09: TypeScript is the one language a person writes inside the brain, in every place jq was accepted, and jq goes, with its patch, its dialect, its documentation and its tests. Nothing keeps two languages, as nothing keeps an old name beside a new one (0007): the product is not live.

What must be kept is every property the jq evaluator gave: the code runs inside the brain's worker pool and, measured, in the hosted runtime's sandbox; it sees no network, files, clock, environment or randomness; it is bounded in work, memory, time, depth and output; the same program and input give the same answer on every server and either store; and a failure ends a run with an ending that exists.

### How products run a person's code safely

- **QuickJS compiled to WebAssembly**, through `quickjs-emscripten`: "Safely execute untrusted Javascript in your Javascript", "By default, no host functionality is exposed to code running inside QuickJS", with `runtime.setMemoryLimit(bytes)`, `runtime.setMaxStackSize(bytes)` and `runtime.setInterruptHandler(callback)`, a synchronous build that "offers the fastest performance and smallest file size", runtimes and contexts that are "reusable across multiple evaluations", tested on Node, browsers, Deno, Bun and the isolate platform the hosted runtime runs on ([quickjs-emscripten](https://github.com/justjake/quickjs-emscripten)). Figma's plugin sandbox moved to "compiling a JavaScript VM written in C to WebAssembly" after a vulnerability in the Realms shim it had used on the main thread; its lesson is the whole design: "What is dangerous is when it has access to input & output… And APIs are all global variables. So hide the global variables!", behind a small auditable membrane, "via whitelist rather than blacklist" ([Figma](https://www.figma.com/blog/how-we-built-the-figma-plugin-system/)).
- **Temporal's TypeScript workflows** run in "a deterministic sandboxed environment" where "Date.now() and new Date() are replaced by deterministic versions that return the time of the last Workflow Task completion", `Math.random()` is "replaced by a deterministic version", and `WeakRef` and `FinalizationRegistry` are "removed because v8's garbage collector is not deterministic" ([Temporal](https://docs.temporal.io/develop/typescript/workflows/basics)). The reason is replay: "Workflow code must be deterministic to support replay".
- **Shopify Functions** run on WebAssembly under "resource limits, not time limits": 11 million instructions, 10,000 kB of linear memory, 512 kB of stack, a 256 kB binary, 128 kB of input and 20 kB of output, and no network ([Shopify](https://shopify.dev/docs/api/functions/latest), [the limits discussed](https://github.com/Shopify/function-examples/discussions/329)).
- **The hosted runtime's isolate platform**: each isolate may use up to 128 MB of memory, the JavaScript heap and WebAssembly allocations together, 30 seconds of CPU a request by default on the paid plan, and 1 second to parse and run a script's global scope, by the platform's published limits.
- **Windmill** runs TypeScript scripts in flows with a `main` function whose "main arguments are used for generating the input spec of the Script", on Bun or Deno, not sandboxed ([Windmill](https://www.windmill.dev/docs/getting_started/scripts_quickstart/typescript)); it derives the schema from the signature. The brain goes the other way, from the schema it already has to the types, so the schema stays the contract every client reads. **n8n**'s Code node runs JavaScript with "You can't access the file system or make HTTP requests" ([n8n](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.code/)).
- **The open workflow standard** says "All runtimes must support the default runtime expression language, which is jq" and "Runtimes may optionally support other runtime expression languages, which authors can specifically use by adequately configuring the workflow", through `evaluate.language`, "Defaults to jq", and `evaluate.mode`, `strict` by default, "requires all expressions to be enclosed within `${ }`" ([DSL](https://github.com/serverlessworkflow/specification/blob/main/dsl.md), [reference](https://github.com/serverlessworkflow/specification/blob/main/dsl-reference.md)).
- **Types from schemas and types checked**: `json-schema-to-typescript` turns a schema into an `interface`, an `enum` into a union, `additionalProperties` into an index signature, and does not express `format`, `pattern`, `minimum`, `maximum` or `multipleOf` ([json-schema-to-typescript](https://github.com/bcherny/json-schema-to-typescript)); `ts-blank-space` strips types by replacing them with blank space using the official parser, "800 lines of code and one dependency", and refuses the syntax with runtime meaning, enums, namespaces, parameter properties and decorators ([ts-blank-space](https://github.com/bloomberg/ts-blank-space)); the TypeScript native port is 10 times faster at checking than the JavaScript compiler ([TypeScript](https://devblogs.microsoft.com/typescript/typescript-native-port/)), and its npm package, `typescript` 7.0.2, exposes no compiler API to JavaScript: two exports, measured, against the full API of `typescript` 6.0.3.

## Decision

### 1. The language

**TypeScript, in the erasable subset the repository itself is written in**, with the library QuickJS gives and nothing else: no `import`, no `require`, no `enum`, `namespace`, parameter property or decorator, no `eval` or `Function`, no `async`, no `await`, no `declare global`. A document is one module, and a module holds type declarations and its exported functions and nothing else at the top level, since a module that kept state between two calls would make a fold depend on where a page ends (section 4).

| Place                                                  | The module                                                                                                                                                                                   | Its arguments and answer                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A computation function                                 | `export default function (input: Input): Output` in the body                                                                                                                                 | `Input` and `Output` are the document's `input.schema` and `output.schema` as types; the answer is the run's output                                                                                                                                                                                                                                                                              |
| A recall function                                      | `export function fold(view: View, event: Event): View` and, when the run answers something other than the view, `export function answer(view: View, input: Input): Output`, both in the body | `View` is `view.schema` as a type, `Json` without one; `Event` is the brain's event, the CloudEvent the recall reference lists: `specversion`, `id`, `type`, `source`, `subject`, `time`, `datacontenttype`, `dataschema`, `data`, with `causationid`, `correlationid` and up to 32 extensions, each optional; the `answer` field of the front matter goes, since the function lives in the body |
| A recall filter's `data`, a trigger's and a listener's | an expression over `$data`, as `'${ $data.revenue > 100 }'`                                                                                                                                  | `true` takes the event; it names nothing but `$data`, checked at save, so the host matches it with no task's variables, and the engine's free-variable analysis of a filter goes                                                                                                                                                                                                                 |
| A workflow expression                                  | an expression inside `${ }`                                                                                                                                                                  | over `$data`, `$input`, `$output` in `export.as` where it equals `$data`, `$context`, `$task`, `$workflow`, `$runtime`, `$item`, `$index` and `$error`; `$data` is what `.` was, the task's data                                                                                                                                                                                                 |

An expression is an expression, not a statement list; it may span lines; it answers the value of the expression, and `undefined` answers `null`, at the top or as a member, as a missing field in jq answers `null`, so `'${ $input.optional }'` and `'${ ({ id: $input.id, note: $input.note }) }'` are values, not errors. A condition holds unless it answers `false` or `null`, as today. A name a `for` or a `catch` binds, `for.each`, `for.at` and `catch.as`, must be an identifier that is not one of the runtime's, since the names are spliced into the wrapper that evaluates the expression. The jq runtime arguments are already valid identifiers, so `$context.decision.decision == "approve"` reads the same; what changes is `.`, which TypeScript cannot say, so the task's data is `$data`: `'${ ({ ...$input, review: $data }) }'` where `'${ $input + { review: . } }'` was.

**The `language` field** of a computation or recall document stays required and takes the one value `typescript`; a document that says `jq`, or anything else, is refused at save with its line: "The brain's one language is TypeScript; write the program as a TypeScript function". A workflow document may say `evaluate: { language: typescript }`, which is what the standard provides for a runtime's own language, and it is the default when left out; `jq` is refused with the same sentence; `evaluate.mode` stays `strict`, the standard's default, and `loose` is refused, since an expression that fails must fail. The standard's default language is not the brain's; the workflow reference says so where it lists the deviations from the standard.

**Types.** The schemas a document already carries are the types its program is checked against. `Input`, `Output`, `View` and the answer's types are generated from `input.schema`, `output.schema` and `view.schema` at save, in the check job (section 5), by a generator of the brain's own over the schema subset the brain accepts (`packages/definitions/src/document/schema-shape.ts`), which `json-schema-to-typescript` showed the shape of and which the brain does not depend on: it reads files and carries a formatter, and its defaults open every object with an index signature, turn `maxItems: 20` into a union of twenty-one tuples and name types after property titles. The brain's generator closes an object unless the schema opens it with `additionalProperties`, keeps a bounded list a list, and names only the four types above. A constraint a type cannot express, `format`, `pattern`, `minimum`, `maximum`, `multipleOf`, keeps its run-time check, as today. `Event` and the workflow's arguments are fixed declarations the runtime carries: `Event` as above with `data: Json`, and the workflow's arguments as `any`, since a workflow carries no schema for its context and an expression over them is checked for its syntax and its names and not for its types; the reference says so. A program may declare types of its own, as the measured example does.

The check is the TypeScript 6 compiler API, `typescript` 6.0.3 installed under an alias of its own so that the repository's TypeScript 7 toolchain and the brain's embedded compiler are two names (the lint of versions compares names), a dependency of the definitions package alone, never of the engine. Its options: `strict`, `exactOptionalPropertyTypes`, `isolatedModules`, `erasableSyntaxOnly`, `noEmit`, `noLib` with the sandbox's own lib as the one lib, `types: []`; the generated types and the sandbox's declarations are a second virtual file, so the program's lines are its own and no offset is subtracted. The sandbox's lib is generated at build time from the compiler's ES2025 libs without `intl` and `weakref`, the module-shaped iterator lib unwrapped, minus the names the prelude removes and the members the engine lacks, with the instance-only members on a list of their own, and kept under the definitions package's `lib/`, outside `src`, which the engine's `tsconfig` includes whole; one list produces the prelude and the lib, so the two never part. The check runs as a job of the pool, `check`, in the one place the repository lets a worker thread live (the lint rule of `.oxlintrc.json:77-78`: worker threads belong to the engine's pool), on a permit the pool reserves for checks apart from the four of runs, so a save never waits behind four ten-second runs; the compiler's host stays warm in the worker, so a check costs 10 ms for a workflow's hundred expressions and 1 to 3 ms for one. A document that holds programs or expressions is checked once per save, as one generated file holding every expression of a workflow; the check is a step of the capability's save, beside `prepare` and not inside it, since `prepare` serves a run too (`packages/definitions/src/operations/definition-preparation.ts:39-53`) and may fail only with `invalid_input` (`capability/capability.ts:173`); `create_definition` and `update_definition` gain `unavailable` among their reasons (`operations/create-definition.ts:30`, `update-definition.ts:30`), without a kind, for the one case of a check that does not answer within 2 seconds, which the API already answers as 503.

**Stripped at save.** The check worker, which holds the compiler, strips the types of a document's module and expressions with `ts-blank-space` once the check passes, which keeps every line where it was so a thrown error's line is the document's, and the save keeps the stripped text beside the source as the version's `stripped`, which no read shows; a run, a page of folds, a filter and `decide` evaluate that text and import no stripper. The document stays the one source of truth: the stripped text is the one thing stored that is derived from it, derived once at save so that no runtime holds a compiler (amended; see Amendments from the build).

### 2. The runtime: QuickJS in WebAssembly, in the pool, in the engine and in the host

**One engine, one build.** QuickJS, the default of `quickjs-emscripten`, in the synchronous release variant, `@jitl/quickjs-wasmfile-release-sync`, 503 KB, compiled once per process to a `WebAssembly.Module` through `quickjs-emscripten-core`, and pinned by version like any dependency: the work a program costs is counted by that build, so a new build is a change the computation reference notes, as it notes the dialect today. QuickJS-ng is the fork with more of the standard and a third slower on the example; the build takes it the day a feature is missing.

**Who loads it.** The variant's JavaScript wrapper reads files, imports Node modules and reads the clock, so it is a host's module, never the engine's: each host, the server, a pool worker and the hosted runtime, compiles the module once at start, asynchronously, keeps fresh instances ready, and hands the engine an `Evaluator` built on them; `decide` stays synchronous and pure, given the evaluator and a clock as it is given `now`. The engine imports the library by type alone; its portability test names the evaluator's module as it named the jq library and finds no import of the wrapper, no `Date.now`, `performance.now` or `new Date` in `programs/`, which its scan forbids (`src/engine/portability.test.ts:55-63,69-73,144,222-225,234-254`), the prelude's messages included.

**Why not the others.** Node's `vm` is not a sandbox: the code runs on the server's heap and thread with no memory limit, and a `while (true)` holds the event loop. `isolated-vm` is a native addon over V8 isolates: a build step per platform, not portable to the hosted runtime, which is itself an isolate and cannot make one. A child process per run is a process per run, which 0014 measured out of the pool, and no process exists in an isolate. A subprocess runtime such as Deno or Bun is the same again with a second toolchain. The hosted runtime's own isolate is where the brain runs there, not something the brain can hand out. QuickJS in WebAssembly is the one choice that runs in a worker thread, in the server's own thread for an expression, and in an isolate, with the same bytes everywhere, and is what the products that must run a stranger's code chose.

**A fresh instance for every evaluation unit.** Every program job, every fold page, every `decide` input and every group of filters gets a fresh instance of the compiled module with its own `WebAssembly.Memory` whose `maximum` is the unit's memory bound, 0.7 ms at 64 MiB and 2.3 ms at 256 MiB with the prelude, prepared ahead by the host so that `decide` never waits; the instance is discarded after the unit, so nothing of one unit reaches the next and a memory stop never leaves a wounded module behind. The memory's `maximum` is the one memory wall, in bytes; the engine's own `setMemoryLimit` is not relied on, since this build counts allocations and not bytes.

**The sandbox.** A context is born empty of the host, and the prelude makes it the brain's, in module mode, with each replacement defined non-writable and non-configurable and the original constructor unreachable through `getPrototypeOf`, `Reflect.construct`, `bind` and `class extends`, which the probes close:

- `Date`: the constructor with no argument answers the run's moment, the time the run recorded for the task, as `now` does today; with one number it is that instant; with one `Date` it is a copy; with one string it takes a date alone or a date-time that names its offset, and raises `TypeError` for a local date-time, a legacy form or anything else, as `Date.parse` does; with several numbers it raises, since those are local; calling `Date` as a function raises. `getTime`, `setTime`, `valueOf`, `toISOString`, `toJSON`, `toUTCString`, `toGMTString`, `Date.UTC` and the UTC getters and setters stay; `toString`, `toDateString`, `toTimeString`, the `toLocale…` methods, `getTimezoneOffset`, `getYear`, `setYear` and the local getters and setters go, and `String(date)`, a template literal over one and `toLocaleString()` raise rather than answer "[object Date]", since the measurement showed the build reads the host's zone through them.
- `Math.random` goes: a pure function has no use for it.
- `WeakRef` and `FinalizationRegistry` go, since collection is not deterministic; `eval` and the `Function` constructors go, since they build code the check never saw.
- Nothing is added: no `console`, no `fetch`, no timers, no `Intl`, no module loader. A program that names one meets the compiler at save and `ReferenceError` at run.
- **Frozen where a context serves more than one evaluation.** A program job's context serves one evaluation and is not frozen. A fold page's context and a filter batch's serve many, so after the module is evaluated the prelude freezes every object reachable from `globalThis` and from the module's exports and their prototypes, 509 objects, 1.7 ms a context, with `name`, `message` and `constructor` of the intrinsic prototypes made accessors first so that `this.name = …` in an `Error` subclass still assigns; the measurement showed state crossing folds through `Object.assign(Math, …)` and `fold.prototype.seen`, which the compiler cannot see and a non-extensible function does not stop.
- **The output is read by `JSON.stringify` with a refusing replacer** in the prelude, 6.2 ms over 264 KB against 3.3 ms plain and 24.5 ms for a walking serializer: the replacer refuses a `Date`, a `Map`, a `Set`, a class instance, a boxed primitive, a typed array, a function, a `BigInt`, a symbol, `NaN`, `Infinity`, an array hole and a cycle, and the path of the refused member is found on refusal alone; `undefined` at the top or as a member answers `null` for an expression and is refused for a module's output; a plain object, an array, a string, a finite number, a boolean and `null` pass, in insertion order.

**The handler.** `setMaxStackSize` takes the place's stack bound, and `setInterruptHandler` the handler, which the engine calls once every 10,000 of its polls, a call or a loop's jump each, and which does three things: counts the call as a checkpoint, the unit of work, and ends the program when the count exceeds the budget; ends the program at the first checkpoint after the host saw the memory's `grow` refused, so a program that catches the engine's `out of memory` still ends by memory, and the host reads the refusal when the evaluation returns besides; and reads the clock the host injected and ends the program at the deadline. The interruption is the one ending the program cannot catch, measured; a stack overflow is `InternalError: stack overflow`, which a program may catch, at a depth that is the same for the same limit every time, so a program that catches it answers the same everywhere. The counter belongs to the context and starts at zero, so a fresh context's first poll is a checkpoint; where a context serves many evaluations, a fold page or a filter batch, the worker spends the rest of the period before each evaluation in a loop the handler interrupts, 26 to 53 µs, so every fold's count depends on the view and the event alone and not on where the page began.

**Values cross as JSON.** The job's input is already JSON text in its envelope (`program-pool/program-pool.ts:35-45`); the worker evaluates the program over `JSON.parse(input)` inside the context, reads the answer out as one string through the replacer, measured at 7.9 ms for 256 KB in and out, and the host checks the output's size and depth as it checks a jq program's (`jobs/program-answer.ts:51-62`). A fold keeps the view inside its context for the whole page and crosses each event in; after each fold the engine writes the view out and the host checks its size and schema, as today (`fold-page.ts:117-123`), so a view stalls at the event that broke it whatever the page size: 22.9 s for 100,000 folds, against 14.5 s with the view read only at the page's end, which would have let a view grow past its bound and shrink back under one page size and not another. No handle to a host object ever enters a context.

**In the pool.** A worker thread keeps the compiled module between jobs, as it keeps its modules and compiled programs (0014 §2), and is let go of after a deadline, a crash or a thousand jobs, as today; the thread's `maxOldGenerationSizeMb` (`program-pool/pool-threads.ts:136`) stays as the thread's own heap limit and bounds no WebAssembly memory. The pool gains the `check` job kind of section 1 and a permit reserved for it; its contract otherwise keeps its shape (0014 §4).

**In the engine.** Workflow expressions are evaluated inside `decide`, which is pure and synchronous (`packages/workflow-engine/README.md:294`): the synchronous build evaluates synchronously, on Node in the pool's evaluation worker, which the thread that decides waits for, and elsewhere on the host's own thread, with the stack bound at 256 KiB on both, since 512 KiB and more overflow the host's own stack on that thread, measured, and one bound gives an expression one answer on every host (amended below). The budget of an expression is checkpoints, and the engine's rule that work is the only budget inside `decide` (`portability.test.ts:227-231`) changes: a checkpoint bounds the interpreter's work and not the engine's native work, since one checkpoint may hold a `JSON.stringify` of a megabyte, so the handler reads a clock the host gives `decide` beside `now`, as today's evaluator takes a `Deadline` with its `clock` (`fold-page.ts:148-150`), 2 seconds for one input, and an expression that reaches it fails its task with a `runtime` error; a memory refusal inside `decide` ends the same way. The handler reads the clock only at a checkpoint, so on Node the thread that decides holds the deadline itself: it waits for the evaluation worker no longer than the deadline and then ends the worker, as amended below. The ending by work is deterministic and the endings by deadline and by memory are the machine's, as a run's deadline is; the machine's rule 2, the same state and input give the same events (`README.md:294`; `decider/workflow-machine.test.ts:25`), holds for a clock that never reaches the deadline, which the memory driver's virtual clock is, and the recorded input logs, which re-evaluate every expression when replayed (`capabilities/coordination/src/…/input-logs.test.ts:20-29,58-59`), replay under such a clock. A recorded history is never re-evaluated in production: `evolve` applies the recorded patch and nothing else (`README.md:296`), so the deadline decides a live run alone.

**In the host.** A trigger's and a listener's filter is matched through the same evaluator, in the pool's evaluation worker on Node, one frozen context for each group of filters, each filter under a deadline of its own and a fresh context after one the sandbox stopped, since a filter is an expression over `$data` alone (amended below).

**In the hosted runtime.** 503 KB of WebAssembly, instantiated in milliseconds, memory bounded under the isolate's 128 MB, a run bounded at 10 seconds inside the request's 30 seconds of CPU: it fits where the prediction runtime's ONNX build (0012) is still to be measured. The run's memory bound is the host's setting, 256 MiB self-hosted and what the hosted runtime's own record sets, so a program may fit one and not the other, as any resource bound differs between hosts; the computation reference says so. The isolate has no worker threads, so there an expression evaluates on the isolate's own thread and the isolate's bound on CPU is the wall for native work a checkpoint does not see. The measurement in a real isolate is the build's, as 0012 makes it.

### 4. Determinism

The rule is the one the computation reference states: the same input gives the same output on every server and either store. What enforces it:

- The sandbox of section 2: no clock but the run's moment, no randomness, no zone, no locale, no I/O, no timers, no modules, no code built at run, and no state between evaluations: a fresh instance for each unit, and a frozen context where a unit holds many evaluations.
- A module holds no state: no top-level binding but types and exported functions, checked at save, and the page's context frozen, so a fold's hundred-thousandth call sees what its first saw, and a view does not depend on where a page ends, which the audits showed a module-level `let`, a property on a prototype and a change to `Math` would make it.
- The work ending counted in the engine's checkpoints, which depend on the program, the input and the pinned build alone, measured identical over 50 runs and over a program with branching and recursion, and the same for every fold of a page once each starts a fresh period.
- The memory ending taken at a checkpoint by the handler after a refused growth, for the same program and input on the same build and the same bound; the stack ending at the same depth for the same limit.
- Numbers as IEEE 754 doubles, as today's numbers are; `BigInt` exists in the language and is refused in an output, since JSON has none.
- Strings compare by UTF-16 code unit, as today, since there is no `Intl`; `sort()` without a comparator sorts by code unit; the reference says so where it said it for jq.
- Object keys keep insertion order in the output, as JavaScript does and JSON allows; where jq's `tojson` sorted keys, a program that wants sorted keys sorts them.
- The test the build adds: one program and one input, run on SQLite and on PostgreSQL and after a restart, give one output and one checkpoint count; a fold over 3,000 events gives one view and one checkpoint count per fold whatever the page size, with a module that writes `Math`, a prototype and a top-level binding refused or stopped; a program reading `Date.now()` answers the run's moment; one calling `new Date(2026, 0, 1)` or `Math.random` is refused at save and raises at run; one reading a local-time method or stringifying a date raises; the catastrophic regular expression interrupted; the memory bomb interrupted at the same checkpoint twice on a fresh instance, uncaught by a `try`; a `Date`, a `Map`, `undefined` in a module's output, `NaN` and a cycle refused with their path, and `undefined` in an expression's output answered as `null`.

### 6. The workflow format

`evaluate.language` is `typescript`, the default; `evaluate.mode` is `strict`. `${ }` encloses a TypeScript expression; the string forms of `if`, `when`, `exceptWhen`, `for.in`, `while`, `input.from`, `output.as` and `export.as` are expressions without `${ }`, as today. The runtime arguments are the identifiers the standard names, `$data` for the task's data, and `Date.now()` for `now`. `$task.startedAt`, `$workflow.startedAt` and the rest keep their shapes. A duration may be an expression, as today. The documented examples are rewritten: `'${ .month }'` is `'${ $data.month }'`, `'${ $context + { data: . } }'` is `'${ ({ ...$context, data: $data }) }'`, `'${ $error.type != "…" }'` reads the same, `'${ "not published (" + $context.decision.decision + ")" }'` is a template literal.

The state holds the workflow document as JSON (`src/machine/run-state.ts:121`), so its expressions are in the state, but the state's schema does not change and no format is added; no run recorded before this exists, since a local database made before it is deleted (section 7). The six recorded input logs under `capabilities/coordination/input-logs/` whose workflows hold expressions, `for-with-wait`, `run-definition`, `switch`, `temporal-global`, `then-jump-back` and `worker-restart`, which the adapter's tests replay through the machine and so re-evaluate (`input-logs.test.ts:20-29,58-59`), are re-recorded with the same workflows written in TypeScript. ### 11. What this record does not decide

A standard library beyond the engine's, such as a date library, in the sandbox; a module shared between functions of a brain; `Intl` with a fixed locale; a language service for editing in the management plane; the hosted runtime's measurement in a real isolate and its memory bound, which is 0012's open item too; whether the prediction runtime's WebAssembly (0012) shares the pool's worker with this one; pricing the engine's native work per checkpoint, which the deadline covers until a case shows it must be deterministic too; a second language, ever, which would need a record and would meet the rule of one.

## Consequences

- A person or an agent writes a computation function, a recall fold or a workflow expression in TypeScript, with the document's own schemas as its types and the compiler's words at save: a misspelt field is refused with "Did you mean", not found at run.
- The sandbox keeps every property jq had, enforced by an engine built for a stranger's code and by a WebAssembly memory wall the engine cannot argue with: no clock, no randomness, no zone, no I/O, no state between evaluations, bounded work, memory, stack, time, depth and output, the same answer everywhere, and the hosted runtime reachable with 503 KB of WebAssembly.
