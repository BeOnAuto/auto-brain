The owner read rows like this one and named five things: the events are not written the way an event-sourced domain writes them, the stream name says nothing a person can read, the data shows ids a person does not want, `result_json` is a string where an object belongs, and context that belongs in metadata sits in the data beside the fact. Reading the served history afterwards, the owner found a sixth: the history replaced a 50-byte output with `output_bytes: 50`, and the row carried a paging bookmark, `cursor`, in place of the event's place in its stream. A cut copy is not JSON, so it had to be a string; the result is a JSON string holding escaped JSON holding escaped JSON, which no person reads, and which no digest verifies.

The step rows of a workflow's history are presented from one run-log record, `workflow_input_applied` plus one row per step (`capabilities/coordination/src/presenting/run-presenter.ts:75-87`), each with an id of its own that no message in the store has (`step-events.ts:57`; `packages/workflow-engine/src/steps/step-ids.ts:7-9`), so a page can end between the steps of one input (`docs/reference/http.md:205`), and a page filtered by type may hold no event while more remain (`packages/ledger/README.md:121`).

What the conventions say, cited:

- **CloudEvents** separates context from payload: "Context metadata will be encapsulated in the Context Attributes. Tools and application code can use this information to identify the relationship of Events to aspects of the system or to other Events", inspectable "without having to deserialize the event data", with `id`, `source`, `specversion` and `type` required, `subject`, `time`, `datacontenttype` and `dataschema` optional, extensions that "MUST follow the same naming convention and use the same type system as standard attributes", and `data` as "Domain-specific information about the occurrence (i.e. the payload)" ([CloudEvents 1.0.2](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)). Its subscription filters match "any CloudEvents context attribute, including extensions", exactly as written ([CloudEvents Subscriptions](https://github.com/cloudevents/spec/blob/main/subscriptions/spec.md)). The brain already speaks it to every reader of brain events.
- **Marten**, the event store the ledger's own design (0001, 0002) took its shape from, carries on every event an id, a version, a sequence, a timestamp, the stream id, a tenant id, a causation id and a correlation id, with headers, "a Dictionary<string, object>? Headers", for application context such as the user, hands the whole wrapped event to an aggregate's `Apply` so a projection or an aggregate can read the metadata beside the data, and draws the line the same way: "the event body captures the business fact (what happened), while metadata provides contextual information (when, who, causation chain)" ([Marten](https://martendb.io/events/metadata.html)).
- **Emmett**, the store the ledger uses, types a recorded message's metadata as above, hands the metadata to every projection beside the data (`packages/ledger/src/projections/inline-projection.ts:30-47`), and overwrites `messageId`, `streamName`, `streamPosition`, `globalPosition` and `checkpoint` on read, so those names are the store's and no one else's. Measured on the installed store: every field the brain puts in the metadata round-trips unchanged through a stream read and an inline projection on SQLite; the store's `message_schema_version` column is not usable for a shape version, since the SQLite store writes the stream's version before the append into it and the PostgreSQL store a constant `'1'`; on PostgreSQL the metadata is stored as raw `jsonb`, unwrapped, so it refuses U+0000 and an unpaired surrogate, which the ledger's data column avoids with its `{json}` wrapper (`packages/ledger/README.md:357`).
- **Large payloads** in every serious event or message system travel as a claim check: the event carries a key and a store beside the stream holds the bytes. Temporal keeps activity results in the run's history under a per-payload bound and sends larger ones to a blob store through a payload codec ([Temporal](https://docs.temporal.io/cloud/limits)); EventStoreDB caps an event and documents storing large data outside the stream with a reference; the pattern is named in the Enterprise Integration Patterns catalogue.

## Decision

### 1. A fact is named for what happened

### 2. The data is the fact and nothing else

The stored data holds the fact's own fields and no copy of the row's `type`, no actor, no time, no definition, no run id, no chain and no content. For the row above:

```
type       delivery_succeeded
data       {"number":1,"result_bytes":132,"result_sha256":"6ff5…","content_kept":true,
            "duration_ms":947,"jsonrpc_id":3,"delivered_as":{"conversation":"C-1","id":"m-1"}}
metadata   {"messageId":"419f8fb7-…","correlationId":"01a120b0-…","causationId":"58c80530-…",
            "at":"2026-10-09T12:43:51.435Z","by":"brain:finance","runId":"ccd1dbdd-…",
            "definitionType":"interaction","definitionName":"approve-report","definitionVersion":1}
```

The schemas are written once as the facts, `Schema.Struct` without `type`, and the union the readers decode is built from the types and the facts by one function, so no fact declares its name twice. The deferral's `record` stays in `run_deferred`: it is what was asked, as it was asked, which is a fact. `run_started` keeps `input`, `calls_tools` and `finishes_later` and nothing else: how the run began, the call, the trigger or the caller, is its chain, which is context (section 3), so the `started_by` object the first draft gave the start goes, and `Run.started_by`, the actor (`packages/definitions/src/runs/run.ts:85`), keeps its one meaning. `event_published` keeps `event` and `filled`; the emitting run and the depth are context. The brain registry's facts keep `brain`, the fact's subject on the org's stream, and lose `by` and `at`; `reaction_refused` keeps `count`, `reason` and `minute`, and the workflow it names is the context's definition.

The names are the store's own convention, camel case inside one object, as `correlationId` and `causationId` already are; on the wire they take the wire's. None is a name the store overwrites on read. Every text in the context is an identifier the brain already bounds, a caller's id, a definition's name, a reference, a run id, and the `Context` schema refuses in each the characters the CloudEvent schema refuses in an attribute, control characters, unpaired surrogates and noncharacters (`packages/definitions/src/events/cloud-event.ts:53-61`), where the command is taken, so PostgreSQL's raw `jsonb` takes the metadata unwrapped and an append never fails on one store and succeeds on the other. The two references, a call's and a trigger's JSON pointers, gain a bound of 256 bytes where they are written, since they become attributes of events.

**The contract.** `Context` and `contextOf(message)` live in `@beonauto/operations` beside `Lineage`, `RecordedEvent` and `ProjectedMessage`, since the definitions package, the mcp package and the capabilities take the ledger as a dev dependency or not at all (`packages/definitions/package.json:30`). The `Decider` (`packages/operations/src/ledger/decider.ts:9-14`) gains `context(command, state): Context`: the ledger's `execute` calls it beside `decide` and writes it through `metadataOf` onto every event of that decision, so a start takes its definition and chain from the command and every later fact takes them from the state. `evolve(state, recorded)` receives the event as it was recorded, `{ type, data, context }`, so the run's own state keeps reading what it reads today, the definition, the chain, `started_at` and `started_by` from the start (`packages/definitions/src/runs/run-state.ts:82-112`), `at` from a finish and a delivery (`:145,150-153`), and the endings keep taking the definition and the chain from the state inside `decide` (`runs/run-decisions.ts:151-168`), where the caller of `execute`, who gives the lineage, could not know them. The shape reaches further than the deciders, and the build changes each place: the stream read returns data alone today (`emmett-event-store.ts:55`) and the codec decodes data alone (`event-codec.ts:26`), so both return the recorded shape; the decision loop folds the events it has just decided (`ledger-service.ts:63`), so it builds the recorded shape for them from the context it is about to write; a projection's `rowAfter` and `keyOf` receive data alone (`projection-keeping.ts:39,74`; `keyed-projection.ts:146`) and `ProjectedMessage` is `{ id, position }` (`keyed-projection.ts:23-26`), so both gain the context; the presenters and readers that branch on `data.type` (`run-presenter.ts:204`; `interaction/src/schedule/request-ledger.ts:27-41`) branch on the row's type; `RecordedEvent` (`reading/recorded-read.ts:25-35`) gains `context`; the memory ledger the tests use carries it (`packages/operations/src/testing/memory-recorded.ts:46-47,148`). The engine's machine is an operations `Decider` too (`packages/workflow-engine/src/machine/run-decider.ts:1-7`; `workflow-machine.ts:10-17`), so its `context` is required like every other: the host builds the run log's context from the run's attributes, which hold the definition, the caller, the depth, the call depth and the lineage (`capabilities/coordination/src/capability/workflow.ts:44-53`) and gain `called_by` and `trigger`, with `by` the run's caller, the actor the run acts as, as an emitted `event_published` uses it today (`ledger-emitter.ts:13,24`); the engine's format governs the data alone.

### 4. Content is kept whole, whatever its size

The owner decided on 2026-10-09 that the ledger keeps every tool call's arguments and every tool's answer whole, whatever their size, as an event store keeps everything and decides later what to do with it.

**What is kept.** A call's arguments, as the object they were sent as, and a tool's answer as the **protocol answer** the client parsed, its `content` and `structuredContent` (`packages/mcp/src/connections/mcp-connection.ts:89-93`), which is what the digest covers and which loses nothing a tool answered: several content blocks, images, audio and resources beside text, all of it. The **answer document**, the one form every reader of an answer in the brain reads (`packages/mcp/src/bounds/tool-results.ts:92-98`, 0021 §5: the structured content, else the first text block parsed as JSON, else that text), is derived from the kept answer when it is read and stored nowhere, so a person opening a row sees the object the tool answered and the ledger holds the whole. Both are scrubbed before they are kept: the scrubber walks every key and every string value, as it cleans keys and values in text today (`packages/mcp/src/bounds/secrets.ts:32`), and a number whose digits are a secret is replaced by the redaction text as a string would be; a key that scrubs to the same text as an earlier key is dropped with its value. `arguments_bytes`, `arguments_sha256`, `result_bytes` and `result_sha256` are always on the fact, measured over `JSON.stringify` of the parsed protocol answer before any scrubbing, as 0003 §5 has it, so the digest proves the answer as the server gave it, and verifies the kept answer when nothing was scrubbed from it; `content_kept` says whether the content is in the table. The same holds for a delivery's arguments and answer, a reading's, a telling's and a tool test's.

**What the model reads, and the cut.** A reasoning run's model reads a tool's answer as its text today, the text blocks with a placeholder for a block that is not text (`calls/call-replies.ts:74`; `call-bounds.ts:95-101`, `resultText`), and that stays what it reads. When the text must be cut (below), the cut is made where the text is still valid: a text that is JSON is cut after the last complete value, member or array element at or before the bound, a string value cut at a code point outside an escape and closed, a key, a number or a literal never cut, every open object and array closed; any other text is cut at a code point; the brain's marker follows, saying how much of the whole the model holds. Today's cut stops anywhere, so the model reads broken JSON (`call-bounds.ts:96-100`). `shown_bytes` on the fact is the length of the text the model received before the marker, present exactly when the model read less than the whole, and the cut is deterministic, so what the model read is recomputed from the kept answer and `shown_bytes` and is stored nowhere twice.

**How much the model reads.** Today a model reads at most 64 KiB of one answer and 256 KiB in a run (`call-bounds.ts:5-6`), constants from a time of small context windows; a model with a million tokens of context reads a 370 KB answer as a few percent of it, and a cut loses the data the function was written over. The owner decided that a model reads the whole answer and that no function carries a setting for it: the author decides, in the instructions and the queries, whether a tool is asked for a page or for everything, and the runner's model shapes each request's arguments. Two bounds remain, neither a constant of the brain. One answer is cut only to what fits the model's remaining context: the brain knows each model's window from its catalog (`catalog/model-list.ts:17-19`), and an answer that would not fit beside the conversation so far is cut to fit, with the marker; where the window is unknown the answer is read whole and the provider decides. A run's reading is bounded in the unit the operator pays for: a deployment setting of the reasoning capability, `REASONING_MAX_INPUT_TOKENS`, the most input tokens a run's model calls may add up to, counted from the provider's usage after each step, default 2,000,000, parsed as the workflow's and recall's settings are (`settings/workflow-settings.ts:24-67`, `function-settings/recall-settings.ts:20-24`, seven digits at most, with a minimum and a maximum) in `function-settings/reasoning-settings.ts`, logged at start as the workflow's are, and reaching the call bounds through the reasoning capability's dependencies; past it the model is told to answer from what it has, as the run's call budget tells it today (`call-bounds.ts:58,111-113`; `tool-loop.ts:57-63`). The arithmetic that forced this: a run resends its conversation at each of up to 26 model steps, so byte ceilings of 4 MiB and 16 MiB would have let one run send about 94 million tokens, and a 4 MiB answer fills a million-token window on its own, so the run ceiling was never reached. A provider that still refuses a request as too long ends the run as any rejected request does today, `conflict` `unworkable` (`api-call-failure.ts:73-91`; `model-rejection.ts:68-76`), with the answer's size in the words where the provider's message names the context. The two settings govern a reasoning run's model and nothing else: a reading refuses an answer past its bound as `too_large` (`read-answers.ts:65-66`), `test_tool_call`'s `answer` is left out past 64 KiB (`tested-answer.ts:8-10`; 0021 §4), and a delivery's `sent` pointers read the answer as today. **A call's output** is the one bound that changes: the part at `read` becomes `run_succeeded.output`, and it takes the bound every run's output has, 1 MiB with its record (`mostResultBytes`), in place of the 64 KiB an interaction's answer from a person has (`run/run-bounds.ts:4`, shared with `answer_interaction`, which keeps it), so a function that reads a list of members out of a 370 KB answer answers with the list; a part past 1 MiB ends `conflict` `unworkable` as today, and the author pages. The protocol answer itself is bounded only by the transport: the stdio transport caps a server's output at 4 MiB (`connections/stdio-transport.ts:35,43`), and the HTTP transport, which has no cap today, gains one of 16 MiB, past which the call fails as a server failure `too_large`.

**Where it is kept.** A fact is read back by every decision on its stream, by every projection rebuild and by the trigger follower, and the hosted runtime's store takes rows of at most 2 MB (`packages/workflow-engine/README.md:258`), so content does not travel in the message. The ledger keeps it in its own table beside the messages, **recorded content**, content-addressed: keyed by the brain and the digest, holding the scrubbed answer as JSON text in chunks of at most 1 MiB cut at a code point, with a head row carrying its byte size and chunk count, through a port `RecordedContent` declared in `@beonauto/operations`, with `put(brain, sha256, text)` and `get(brain, sha256)`, since the mcp package takes no dependency on the ledger; the chunker moves to `@beonauto/operations` from the engine's snapshot code (`run-log/snapshot.ts:14,70-81`), since the engine depends on the ledger and not the other way. The chunks are written first, each in its own transaction on PostgreSQL, where every open write holds back the oldest-first reads (`packages/ledger/README.md:88-96`), and the head last, in one transaction where the store has one; the fact is appended after the head. A write of a digest the brain already holds writes nothing, measured at about 0.1 ms on SQLite and 1 ms on PostgreSQL, so an identical answer fetched a hundred times is kept once and a retried append rewrites nothing; a crash between the content and the fact leaves content nothing names, which is harmless. Measured: a 5 MB answer writes in 21.6 ms on SQLite and 127 ms on PostgreSQL and reads back in 9.7 and 26 ms; 20 MB in 85 and 573 ms, read in 45 and 125 ms; the chunks join back exactly. A fact whose server keeps no content carries the digest and `content_kept: false`, and no read joins content for it, so a non-recording server's answer never shows through another server's identical one. Nothing is deleted: the content of a fact stays as long as the fact, which is for good; a secret the operator adds later is scrubbed from nothing already kept, and a redaction, when there is one, reaches every fact that shares the digest, which is right since they share the content; both are section 10's. The hosted runtime's store is in the private repository and offers no transactions today (`packages/ledger/README.md:365,382`), so its table is that repository's step. The table is the claim check every event store takes for a payload its rows cannot hold.

**Where it is read.** `get_event` (section 5) answers the row with `arguments` and `result` whole, joined from the content by the digests the fact carries where `content_kept` is true, and `answer`, the document derived from `result`; the history page shows `arguments` and `answer` within 2 KiB, `mostContentBytes`, and otherwise their sizes, since a page bounds a row's data at 4 KiB (`packages/operations/src/reading/public-event.ts:3`). A served row is therefore whole whatever its size and the ledger's layout is the ledger's business.

**Content is kept by default.** A server's entry in the configuration file, `mcp_servers.<name>.record_content`, decides whether its calls' content is kept; today it is `false` when left out (`packages/mcp/src/settings/entry-checks.ts:247`; `entry-reads.ts:28`; `settings/server-entries.ts:79-84` and the generated `auto-brain.schema.json:236-239`; `packages/mcp/README.md:33,132`; `docs/reference/http.md:187,388`; `docs/engineering/self-host/configuration.md:84`; `docs/engineering/reference/http.md:99`; `reasoning-format.md:118`; the tests `settings-reading.test.ts:96` and `scripts/docs-mcp.test.ts:53`), a default 0003 §5 chose so that a third party's content was never kept unasked. It is `true` when left out: the scrub cleans keys and values in place, and a run that cannot be understood from its history is the greater harm; an operator whose server's content must not be kept writes `record_content: false` on that entry, and the fact then carries the sizes and digests alone. `list_tool_servers` gains `record_content`, the value in force. 0003 §5 is read as amended by this section.

**What bounds it.** Nothing the brain adds beyond the transport's cap on one answer: the content table takes it in chunks, and storage grows with what tools answer, which the operator sees in the ledger's size as for every fact. A first-draft rule that kept 4 KiB of an answer kept a fragment no digest could verify and no person could read; a second kept the answer only within the model's bound, which kept what the brain had read and lost what it had not; a third kept the answer document, which loses every block but the first and which the digest does not cover. All three are gone.

Amended (2026-10-11) by [decision 0012](0012-prediction-functions.md): `RecordedContent` takes bytes as a stream with a media type, `put(brain, sha256, { stream, bytes, mediaType })` and `get(brain, sha256)`, the digest the SHA-256 of the bytes, which for a text is that of its UTF-8, and a staging namespace, `stage`, `staged` and `unstage`, kept in `staged_content` by the build's run id.

### 5. What a reader sees

**The row** of `get_run_history` and of `list_brain_events`, which share `PublicEventSchema` (`packages/brains/src/feed/list-brain-events.ts:48`): `{ id, type, summary, data, metadata }`, with `metadata` the context under wire names and nothing withheld: `{ stream, position, global_position, correlation_id, causation_id, at, by, run_id?, definition?: { type, name, version? }, called_by?, call_depth?, depth?, trigger?, trace_id?, span_id? }`, in the words of event sourcing: `stream`, `position` and `global_position` read from the table's own columns, since the SQLite store's metadata writes the position within the append and the PostgreSQL store's writes neither; `position` is the event's number in its stream; `global_position` is the store's sequence across every brain, with gaps, and on PostgreSQL not the read order, which is the transaction and the position together (`packages/ledger/README.md:84-86`); the trace and span ids are the store's, one pair for every event of one append. `summary` is the fact in words and `id` the event's own; the row has no other top-level field. The paging bookmark `cursor` leaves the row: it was the global position wrapped with the brain's key and encoded, a bookmark a page needs and an event does not. The two event reads keep their page bookmark where it belongs, on the page: `cursor` in and `has_more` and `next_cursor` out, as every list has them, since a page filtered by type may hold no event while more remain and a page may end between the steps of one input, where no event's id could say where the read stopped; the two reads take paging fields of their own, since `PagingInputFields` and `PagingOutputFields` are shared with the run and interaction lists (`paging-fields.ts:23-44`). A step row's `id` becomes its record's message id followed by the step's number in that record, `<message id>/<n>`, so that a step is resolved by reading its record, and a `causation_id` that names a step stays resolvable. Each field of `metadata` is present when the context holds it; `data` is the fact as section 2 has it, under one rule for every field that may be large, `input`, `output`, `record`, `answer`, `event.data`, `arguments` and `result`: the field is shown whole when it is within 2 KiB as JSON, `mostContentBytes`, and otherwise as its size under its name and `_bytes`, and when a row's data would still pass the page's 4 KiB the largest field is replaced by its size first; a published event keeps its attributes and shows `data_bytes` for its data, as today (`published-event-presenter.ts:9-34`). A run's 50-byte output therefore shows on its `run_succeeded` row, where today every input, output, record and answer appears as its size whatever that size (`run-presenter.ts:145,155,160`; `run-work-accounts.ts:113-115`) and `get_run` is the only way to read it. `run_id` repeats the route on a run's history and tells the runs apart in the brain's feed. **One row whole** is read by its id with `get_event`, `GET …/brains/{brain}/events/{event_id}` beside `publish_event`'s route and the MCP tool of the same name, under the brain's read permission, `event_id` being the row's `id` and not a published event's own: the same row under a schema without the page's 4 KiB check, every field whole, `arguments` and `result` joined from the recorded content and `answer` derived, which is how a person opens a tool's answer from the history; on MCP, where a result carries its output twice (`packages/api/src/tools/tool-result.ts:53-59`) and an agent reads it in its context, `arguments`, `result` and `answer` are whole within 64 KiB each and their sizes beyond. Its tool description keeps the listings within their bounds, 40,000, 9,000 and 32,000 bytes, against 37,714, 8,157 and 29,618 served today, where `get_run_history`'s own description takes 1,653; the tool counts in `.github/workflows/ci.yml:214` and `served-schemas.test.ts:88,90` rise by one.

**The brain's events**, the CloudEvent `brainFactOf` builds (`brain-facts.ts:125-128`), which recall functions fold, event triggers and `listen` filters match, workflow views read and a triggered run takes as its input: `source` `/runs/<id>`, `subject` `<type>/<name>` on a run fact and none on a definition fact (`:89-104`), `time` from `at`, `causationid` and `correlationid` as today, and every other field of the context as an extension under a CloudEvents name, a scalar each: `caller` from `by`, `definitionversion`, `depth`, `calldepth`, `calledby`, the calling run's id, `triggerkind` and `triggerreference`, each present when the context holds it; the call's reference and run number stay in the ledger and leave the event, which 0007's rule of one name allows since the event never carried them as attributes. The seven names join `causationid` and `correlationid` among the attributes `publish_event` and `send_run_event` refuse (`reserved-attributes.ts:87-101`), so no published event can claim a caller or a depth. `data` is the fact: for `run_succeeded` the `output` or `output_bytes` as today, for `run_rejected` the `reason` and `kind`, for `run_started`, `run_failed` and the definition events nothing, so `data` is left out. Only run and definition facts become brain events, as today (`brain-facts.ts:26,106-116`); a published event stays as its publisher gave it. **A filter names `type` and may name any other context attribute of the event, `source`, `subject` and an extension such as `triggerkind` or `caller`, each as written, a whole number for `depth`, `calldepth` and `definitionversion`, and `data` as a value or as an expression over the data alone**, which is the standard's exact filter and replaces the one rule that named three attributes (`docs/reference/recall-format.md:154-161`; `packages/definitions/src/registry/definition-triggers.ts:7-13`); the save-time checks of a filter's attributes (`event-filter.ts:27` and recall's `source-filters.ts:32-33` on 0022's branch) take the integers, and the matching already reads any named attribute there (`attribute-match.ts`). ## Consequences

- A person reading a row of the ledger reads a named fact with its own data, and the who, when, which definition, which run and which chain beside it as metadata, the way an event-sourced domain writes them and the way CloudEvents, Marten and the store itself model them.
- A decider, a projection and a reader get the context the same way, through one contract, without opening the data; a reader of the history or the brain events gets the row in the shape the ledger holds it, with a tool's arguments and answers as objects; a trigger or a recall function filters on the context as the standard's filters do, and no published event can forge it.
- A tool's arguments and answers are kept whole whatever their size, beside the stream and keyed by their digest, so a run can be understood after the fact from its history alone, nothing a tool answered is lost, and the streams stay as light as today; a fact is proved by its digest and a person reads the object the tool answered.
- A reasoning function's model reads whole answers up to its own context, and a function that asks a system answers with the whole part it read; the operator bounds a run's reading in tokens.
- The cost: every fact's schema, the decider contract reaching the stream read, the codec, the decision loop, the projections and the engine's machine, the two stores' reads and fills, every reader of the moved fields, three projection versions, the words, the row, its paging fields and the brain-event mapping, `get_event` with its index, the recorded-content table and port on both stores, the filter rule, the HTTP transport's cap, the new setting, the recall and workflow references, the smoke steps and the measure scripts, and the deletion of a local database; storage that grows with what tools answer; a client of the history or the events, Studio among them, changes what it reads, with the table of section 8.

### Decision

1. **The digest and the size describe the kept text, and nothing is digested that is not kept.** The scrubbed protocol answer, and the scrubbed arguments, are the one text a fact describes: `arguments_bytes` and `result_bytes` are measured over it, `arguments_sha256` and `result_sha256` are its SHA-256, and the content table is keyed by that digest, so the key is the content's own address, and `read` checks the joined text against it, failing as a defect on a text that does not match, as the ledger fails on a fact that no longer decodes. The digest is present exactly when the content is kept, so `content_kept` goes: an entry with `record_content: false` gives a fact its sizes and no digest, since a digest of a document a reader can guess, a decision, an amount or a date, confirms the guess as the digest of a secret did; the page join and `get_event` read the digests a fact has and nothing else. What the model read is `resultText` of the kept answer, cut at `shown_bytes` where the fact has it, and a reply's `resultBytes`, the run's `answeredBytes` and `test_tool_call`'s `result_bytes` are the one size measured once over the kept text, so every number a reader meets describes a text a reader can open. When the secret set changes between two keeps of the same answer, each scrubbed text is kept under its own digest and each fact names the one that was kept for it; a redaction added later reaches only the facts recorded after it, which is right, since a fact names what was kept. 0003 §5's rule, that the digest proves the answer as the server gave it, goes: a digest of text that is kept nowhere proves nothing a reader can check, and gives away what the scrub took out, measured above. Ruled out: keeping `content_kept` beside an optional digest, two fields for one fact; a digest over the received text kept only where nothing was scrubbed, which tells a reader which answers held a secret.
2. **The tools of one connection stay 26, under a bound set by reason.** `get_run_history` and `list_brain_events` are two reads with different scopes and defaults, one run's own events oldest first against the run's whole tree newest first, and one tool for both would carry a parameter to say which read is meant, so they are not merged, and the route of a run's history and the reads of the management plane stay as they are. The bound is the one [0016's amendment of 2026-10-11](0016-speaking-to-agents.md#amendment-2026-10-11-the-bound-on-the-tools-of-a-connection-is-set-by-reason) sets: the bytes of a connection's listing bind, 40,000, 9,000 and 32,000, enforced when the server starts, and the count is a limit of 32 that does not move when a tool is added; `mostToolsOnAConnection` takes that limit, the two test names that say twenty-five say what they count, the start test holds 32 and 33 where it holds 26 and 27, the api README's row reads the limit by 0016, and nothing else of point 11 above changes: the server lists 26, and the listings measure 39,248, 8,157 and 31,037 bytes, since decision 10's description of `get_event` names every field it sizes.
