# 0011 — Waiting calls: a workflow waits for a run that finishes later, and a run can be cancelled

**Status:** accepted (2026-10-07)

## Context

A workflow calls a function through `execute_spec` and continues with the run's output. A run of a reasoning or a computation function ends within its call. A run of a workflow does not: its capability answers `finishesLater`, specs records `execution_deferred`, and whoever started the work settles the run later through `executionSettler`, which only the composition root holds and only the workflow host uses. The interaction function (0010) is a second kind of run that finishes later, by its nature: it asks and waits for an answer, for minutes or days.

Verified against the code at adf527b, a workflow cannot wait for such a run today, and several things around it are wrong in ways that this record fixes rather than works around:

- the orchestration capability turns a child that is still `started` into a failed call, with the words "The run finishes later, and a workflow cannot wait for it in this version" (`primitives/orchestration/src/calls/function-results.ts:21-23`); the rule that a workflow may not call a workflow lives in four places, at save (`document/workflow-functions.ts:30-33`), at dispatch (`calls/spec-arguments.ts:27-29`), in the server's composition, where the nested `execute_spec` is built over the primitives without the workflow adapter (`packages/server/src/workflows/host-dependencies.ts:101`), and in the result mapping, and lifting it meets a cycle in the composition root, since the adapter needs the host's start and the host's perform needs `execute_spec` over the adapter;
- a call row left `running` is performed again once per restart (resume skips rows whose fiber is alive, `host-executor.ts:178`), and a running call holds one of 32 permits (`host-executor.ts:79,91`, `workflow-settings.ts:47`), so a call that waits for days cannot stay `running`;
- one deadline serves every call of every run, the longest run of any capability plus sixty seconds (`packages/server/src/workflows/workflows.ts:11,21-23`, `workflow-engine/src/runner/run-timers.ts:99-105`), armed inside the pure machine from the run's recorded limits when the call starts (`tasks/call-task.ts:41`), where the machine cannot read the registry; a deadline today ends the call as `unreachable`, a `communication` error retry policies match (`call-task.ts:73-76,87-89`, `dsl/raised-error.ts:149-155`);
- nothing cancels a run from outside: `cancel_requested` is produced only by the test driver; a cancelled or overrun workflow settles `failed` (`raised-error.ts:121-126`, `runner/run-lifecycle.ts:194-195`), indistinguishable from the server breaking; `whenCancelled` on the capability interface already means how a run behaves when its own request is interrupted, `stop` or `finish` (`primitive.ts:46,64`); the host's `cancelled()` marks a row before anything else and tombstones unknown states (`host-executor.ts:144-152`); only the server holding the lease can touch a workflow, the others refuse with `HostElsewhere` (`host/run-requests.ts:33-54`), so a command that lands on a standby server cannot reach the engine;
- a settlement records the run's starter as its author (`execution-decisions.ts:143`), drops every rejection kind but two, every `because` and the issues of an `invalid_input` (`execution-settler.ts:61-74`), is deduplicated by comparing whole results (`execution-decisions.ts:139`), and a workflow that finishes in its first input tries to settle before its deferral is recorded and is refused until the next sweep (`workflow.ts:54-60`, `execution-running.ts:41`, `settle-back-off.test.ts`); the engine's settlement schema has free-string kinds and no issues (`settlement.ts:3-15`); a conflict's kind is not recorded on main although every conflict is replayed as `unworkable` (`operations/execution-attempt.ts:78-80`, `execution-lookup.ts:39`), which the computation branch (0005) fixes for runs within their call but not in the settler;
- the run decider refuses a tool-call fact once the run has deferred, with the words "The run has finished" (`execution-decisions.ts:42,120-124`); its one count of tool calls both says "something may have changed" and carries across starts of the same id (`execution-state.ts:28,69-70`), so any recorded call refuses a re-run with `tools_called`, and the host performing a `running` call again after a restart meets that refusal;
- the host dispatches a run's outputs in order and stops at the first failure without advancing its watermark (`engine/output-dispatch.ts:45-62,84`), so an output that fails for good holds every later output, the settle included;
- the engine discards a second `call_answered` once a call is closed (`machine/admission.ts:49-50`), a child's id is derived from the parent run, the step and the attempt and named on the parent's `step_waiting`, ending a run cancels all its calls (`runner/run-ending.ts:53`), and settlements are decided on the run's stream with retry on version conflicts.

Every message carries its cause and its correlation (0009). The reactions build (0004) adds to the host a follower of the ledger: a fiber under the lease, woken by an in-process signal on every append and by the sweep, with a cursor per brain, reading the partition forward and delivering durable inputs, with the brain's own facts built from stored records.

## Decision

### 1. A call whose run finishes later waits, and the child's ending answers it through the follower

When a `call` of a function starts a run that defers, the call is a **waiting call**: the host moves its call row from `running` to `waiting`, releasing its permit, with the child's id, and no sweep or restart performs it again. The child's start records the parent run and the call key it answers, and every finish of the child copies them from the state as it copies the capability, the name and the version, so the link is on the fact the follower reads and nothing is looked up.

The child's ending, its settlement or the finish of a run that ends within a later request, is a fact on the child's stream that names the parent call. The host's follower, reading each brain's partition in order, sees every finish that names one and delivers it to the parent as the input `call_answered` under the call key, mapped by the orchestration capability's own result mapping, injected into the host, the 1 MiB check and the folding of issues included; the engine dedupes the key, so a delivery repeated after a crash is harmless, and a delivery that meets a closed call is a no-op receipt, never a failure. The follower runs on the lease holder, so an answer, an expiry or a cancellation that lands on any server reaches the parent through the ledger, within the follower's wake, and the standby servers' refusal of host commands no longer matters for anything that is a fact. This amends the follower of 0004 in three ways: it keeps a cursor for every brain, found at start from the brain registries of the orgs and afterwards at a brain's creation fact, not only for brains with subscriptions; its two built-in consumers, child endings and cancel requests, are never skipped after failing sweeps, since skipping one would lose an answer; and a `conflict` that says the run has already ended is a success for both, as a closed call's receipt is. A call row's `waiting` state is a cache the follower keeps; the resume of a run after a restart finds its waiting calls by the row and the child's id, and a row whose child has already ended is delivered by the follower's pass from the brain's cursor.

A settlement carries what the result carries, in a typed schema shared by the engine and specs: a success's output and record; a rejection's reason, kind, because, detail and issues; a failure's incident; and the actor who settled it, the acting identity `brain:<brain>` for a settlement of the host's own, the caller for a cancellation. Nothing is dropped on the way to the run's record, the run list or the words. A conflict's kind is recorded on the run and replayed as recorded, in the settler as the computation branch does for runs within their call. A settlement's key is its status, reason and kind, plus a part the capability supplies, the output's digest for a success: a second settlement with the same key, from any actor, answers the one that landed; a different one is `conflict`. A rejection keeps its optional record, which analytics reads. A capability declares on its prepared definition that its runs finish later, as it declares that they call tools, and the start records it as `finishes_later`; a settlement is accepted once the start says so, so the settle of a run that ends in its first input is never refused for arriving before the deferral, while the claim of an existing run under its id still needs the deferral, so a crash between the start and the deferral leaves a run that a retry under its id starts again rather than a stuck one; and a finish records no deferral once a result exists. A reasoning function's longest run includes its tool loop, the larger of the loop's bound and the model's deadline.

### 2. Each call has its own deadline, resolved when the workflow starts

When a workflow run starts, the orchestration capability resolves, from the registry, the longest run of every definition the document calls, each declared by its capability per definition, the reasoning capability's model deadline, the computation capability's ten seconds, an interaction function's `expires`, a workflow's `ORCHESTRATION_MAX_DURATION`, and records them in the run's limits, so the pure machine arms each `call_deadline` from the recorded limits as it does today, per call, with sixty seconds of grace, capped by the run's remaining duration. A definition saved after the run started uses the run-wide value, which stays as the default. Only a call that names its definition literally is resolved at start; a call whose definition is an expression gets the run-wide value; a version saved during the run keeps the limit resolved at start. A deadline that passes ends the call as the format's `timeout` error, which retry policies do not match unless they name it, a change from today's `unreachable` that the format reference's upgrade note says; and it cancels the child through the command of section 3 by the derived id. After downtime, when a child's own ending and the parent's deadline are both overdue, the child's ending is performed first, so a request that expired while the server was down ends `unanswered` and not `cancelled`. A waiting call whose child ends after the deadline passed delivers nothing, since the key is spent. The limits in the state are a change to the state's schema, which the engine's rule makes the next format, with the corpus and the input logs re-recorded.

### 3. A run can be cancelled, and a cancellation is one ending

`cancel_execution`, `POST /executions/{execution_id}/cancel`, under `brain:write`, also an MCP tool, with a reason, records `execution_cancel_requested` on the run's stream with the caller and the reason: the request is a fact, so it can land on any server and survives a crash. A run that has ended, or that runs within its call, is `conflict`, since no server can interrupt another request's fiber, and the reference says so. The follower turns the fact into the effect, under the lease:

- for a workflow run, the engine input `cancel_requested`, which carries the actor and the reason into the record and ends the run as it does today, its in-flight tool calls interrupted and its waiting calls cancelled child by child, by their derived ids; the child is cancelled before its row is marked, every state of a row is handled by name, and a child that has already ended answers `conflict`, which the host takes as the receipt it is; the engine's `cancel_call` output gains the reason it cancels for, in the same format bump;
- for a deferred run of another capability, the capability's new hook `cancel(run)`, a pure decision over the run's record that answers what the settlement must say, idempotent and without I/O, followed by the settlement; a hook that throws is a failure of the run.

A cancelled run ends **`rejected` with the reason `cancelled`**, a reason of its own beside `invalid_input`, `unavailable` and `conflict`, with the kind `requested` for a caller's cancel, `deadline` for a parent's call deadline or an enclosing timeout, `overrun` for a run past its longest duration, and `parent_ended` for a child whose parent ended or whose branch lost a race; a workflow whose output does not fit its record ends `rejected` `conflict` with the kind `oversized`, no longer `failed`, and `failed` stays for a broken run alone; carried through the settlement schema, the listed rejection, the words, its problem type, which sends no `Retry-After`, and its workflow error type, which no retry policy matches by accident. A cancelled or overrun workflow therefore no longer ends `failed`. The cause of the engine input is the request's message id; of a deadline's cancel, the parent's step event.

A workflow may now call a workflow: the four places that refuse it go, the composition root builds the nested `execute_spec` over every capability by giving the adapter the host's start through a port bound late, and the called workflow's run is a waiting call. A run carries a **depth** in its attributes, passed in-process with the lineage and recorded on its start: the number of calls above it, bounded at 8, and the number of reactions above it, bounded at 8 as 0004 keeps it in the same attributes; the ninth start is refused as `conflict` with the words that say so, and the calling step ends `runtime`. The descendants of one root run are bounded at 1,000 open calls, counted by the host on its call rows through a root column and its index, so a self-calling workflow with many branches ends at that bound and not at the host's permits.

### 4. The decider's rules for a run that works after its call

A deferred run accepts the facts of its own work: tool calls as today, the outbound calls of 0010, and the settlement; it refuses them once settled, with words that say the run has ended rather than finished within its call. Its state keeps two counts instead of one: the number of the last recorded call, assigned by the decider when the fact is appended, so parallel tool calls of a reasoning run each take the next number in the order they land and a delivery attempt names the number the read model expects, which a fire repeated by two hosts fails to match; the state's fold knows `execution_cancel_requested` and the delivery facts as work of a started run, and the status map lists them under `started`; and whether any call may have changed something outside, which only tool calls of a reasoning run set, so an outbound delivery never blocks a re-run under the same id and a `running` call performed again after a restart is accepted.

### 5. Bounds

| Bound                         | Value                                                                                                           | When reached                                                             |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Calls above a run             | 8                                                                                                               | the ninth start `conflict`; the calling step `runtime`                   |
| Open calls under one root run | 1,000, a setting                                                                                                | the next start `conflict`; the calling step `runtime`                    |
| A call's deadline             | the definition's longest run plus 60 s, capped by the run's remaining duration; the run-wide value when unknown | the call ends `timeout`, the child is cancelled with the kind `deadline` |
| Delivery of a child's ending  | at-least-once through the follower, deduplicated by the call key                                                | —                                                                        |
| Running calls at once         | the host's 32 permits, waiting calls not counted                                                                | —                                                                        |

### 6. Vocabulary and surfaces

In text a user reads, a step waits for the function's run; the format reference's `call` section says which functions finish within the call and which finish later, that a step waits for the latter up to the function's own deadline, that a workflow may call a workflow, and the upgrade note on `timeout`. The HTTP and MCP references gain `cancel_execution` and the `cancelled` reason with its kinds; the run words gain cancellation; the tool count rises by one; a cancel that lands on a standby server is accepted, since it is a fact.

### 7. What this record does not decide

Cancelling a run that executes within its call across servers; pausing a run; a cancel with a grace period; reminders to a waiting step; priorities among waiting calls.

## Consequences

- Any capability can take as long as it needs: the host owns the waiting, the deadline is the definition's, and the follower delivers what any server records.
- Sub-workflows come with it, bounded by depth and by descendants.
- Debts paid: a settlement carries its actor and its whole result in a typed schema and is deduplicated by a key; a conflict's kind is recorded and replayed truthfully in the settler too; a cancelled or overrun workflow ends as cancelled; a run that finishes later says so on its start; the deferred decider accepts the facts of its work and tells "may have changed" from "was called"; call numbers are the decider's; unfinished calls are no longer performed again; a `start_call` or `cancel_call` output that fails for a run that has ended no longer holds the run's later outputs, while a `settle` is never skipped; the host handles every row state by name; the workflow-calls-workflow rule lives nowhere.
- The follower of 0004 gains two built-in consumers, child endings and cancel requests, which is why this record builds after it.

## Verification the build must include

- A workflow calling a workflow end to end over HTTP and MCP, the child's output reaching the step, its rejection reaching a `catch` by kind, the depth bound at nine and the descendants bound; a restart while a child waits, with the call not performed again and the permit released; a child settled on a standby server reaching the parent through the follower; a delivery repeated after a crash applied once; a closed call receiving a delivery as a no-op; a run that ends in its first input settling at once.
- Per-call deadlines: a reasoning call timing out at its own deadline while a sibling call to an interaction function keeps waiting; the child cancelled with the kind `deadline`; a child ending after the deadline delivering nothing; a definition saved after the run started getting the default; the format bump with the corpus and the logs.
- `cancel_execution` on each kind of run, on an ended run, on a run within its call, on a standby server, on a tree of three levels, by a deadline; the fact, the effect through the follower after a crash between them, the ending `cancelled` with each kind, the words and causes; a cancelled workflow no longer `failed`.
- The settler carrying every kind, because and issue with the actor; the settlement key; a conflict's kind recorded and replayed; the deferred decider accepting work facts, refusing a repeated number, and telling outbound calls from tool calls; the run list and words.
- The references, the tool count, the internal-terms check.
