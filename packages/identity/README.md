# @on.auto/identity

Who calls the runtime: a key, the local developer, or a signed-in person the Auto identity service vouches for. `authenticatorFor` of `src/index.ts` takes the settings, the API keys, local mode and, where sign-in is on, the identity service, and answers the access mode and an asynchronous `authenticate`, which takes the credential a request presents and the path of the MCP endpoint it reached, if any, and answers its `Authentication`: the `Principal` of the caller, or a `Refusal` whose `because` says why a token was refused, in words that name a rule or a claim and never a value of the token (`isRefusal` tells the two apart). A principal holds its own caller, `own`, and answers the caller of an org with `callerIn(org)`, or `undefined` for an org it does not admit: a key admits its own org, the local developer every org, and a signed-in person the org their token names. The key command, `src/key-command.ts`, prints a new key once and the `API_KEYS` entry that admits it.

## Keys

A key is `abk_<id>_<secret>`, stored as the SHA-256 of the whole key with its org, permissions and playbooks, and verified in constant time. The org `local` is local mode's and the id `local` the local developer's, so `API_KEYS` and the key command refuse both.

## Signed-in persons

`identityServiceOf` of `src/identity-service/identity-service.ts` takes the issuer, `autoIdentityService`, `https://clerk.on.auto`, unless a development runtime names another, and `PUBLIC_URL`. `signInScopes` are the scopes the runtime asks a client to request of the identity service: `user:org:read`, which binds the access token to the organization the person signs in to, as the `org_id` claim, and the four permissions, `allPermissions` of `@on.auto/operations`, the one definition of them, which the identity service defines as scopes of its own, each with a sentence its consent screen shows. At start it reads the issuer's metadata, from the addresses the MCP authorization specification orders, and its key set, each within 64 KiB and 10 seconds and following no redirect (`src/identity-service/issuer-requests.ts`), and stops with `UnusableIdentityServiceError` naming the service when one cannot be used or its key set holds no keys.

The [`jose`](https://github.com/panva/jose) library verifies the tokens and keeps the key set: `jwtVerify` checks the signature with the key of the token's `kid`, or, for a token without one, with the issuer's only key of its type, refusing it when several fit, the algorithm among `RS256`, `PS256`, `ES256` and `EdDSA`, the issuer, the audience, `exp` and `nbf` with 60 seconds of leeway and that `exp`, `sub` and the org claim are present; `createRemoteJWKSet` holds the service's key set, read through the bounded read above, read again for an unknown `kid` once 60 seconds have passed since the last read that succeeded, and at the first token after it is ten minutes old, `jose`'s default age, set in `src/identity-service/issuer-keys.ts`; a token whose key set cannot be read once it is ten minutes old is refused, never verified against the old one. The runtime checks itself what is its own rule (`src/tokens/token-verification.ts`): a token at most 8 KiB before anything is decoded, a `typ` of `at+jwt`, `application/at+jwt`, `JWT` or `application/jwt` or none, an `iat` at most 60 seconds ahead, a `sub` that is a non-empty string of at most 256 bytes without control characters, unpaired surrogates or noncharacters, an org claim that is an org id other than `local`, and a `scope` claim, where the token holds one, that is a string; `identityServiceOf` names the audiences a request may hold, `PUBLIC_URL`, with a final `/` or not, and on an MCP endpoint that endpoint's URL. The org claim is `org_id`, the one constant `orgClaim` of `src/tokens/token-verification.ts`, since the service's metadata advertises no claim name, and the tests of `src/identity-service/identity-service.test.ts` pin it. The person is `person:<sub>` in that org alone, over every playbook, with the permissions among the scopes its `scope` claim names, split at each space, in the order of `allPermissions`; any other scope, `user:org:read` among them, grants none, so a token that grants none of the four, or holds no `scope`, is a person of the org with no permission (`signedInPersonOf` of `src/access/principal.ts`). No org is taken from anything else the token holds, and `user:org:read` is not checked: `org_id` is. The security guide of the documentation sets out every rule.

`fakeIssuer` of `@on.auto/identity/testing` is an issuer for tests: it answers its metadata, its key set and a token endpoint for the client credentials grant, whose token's `scope` claim holds the scopes the request asked for, signs a token with `jose` and a key of each algorithm, and turns its keys over; `signedTokens` and `principalIn` help tests sign a token, which holds every sign-in scope unless a test gives it a `scope` of its own, and read the person it admits.

## Measurement

`pnpm --filter @on.auto/identity measure` starts the identity service 200 times against the fake issuer answered in process, its metadata and a key set of four keys, and verifies 10,000 tokens of each algorithm one after another through `personOf`: the `jose` verification with its key, the runtime's own checks and the person it admits. In process, the start measures the runtime's own work; the identity service's two round trips at start add their network time to it, and `jose` imports a key the first time a token names it. On Node v26.10.0 with 16 cores, on 2026-10-13, two runs:

| Measured                                      | Run 1   | Run 2   |
| --------------------------------------------- | ------- | ------- |
| Start: metadata and key set read              | 0.06 ms | 0.04 ms |
| Verification of an `RS256` token, per request | 29.1 µs | 28.4 µs |
| Verification of a `PS256` token, per request  | 29.6 µs | 28.8 µs |
| Verification of an `ES256` token, per request | 52.7 µs | 52.7 µs |
| Verification of an `EdDSA` token, per request | 52.9 µs | 52.6 µs |
