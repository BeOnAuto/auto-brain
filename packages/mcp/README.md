# @on.auto/mcp

How a playbook reaches the outside world: the MCP servers the operator configures, and the tools a run is offered from them, as [decision 0003](../../docs/decisions/0003-mcp-servers.md) sets out. The server reads the settings and makes one `ToolAccess` at its composition root, which it gives to both capabilities that reach a tool: the reasoning function adapter opens a run's tools through it when a reasoning function names `tools`, and runs the model's tool loop over what it gets back; the interaction function adapter delivers a request, reads the replies to it and tells its party how to answer with one call of one tool each, the tools its function names; `list_tool_servers` lists through it the servers an org's playbooks, or one playbook, may use and their tools; and `test_tool_call` calls one tool through it, as a run would, so an agent learns what the tool answers, as [decision 0018](../../docs/decisions/0018-testing-a-tool-call.md) sets out.

## Entry points

- `@on.auto/mcp`: the settings, `makeToolAccess`, `defineListToolServers`, `defineListToolServersInOrg`, `defineTestToolCall` and `toolTestPresenter`, and the facts of a call that `@on.auto/definitions` builds the run's events from. The access loads the MCP client, its OAuth providers and `node:child_process` (`src/access/linked-access.ts`) through a dynamic import when a run first opens its tools, a listing first asks a server or a test first calls a tool, so a server that never does any of them never loads them: the server's start loaded 55 files and 0.94 MiB more with them (measured 2026-10-06 with a module load hook, 1,241 files against main's 1,186). Without them it loads 34 files and 77 KiB of this package, the operations `list_tool_servers`, at the playbook and at the org, and `test_tool_call` among them (measured 2026-10-08 with a module load hook over both entries, against 33 files and 71 KiB before the org's listing, and 20 files and 42 KiB before `test_tool_call`).
- `@on.auto/mcp/policy`: the pure helpers a caller needs without connecting to anything (`toolReferenceOf`, `toolReferenceShape`, `writtenOf`, `runBoundMs` and `runIdKey`). It loads no transport code, so the reasoning function adapter, which parses a function's `tools` and bounds its run, does not load the MCP client wherever it is bundled; it takes `ToolAccess` as a type only.
- `@on.auto/mcp/testing`: the fake server and the helpers of the tests (see Testing).

## Settings

`readMcpSettings(environment, { modelProviders })` reads `MCP_SERVERS`, JSON, which the server also writes from the configuration file's `mcp_servers`: an object with one entry per server, keyed by the name a reasoning function writes in `server/tool`. Each entry carries the tools of its server, in `McpServerSettings` as `allowed`, the names or `null`, and `testable`, the names:

- `allowed`: the tools of the server a function may name, each named as the server lists it, without the server's name and without `*`. Every tool of the server when it is left out, so an entry always allows at least one tool.
- `testable`: the tools `test_tool_call` may test although the server does not mark them read-only, each among `allowed`, since a tool a function may not call cannot be tested either. Only the tools the server marks read-only can be tested when it is left out. It is the only place an operator vouches for a tool, and names none a server marks read-only, since those need no listing.

Each list is checked at start (`src/settings/tool-lists.ts`), at the pointer of the name and never with a value: a name that is not a tool name, such as `graph/search`; `*`, which in `allowed` is what leaving it out means and in `testable` would vouch for every tool of the server, those it adds later among them; a name listed twice; an empty list; and in `testable` a name `allowed` does not name, checked only while `allowed` can be read. Whether a server has a tool is learned from the server, never at start.

| Field            | Of    | What it holds                                                                                                                                 |
| ---------------- | ----- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`           | both  | `http` or `stdio`; taken from `url` or `command` when left out                                                                                |
| `url`            | http  | The http or https URL of a server spoken to over Streamable HTTP                                                                              |
| `headers`        | http  | Headers sent with every request; the values of their references are secrets                                                                   |
| `auth`           | http  | OAuth client credentials: `issuer`, `client_id`, `client_secret` or `private_key` with `algorithm`, and `scope`                               |
| `command`        | stdio | An installed, pinned command, never a package downloaded at start such as `npx -y`                                                            |
| `args`           | stdio | The arguments of the command                                                                                                                  |
| `env`            | stdio | The whole environment of the process, the values of its references secrets: it inherits nothing else, so give `PATH` or an absolute `command` |
| `org`            | both  | The org the server serves, required                                                                                                           |
| `playbooks`      | both  | The playbooks of the org it serves; every playbook of the org when left out                                                                   |
| `allowed`        | both  | The tools of the server a function may name; every tool of the server when left out                                                           |
| `testable`       | both  | The tools `test_tool_call` may test although the server does not mark them read-only, each among `allowed`; none when left out                |
| `record_content` | both  | Whether the arguments and answers of calls are kept whole, scrubbed, in the playbook's recorded content; `true` when left out                 |
| `request_id`     | both  | The response header, or the key of the metadata of a result, in which the server carries its own id of a request, recorded with each call     |

A secret is a value resolved from a `${NAME}` reference to the environment when the settings are read, an `auth` credential, or a token minted from one, and nothing else: a header such as `X-Region: production-eu` or an environment value such as `MODE=production` is not, and is never scrubbed. The scrubber (`src/bounds/secrets.ts`) replaces each secret as written, as it is written inside a JSON string, where a quote, a backslash or a line break in it is escaped, and as it is written inside JSON twice, as in a result whose text content is itself JSON, so a secret in the recorded arguments or result of a call is caught too. A value shorter than 8 characters is never scrubbed, since replacing it would erase ordinary words in every message; a reference that resolves to one is still a secret in every other sense, and the operator gives a server a key at least that long. Only `headers`, `env` and `auth` may hold a reference: one in `url`, `command` or `args` is refused with its pointer, since a key in an argument shows in the listing of the machine's processes and a key in a URL is not a header. A value that looks like a credential written out is refused, as a model gateway's key is, and so is a password in a `url`, and a user, a query value or the part of an argument after its `=` that looks like one, as in `--key=sk-live-...`; a value is judged by what it holds, never by the name it is given, so `--token-file=/run/secrets/notes` and `?token_type=bearer` are accepted. The settings also refuse an entry with neither `url` nor `command` or with both, a name outside 1 to 32 lowercase letters, digits and hyphens starting with a letter, the name of a model provider or gateway, a missing org, an org or playbook that is not an id, an `Authorization` header beside an `auth` block, an issuer that is not https (or http on a loopback address), a header the MCP client sets itself, the fields of the other type, and the refusals of `allowed` and `testable` above. Each problem names its setting and a JSON pointer, never a value; `McpSettingsInvalid` carries them all.

Nothing is learned from a server when the settings are read: the server starts without the network and without spawning anything.

## A run's tools

`makeToolAccess(settings, { reportServerMessage, reportUntestable, fetch?, now?, timing? })` holds one link per configured server and answers:

- `configured`: whether any server is configured, which makes `run_definition` destructive.
- `testing`: each server's name with its `allowed` and `testable`, which `test_tool_call` checks a tool against on the entry of the server it names.
- `open(context, references)`: the tools of one caller, for its id, org, playbook and journal and the metadata its calls carry, and the `server/tool` references it names. A run gives its run id as `auto.on/run_id` (`runIdKey`, which `@on.auto/mcp/policy` exports).
- `named(address, references)`: whether every reference names a server that serves the playbook and a tool its operator allows, the result of `namedLinks` and nothing else, with no connection, which an interaction function's run checks at its start.
- `startOf({ reference, input })`: the fields of the start of one call, the server, the tool, the size of the scrubbed arguments and, where the entry keeps content, their digest, the arguments kept whole and scrubbed in the playbook's recorded content first, which a delivery, a read or a telling records before it calls.
- `callOnce(call, runCall?)`: one call of one tool for an interaction function, its call, a delivery, a read or a telling (see [One call](#one-call)).
- `listServers({ org, playbook }, named?)`: the servers that serve the playbook, or every server of the org when `playbook` is `undefined`, or only the one named, with their tools (see [Listing the tool servers](#listing-the-tool-servers)).
- `playbooksServedBy(server)`: the playbooks of its org a server serves, as its entry's `playbooks`, or `['*']` when the entry leaves them out, read from the settings without loading anything.
- `close()`: ends every session and stops every process, when the server stops.

`open` fails with `ToolNotOffered` when a reference names a server not configured for the run's org and playbook (`mcp_server_not_configured`), a tool the operator does not allow (`tool_not_allowed`), or a tool its server does not list (`tool_not_listed`), and with `McpServerFailed` when a server cannot be used (`unreachable`, `failing`, `rate_limited`, or `key_refused` when it answers HTTP 401 to the key the runtime gives it). Otherwise it connects to each named server, lists its tools once, and keeps that listing for the run: a `list_changed` notification changes nothing, and a call to a tool the server no longer has is a tool error. `server/*` offers every listed tool the operator allows.

`RunTools` offers each tool under its model-facing name, `mcp__server__tool`, with characters outside letters, digits and underscore mapped to underscores, cut to 64 characters with an 8-character hash when longer or when two names would collide. A numeric suffix resolves any remaining collision, so every tool offered in a run has a distinct name. Its description is cut to 4 KiB and the server's input schema is unchanged. It also says whether the calls have ended (`callsEnded`, `ended`, `ending`), whether the run called any tool (`calledAny`), whether every tool it called is one its server marks `readOnlyHint` (`calledOnlyReadOnly`), which decides whether a run that cannot finish ends `tools_unfinished` or `effect_unknown`, and the tools it used in words (`usedInWords`), and lets the run's servers go (`close`).

A call of an offered tool:

1. is refused as a tool error, never sent and never recorded, when the run's calls are spent, its arguments are too large, or it repeats a call made twice already;
2. records `tool_call_started` through the run's journal, which answers the number the run's record gave the call, and is not sent if that fails, the sequence of this step and the next two being the one `journalledCall` (`src/calls/tool-caller.ts`) that `callOnce` shares;
3. is forwarded as a `tools/call` request through the client's `request`, which checks the answer against the protocol's call result and never against an output schema the server declares, so a tool that broke its own schema still answers, with the metadata the opener gave, a run's id under `auto.on/run_id`, within its deadline, waiting out a 429 whose `Retry-After` fits the longest wait, opening a session the server forgot once, and restarting a `stdio` process that exited once per run;
4. records `tool_call_answered` when the tool answered, or `tool_call_failed` when it did not, unless the run was cancelled meanwhile;
5. answers the model: text content as text, structured content only when there is no text, other content as a one-line placeholder, an `isError` result as a tool error, and a failure as a tool error naming the server, all scrubbed of the entry's secrets and minted tokens. A server's `instructions` never reach the model. The answer is whole unless it would not fit the room the caller gives the call, the model's context window less what the conversation holds so far, as the reasoning capability counts it: then it is cut where it stays valid JSON, closing what the cut left open (`cutWhereValid` in `src/bounds/structural-cut.ts`), or at a code point for text that is not JSON, with a note of how much was left out, and `tool_call_answered` records what the model read in `shown_bytes`. A call given no room, as where the catalog does not know the model's window, is read whole and the provider decides.

The call answers a `CallReply`: the model reads its `text` and `isError`, and beside them it carries what was recorded, the `outcome`, `resultBytes`, the size of the whole answer, `shownBytes` where the model read less, `durationMs` and `serverRequestId`, with `not_sent` as the outcome of a call refused inside the playbook or whose start could not be recorded. `RunTools.answeredBytes()` adds up the size of every answer of the run, which the reasoning capability names when a provider refuses a request as too long.

Where a server's tools are first listed, by a listing, a run's opening or a test (`connectedTo`), a server none of whose allowed tools carries `readOnlyHint` and whose entry has no `testable` is reported once to `reportUntestable`, by name, for the life of the access, which the server logs as one line at INFO saying that `test_tool_call` can test none of its tools and that the tools safe to test go under `testable` (`untestableNoting` in `src/tool-tests/testing-guard.ts`). Nothing is noted at start, since no server is asked before a run or a listing needs it.

A server failure is also reported to the operator through `reportServerMessage`, bounded and scrubbed, naming the run by `run_id` or a test by `tool_test_id`, whichever the opener's metadata gives, and the fifth ends the run's calls, with `ending()` saying `failing` or `rate_limited`.

## One call

`callOnce({ org, playbook, reference, input, meta, longestRetryWaitMs? }, runCall?)` (`oneCall` in `src/one-call`) makes one call of one tool for an interaction function: the call of a function that asks a system, a delivery of a request, a read of the replies to it or a telling. It refuses what a run's opening refuses, in the same words: `namedLinks` refuses a server not configured for the playbook's org and playbook, or a tool the operator does not allow, with no connection; then it takes the server's session within the open bound, 10 s (`takenWithin`), letting go of a session that opens later, starts a `stdio` process that exited again within the same bound (`boundedSlot`), lists the server's tools as a run's opening lists them (`listedThrough` of `src/access/server-listing.ts`), within that bound too, and refuses a tool the server does not list. A caller that passes `runCall`, `{ callId, journal }`, has `tool_call_started` recorded on its run once the tool is found and before the call is sent, and `tool_call_answered` after, through `journalledCall`, the sequence a run's calls follow; a start the journal does not record ends the call path with a defect, and nothing is sent. A caller that passes none records what it records itself, before calling, with the fields `startOf` gives, and after, from what the call answers. The call waits out a 429 whose `Retry-After` fits the caller's `longestRetryWaitMs`: none for a delivery, a read or a telling, whose schedules honour the wait, and `toolBounds.longestRetryWaitMs` for an interaction function's call. It opens a session the server forgot once, within the open bound. The call carries the metadata its caller gives, as a run's calls do: a call or a delivery gives the run's id under `auto.on/run_id`, a delivery the delivery's id under `auto.on/delivery_id`, the same on every attempt of one request, and a read or a telling its own id under `auto.on/conversation_call_id` (`runIdKey`, `deliveryIdKey` and `conversationCallIdKey`, which `@on.auto/mcp/policy` exports). It answers the call whole, `CalledOnce` ([decision 0021](../../docs/decisions/0021-asking-a-system.md)):

- `unopened`, sent nowhere, refused as `tool_not_offered`, with the `because` and words of `namedLinks` or, for a tool the server does not list, `tool_not_listed`, or as `mcp_server_failed`, when the server could not be reached, no connection opened or its tools were not listed within the bound, with the `because` and words of a run's opening, cut at 1 KiB and scrubbed;
- `answered`, with the outcome `result` or `tool_error` and the fields of `tool_call_answered` in `answered`, or `server_failure`, `timed_out` after 30 s, `cancelled`, `arguments_refused` or `too_large` and the fields of `tool_call_failed` in `failed`; the words of a failure cut at 1 KiB and scrubbed, the wait a 429 asked for in `retryAfterMs`, the hints the server gave the tool in its listing as `annotations`, and for a result what the tool answered whole, its `content` blocks and its `structuredContent`, read back from the answer once it is scrubbed of the server's secrets.

What a tool answered is read two ways, in `src/bounds/tool-results.ts`: `resultText`, what a model sees, text content as text and structured content only when there is no text, and `answerDocument`, the document a call's `read` points into, the structured content, else the first text block parsed as JSON, else that text, or none when the tool answered neither.

## The playbook's calls in a conversation

The reads and tellings of an interaction function are calls of the playbook's own, on a stream of their own under the playbook, `conversation-calls/<id>` (`src/own-calls`), decided by the one decider of such calls, `conversationCallDecider`: `replies_read`, one fact appended after a read that found a reply, carrying the fields of the start and the answer of its call, the conversation, the cursor, the replies considered, taken and refused, and the wait a 429 asked for, or `reading_failed` after one that failed, with `because`; and for a telling `telling_started`, before it is sent, and `telling_succeeded` or `telling_failed` after, caused by it. `repliesReadOf`, `readingFailedOf`, `tellingStartedOf` and `tellingEndedOf` build them. `conversationCallPresenter` shows them in a playbook's events, `arguments` and `answer` read from the recorded content where each is within 2 KiB and otherwise their sizes, in words that name the conversation and the tool; no recall function folds them and no trigger takes them.

## Listing the tool servers

`defineListToolServers(access)` makes `list_tool_servers`, `GET /tool-servers` relative to the playbook, under `playbook:read`, which reaches outside (`openWorldHint` over MCP). It answers `{ tool_servers }`: each server that serves the playbook's org and playbook, sorted by name, as `{ name, type, tools }`, or `{ name, type, unavailable, because }` for a server that could not be asked, whose words say why: `key_refused` when it did not accept the key the runtime gives it (HTTP 401), which only the operator can put right, otherwise `failing`, `rate_limited` or `unreachable`. `server` keeps only the server of that name, and asks no other; a name that no server serving the playbook has is `invalid_input` at `/server`, whose words say so and to call it without `server`.

`listServers` lists as `open` does, through the same link (`connectedTo` in `src/access/server-listing.ts`), under the same bounds: it takes a connection, lists the server's tools within `openMs`, and lets the connection go, so an `http` session no run holds is ended once the listing has its tools, and a `stdio` process is started when no run started it and kept until `close()`. Listings made at once share the link's connection, as runs do, and one listing of an `http` server no run holds costs it five requests when the server issues a session id: initialize, its notification, the stream `GET`, `tools/list` and the `DELETE` that ends the session. A server that issues none gets four, since the MCP client sends the `DELETE` only for a session it was given. A listing interrupted meanwhile still lets its connection go once the server answers. The tools are those `server/*` would offer a run (`offeredOn`): what the server lists that its entry's `allowed` names, or all it lists when `allowed` is left out, in the server's order, each with its `name`, its `description` cut to 4 KiB as a run cuts it, its input schema as `input_schema`, the hints its server gives it as `annotations`, `readOnlyHint`, `destructiveHint`, `idempotentHint` and `openWorldHint` as booleans and only when it gives any, and `testable`, whether `test_tool_call` may test it: when its server marks it read-only, or its entry's `testable` names it. The words name the tools that can be tested, or say none can. Every server serving the playbook is asked, since its entry allows at least one tool. A server that cannot be used is `unavailable` with the words `McpServerFailed` would carry, cut to 1 KiB (`toolBounds.failureBytes`, the bound a delivery's detail has too), and the other servers are listed beside it. The listing adds no header, environment value, URL, command or credential of its own; what a server writes, the names, descriptions, the keys and values of input schemas and the words of a failure, is passed on scrubbed of every entry's secrets and minted tokens before it is cut, and, as everywhere, a secret shorter than 8 characters is never scrubbed. When no server serves the playbook, it answers an empty list without loading the MCP client.

`defineListToolServersInOrg(access, lookUpPlaybook)` makes the same name at the org's scope, `GET /tool-servers` relative to the org, an org query permitted by `org:read` or `playbook:read`, as `list_playbooks` is, since a key that may read a playbook may see what serves it. Its input adds an optional `playbook` to `server`: without it, it answers every server whose `org` is the org, each with `playbooks`, the playbooks it serves, `['*']` for an entry that leaves them out; with it, the servers that serve that playbook, as the playbook's own listing has them, each with `playbooks` too, and the words of the playbook's listing. A key limited to some playbooks is shown in `playbooks` only the playbooks it may access, and `['*']` as it is; the dispatcher refuses it the listing of the whole org, since an org operation that takes `playbook` checks the caller's access to the playbook it is given, and none is given, with the detail `The caller may access only some playbooks of this org; name one of them in playbook`. Given a playbook, it first looks it up with `lookUpPlaybook`, a `PlaybookLookup` that needs `OrgReader` and fails with `NotFound`, since the org's playbooks are the registry's and the dispatcher looks up no playbook of an org operation: the server gives `foundPlaybook` of `@on.auto/playbooks`, so a playbook the org does not have is `not_found` in the words of the playbook's own route, and no server is asked. A name no server of the org, or of the playbook, has is `invalid_input` at `/server`, whose words name the org or the playbook. Every other rule of the listing, the asking, the bounds, the scrubbing and each entry's `allowed`, is the playbook's, through the same `listServers`. Its words open with "The playbooks of this org may use 2 tool servers." and name each server with its playbooks, "“graph”, for every playbook, offers 2 tools: search and echo; search can be tested.", and an org with no server says so and that the give-tools guide says what whoever runs the server needs. Over MCP, `/mcp` offers this operation in place of the playbook's, under the same name, its `playbook` its own and optional (see the api README's [playbook argument](../api/README.md#over-mcp)), the org endpoint offers it too, and a playbook endpoint offers the playbook's.

## Testing a tool call

`defineTestToolCall(access)` makes `test_tool_call`, `POST /tool-servers/{server}/tools/{tool}/test` relative to the playbook, a command under `playbook:write` that reaches outside (`openWorldHint` over MCP) and may change something outside, which makes it destructive, only while an entry marks a tool testable. It calls one tool of one server with `arguments`, `{}` when left out and at most 16 KiB as JSON, refused at `/arguments` by its input schema, as a run of a reasoning function would call it, and answers what that run's model would see and the document a call reads: `{ test_id, server, tool, outcome, text, answer?, result_bytes, duration_ms, server_request_id?, tested_at }`, `succeeded` however the tool answered, with the outcome `result`, `tool_error`, `server_failure`, `timed_out` or `too_large`, and `result_bytes` the size of the answer as kept, scrubbed. `text` is `resultText` and `answer` `answerDocument` of the same answer, scrubbed alike, `answer` left out when the tool answered neither structured content nor text and when it takes more than 64 KiB as JSON.

A test reaches the tool in the one way a run does, through `ToolAccess`: it opens the tools with one reference, under a context whose id is the test's, whose journal records the test and whose metadata carries the test's id under `auto.on/tool_test_id` and no run's id; `namedLinks` refuses a server that does not serve the playbook or a tool the operator does not allow before any connection, and the opening refuses a tool the server does not list; the words of these three refusals end with what `list_tool_servers` shows, from the test's own `remedies`, where a function's refusal speaks of the function. Then it checks the guard (`src/tool-tests/testing-guard.ts`): the tool can be tested when its server marks it `readOnlyHint`, or the entry of its server marks it testable, and that entry allows it; any other is `unavailable`, kind `tool_not_offered`, because `not_testable`, and its connection is let go without a call. Otherwise it makes one `call`, admitted, recorded, forwarded, scrubbed and cut as a run's, and lets the tools go through the `close` of the tools it opened once that call has settled, also when the caller goes away meanwhile: the call is aborted, nothing is answered or recorded of it, and the session is ended once the forwarded call settles; the test waits for the call to answer, not for the session to end, so a failure of the call, such as a start the ledger refuses, is still reported as an incident while a server slow to end its session does not hold the answer. A test of an `http` server no run holds costs it six requests, initialize, its notification, the stream `GET`, `tools/list`, `tools/call` and the `DELETE`, or five when the server issues no session id; a test and a listing made at once share one session.

Each test is two events on a stream of its own, `tool-tests/<test_id>`, appended through `PlaybookWriter` by the journal of the playbook's own calls, `ownCallJournal(kind, place)` (`src/own-calls`), with the one decider of such calls, `ownCallDecider`, whose turns are the stream kind's, for a test a start once and an ending once after it: `tool_test_started` and then `tool_test_answered` or `tool_test_failed`, the facts of `tool_call_started`, `tool_call_answered` and `tool_call_failed` with `test_id` in place of the run's number and the model's call id, built by the same builders from the same recording, so content is kept and scrubbed where and as a run's is. The ending names the start as its cause. A start the ledger refuses fails the test with an incident before the call is sent. `toolTestPresenter` shows them in a playbook's events, `arguments` and `answer` read from the recorded content where each is within 2 KiB and otherwise their sizes, with summaries that say who tested which tool and how it answered in the words of a run's calls. A server failure is reported to the operator under `tool_test_id`.

## Connections

Each entry has one link. An `http` link opens a session when a run or a listing first needs it, shares it with every run and listing that holds it while it is open, and ends it explicitly when the last of them lets it go. Session termination is bounded by the connection timeout; the client closes even if the remote DELETE never answers. A `stdio` link starts its process on first use and keeps it until `close()`; it spawns the command without a shell, with the entry's `env` and nothing else, reports each line the process writes to stderr (at most 100 lines of 2000 characters), and takes at most 4 MiB of output at once: past it the link closes the process and every call it was answering ends `too_large`. Closing a process ends its input, and kills it through its handle after two seconds.

With an `auth` block, tokens come from the MCP client's client-credentials or private-key provider, with the issuer pinned: the client sends the credential to no authorization server whose metadata names another issuer. One token is minted for every concurrent run, renewed a minute before it expires (or halfway through a shorter life), and minted again once when the server answers 401; a second 401 is a failure. Every remote request goes through the `fetch` given, the server's outbound fetch, so `HTTPS_PROXY` and `NODE_EXTRA_CA_CERTS` apply, and a certificate the server does not trust is a fixed message.

The MCP client has no logging option. The errors it meets, such as a line from a process that is not JSON-RPC or a stream it could not read, reach the client's `onerror`, which reports them through `reportServerMessage` as the messages of their server, scrubbed. They are bounded as the stderr of a `stdio` process is: at most 100 of 2000 characters for each process started or session opened, then one line saying the rest is not shown. The few warnings it writes to the console about how it was configured are left on stderr: catching them would mean patching the global console of the whole server, which every other library writes to as well.

## Bounds

`toolBounds` holds them; `timing` replaces the three durations in tests.

| Bound                                                                   | Value                                        |
| ----------------------------------------------------------------------- | -------------------------------------------- |
| Tool calls in one run                                                   | 25                                           |
| One answer, as the model reads it                                       | whole, or cut to its room                    |
| One answer of an `http` server (`httpAnswerBytes`)                      | 16 MiB, past it `too_large`                  |
| One answer of a `stdio` server                                          | 4 MiB of output at once, past it `too_large` |
| One call's arguments                                                    | 16 KiB                                       |
| The same tool with the same arguments                                   | twice                                        |
| Server failures in one run                                              | 5                                            |
| The longest wait a 429 may ask                                          | 10 s                                         |
| One call                                                                | 30 s                                         |
| Opening a connection, or starting a process, and then listing its tools | 10 s each                                    |
| A whole run (`runBoundMs`)                                              | 10 min, or one step longer                   |
| A tool's description                                                    | 4 KiB                                        |
| The words of a server failure, in a listing and one call                | 1 KiB                                        |
| The answer `test_tool_call` shows (`testedAnswerBytes`)                 | 64 KiB                                       |
| The answer a read of replies takes (`readAnswerBytes`)                  | 64 KiB                                       |
| Calls in one test                                                       | 1                                            |

A run's reading is bounded beside these by the reasoning capability, in the input tokens its model calls add up to, `REASONING_MAX_INPUT_TOKENS`; past it, as past the calls of a run, the model answers from what it has. What a call keeps is not bounded beyond the transport: the arguments and the answer go whole, scrubbed, into the playbook's recorded content, which the ledger keeps in chunks beside the facts.

## What is recorded

The arguments, as `JSON.stringify` writes them, and the protocol answer are scrubbed of the entry's secrets in place, keys, values and numbers alike, and the scrubbed text is the one text a fact describes: its size, measured once, is `arguments_bytes` or `result_bytes`, and where the entry keeps content it is kept whole through the `RecordedContent` port of `@on.auto/operations`, as its UTF-8 bytes of the media type `application/json`, before the fact that names it is appended, and its SHA-256, its own address, is `arguments_sha256` or `result_sha256`, so a fact never names content that is not there. The recording puts the text with that digest expected, so the port checks the bytes against it and, when the playbook already holds the digest, writes nothing, however large the answer (`KeepContent` keeps a text and answers the digest the port kept it under). The digest is present exactly when the content is kept: an entry with `record_content: false` gives its facts the sizes alone, since a digest of a document a reader can guess would confirm the guess, and nothing digests a text that is not kept, so the digest of what was received, before the scrub, is nowhere. When the secrets change between two receipts of one answer, as when a token is minted, each scrubbed text is kept under its own digest and each fact names its own. What the model read is `resultText` of the kept answer, cut at `shown_bytes` where the fact has it; the reply's `resultBytes`, the run's answered bytes and `test_tool_call`'s `result_bytes` are the same size of the kept text.

`tool_call_started` carries the call's number in the run, the id the model gave it, the server and tool, the size of the arguments and their digest where they were kept, and `read_only: true` when the server marked the tool `readOnlyHint` when it was listed. A call ends with one of two facts. `tool_call_answered`, when the tool answered, carries the number, `is_error`, the size of the answer and its digest where it was kept, `shown_bytes` when the model read less than the whole, the duration and the JSON-RPC id. `tool_call_failed`, when it did not, carries the number, `because` (`arguments_refused`, `server_failure`, `timed_out`, `cancelled`, or `too_large` for an answer past the transport's cap, which is not counted among the server's failures since the server answered), the words of the failure as `detail`, cut at 1 KiB and scrubbed, the duration and the JSON-RPC id. An entry with `request_id` adds the server's own id of the request to either. The fields of the facts are written once, as the effect schemas `CallStartedSchema`, `CallAnsweredSchema` and `CallFailedSchema`, which the package exports, and `@on.auto/definitions` builds the run's events from them, adding the call's `number`; who and when are the context of the message, as for every fact.

## Testing

`@on.auto/mcp/testing` holds a fake MCP server built with the MCP server package:

- `serveFakeMcp({ bearer?, client?, requestIdHeader?, issuesSessionIds?, annotated?, hints?, chat?, data? })` serves it over Streamable HTTP on a loopback port the system picks, with a bearer check or a fake authorization server, sessions, or none with `issuesSessionIds: false`, its tools listed without their annotations with `annotated: false`, its tools' annotations replaced by `hints`, and ways to answer the next requests with a status (`answerNextWith`, for a 429 with `Retry-After`, or `answerNextOf` for the next of one method alone, such as `tools/call`), answer the next tool call after messages that are not JSON-RPC (`answerNextCallAfterNoise`), forget every session (a 404), revoke tokens (a 401), remove a tool and send `list_changed`. With `chat: true` it also holds a chat, `chat`, whose `post_message` posts a message and answers where it landed and whose `thread_replies` lists the messages of a conversation or of one thread after a point, oldest first, and a test replies as a person with `chat.reply`. With `data: true` it also holds tools whose answers a call reads: `thread`, structured content beside a summary text, the replies of `threadReplies`; `pages`, one page and the cursor of the next; `blocks`, two text blocks of JSON; `strict`, which refuses an argument that is not a whole number with -32602; and `promised`, which declares an output schema of a count and answers `brokenPromise`, a count that is not a number. `holdNextOf` holds the next request of one method unanswered, such as a listing that never comes. A request its handler fails on is answered with a 500 and recorded in `failures()`, beside the requests in `seen()`, instead of rejecting where no test awaits it.
- `fakeStdioServerPath` runs the same tools over stdio under `node`, with `--chatter`, `--pad`, `--stdout`, `--linger-ms` and `--start-once` to make it talk, misbehave or fail to start again. Start it with `process.execPath` directly, never through a package manager: it imports only the MCP server package and the fake's tools, not `effect`, and answers its first message in about 90 ms on a laptop. A spawn is real time, so a test that starts it takes `stdioTestTimeoutMs`, 30 s, and its connection `patientTiming`, and a file shares one process across the tests that only need it running.
- Its tools answer text (`search`, `echo`, `graph.query.v2`), structured content (`profile`), non-text content (`photo`), a denial marked `isError` (`denied`), an error (`broken`), slowly (`sleep`), at length (`large`), the channels of a workspace (`list_channels`, `fakeChannels`), with its environment (`environment`), or by exiting (`exit`). Their annotations cover every case of a test: `search`, `profile`, `photo`, `denied`, `sleep`, `large`, `broken` and `list_channels` are marked read-only, `graph.query.v2` read-only and destructive at once, `exit` destructive, the long-named tool only additive (`destructiveHint: false`), `echo` and `verbose` have none, `environment` has annotations with a title and no hint, and `verbose` has a title of its own.
- `openFakeToolRun`, `reportingAccess`, `noToolServers`, an access with no server, `recordingCallJournal`, `toolRun`, `controlledSignals` and `inTurn` open a run's tools against it, and `toolTests` dispatches `test_tool_call` as `toolTester`, a caller that may write the playbook, over a memory ledger, optionally one that refuses every write.
- `recordingTimer` stands in for the timer a link's options take, which bounds the end of a session: it records each wait and whether it was stopped, so a test of that deadline touches no global timer. `fetchWithDeletion` sends a session's `DELETE` to a handler of the test's own.

## A manual run against an agent services gateway

The tests never call a real gateway. Once, before relying on one, run a reasoning function against it by hand:

1. In the gateway, create an application for the playbook and an API key for it, and attach a policy that allows the reads the run needs and denies one field you can name.
2. Export the key as `GRAPH_API_KEY` where the server runs. It never goes in the configuration file.
3. Configure the gateway as an `http` entry:

   ```yaml
   mcp_servers:
     graph:
       url: https://gateway.example.com/mcp
       headers:
         Authorization: Bearer ${GRAPH_API_KEY}
       org: acme
       playbooks: [sales]
       allowed: [search, introspect, validate, execute]
   ```

4. Start the server and create a reasoning function in that playbook with `tools: [graph/*]` whose prompt asks a read-only question the policy allows, including the denied field.
5. Run it with `run_definition`, then read the run with `get_run_history`.

Check that the run succeeded; that its history shows a `tool_call_started` and a `tool_call_answered` for each call, the denial answered with `is_error` and the model's answer saying the field was withheld, and that `get_event` reads each answer whole; that the gateway's audit shows the calls made by the application, each carrying the run's id under `auto.on/run_id`; that `run_definition` for the same `run_id` answers the same run again; and that the server's log holds no key or token.
